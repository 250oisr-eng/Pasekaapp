## 6. Нерешённые вопросы и риски

1. **Доменная модель секций/семей/маток не определена.** Источник описывает разделение одной семьи на три секции, три семьи в альтернативной зимовке и последующее объединение в одну. Он не определяет, должны ли три секции иметь один familyId с тремя матками или три самостоятельных familyId с общей историей происхождения. До решения пользователя нельзя связывать `sections[]` с `S.families` и реестром маток.
2. **UI физической установки принадлежностей отсутствует.** В `renderAccessoryInventorySection()` можно зарегистрировать предмет и изменить состояние; установка из склада в улей недоступна. `PasekaEquipmentItems.place()` поддерживает location/footprint на уровне API, но интерфейса выбора корпуса и FULL/HALF нет.
3. **Профиль `sectional-multiqueen-v1` отсутствует в `HIVE_PROFILE_CATALOG`.** `PasekaInventory.profileForState()` обслуживает встроенный объект профиля либо Farrar; неизвестный профиль без объекта возвращает `null`. Общая физическая модель не поддерживает отдельные секции, днища и межсекционные соединения.
4. **UI техпроцесса неполон.** Карточка создаётся с `sections:[]` и `queens:[]`; нет редактора секций, маток, физических корпусов и принадлежностей. Статусный редактор не может подготовить данные для OP-04/OP-07.
5. Точная физическая схема 2/4 медовых корпусов и связанные с ней перемещения должны быть реализованы только по подтверждённой геометрии; не додумывать отсутствующие детали.
6. Последовательность OP-07 имеет варианты в источнике: сразу, после снятия сетчатых заглушек либо примерно через 12 дней после установки вторых корпусов. Основной пользовательский сценарий для интерфейса не выбран.
7. PR #90 и #91 затрагивают общие документы управления; ранее GitHub сообщал о конфликте/непригодности независимого слияния PR #90. Нужна консолидация без потери протокола DOCX.
8. PR #94 дублирует часть проверки PR #95; не объединять оба независимо без анализа зависимостей.
9. Workers Builds ранее завершался failure без поясняющих аннотаций; причина не установлена. Deployment не подтверждён.
10. CI не заменяет проверку в реальном браузере и на физическом Android-устройстве. PR #95, #96, #99 и #100 остаются Draft; merge и публикация не выполнялись.

## 8. Следующая конкретная задача

**Следующий шаг требует одного доменного решения пользователя.**

Как приложение должно идентифицировать три секции после OP-04?

- **Вариант A:** одна исходная семья/колония с одним familyId, разделённая на три секции; каждая секция имеет свою матку и два физических корпуса. История семьи общая, наблюдения и операции могут иметь детализацию по секциям.
- **Вариант B:** три самостоятельные семьи с отдельными familyId, каждая привязана к своей секции и матке; дополнительно сохраняется общий идентификатор исходной семьи/системы для истории разделения, совместной работы и последующего объединения.

Источник описывает оба состояния в разных фазах сезона, но не задаёт идентификаторы для цифрового реестра. Выбор меняет связи журнала, перемещения, зимовки, объединения и отводков. До ответа не реализовывать связь `sections[]` с `S.families` и матками.

После решения:
1. Спроектировать минимальную модель секции, физической пары корпусов, матки и семейной идентичности.
2. Согласовать её с физическим реестром и `PasekaSectionalTechProcess`.
3. Только затем проектировать UI установки двух больших решёток, постоянных технических решёток, заглушек и конфигуратора.
4. Не активировать профиль, пока все связанные модули, миграции, backup/restore и офлайн-кеш не поддерживают его полностью.

### 2026-11-16 — Аудит backup/restore пути физических принадлежностей (анализ кода завершён; интеграционный тест не выполнен)

- В PR #95 проверен экспорт: `downloadBackup()` сериализует весь объект состояния `S`, включая `equipmentInventory.items`, `itemEvents` и footprint.
- Проверен снимок сохранения: `save()` включает полный `equipmentInventory` в исторический snapshot и клонирует состояние перед записью.
- Проверена валидация импорта: `validateBackupState()` запускает `PasekaEquipmentItems.inspect()` и `validateReferences()` при наличии реестра принадлежностей; технологические записи проверяются с полным state.
- Проверена предварительная проверка сырых данных: `validateRawBackupIntegrity()` передаёт полный state в `validateStoredRecords()`.
- Проверен restore: `restoreBackup()` валидирует архив до подтверждения, запускает `migrateState()`, повторно проверяет `validateVirtualApiary()` и записывает восстановленное состояние через `writeMainWithBackup()` в одной IndexedDB readwrite transaction, сохраняя предыдущее состояние.
- Проверен `migrateState()`: предварительная и финальная проверки техпроцесса передают полный объект `S`. Первоначальное подозрение об отсутствии третьего аргумента не подтвердилось после чтения точного участка файла.
