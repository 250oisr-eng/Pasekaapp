## F0: ситуация до изменения

Исполнитель `js/sectional-season-physical-executor-v2.js` требует точных `targetLayout`, `bodyMoves`, `itemMoves`, `storageLocations`. Форма OP-11–14 имеет подтверждение корпусов и диафрагм, но не полный сквозной ввод всех этих структур; свободный JSON / ручное сочинение ID опасно. Операции не должны присваивать фактическое выполнение из выбранного варианта или календарного ориентира.

Точные исходные физические правила из кода и сверки с документом:
- OP-11: сохранение **трёх действительных верхних** корпусов, итоговая идентичность матки не выдумывается.
- OP-12: три семейства, зимний столб 2+1+1, две отдельные сетчатые диафрагмы с реальными позициями `lower-middle`/`middle-upper` и стеком. Лично подтверждается, какая семья сильнейшая.
- OP-13: две однокорпусные семьи получают дополнительные фактически складские корпуса и отдельные днища, диафрагмы снимаются с учётом реального места.
- OP-14: ранний медовый ярус снимается полностью вместе с двумя настоящими большими решётками; сохраняются три действительных верхних корпуса, по исходной технологии допускается сокращение до 3 или 4 гнездовых корпусов.
- `temporaryQueenIsolation` — **metalMeshPlug**, `closedOpenings` — **plasticPlug**. Нельзя считать их одним видом.

## F1: минимальная безопасная реализация

`js/sectional-season-body-manifest-v2.js`: `stageManifest(state,{operationId,hiveId,userConfirmedTargetLayout,targetLayout,storageLocations,itemMoves,...})`.

1. Источник и цель — один действительный `sectional-multiqueen-v1` улей/профиль/layout. Режимы переходов фиксированы для каждой OP.
2. Ни один новый физический корпус или ID не создаётся. Целевые и уже установленные корпуса сверяются с инвентарём, состоянием, точной вместимостью 6/10, профилем и историей реальных рамок; чужие ульи/старые legacy placements блокируются.
3. **Все** `bodyMoves` автоматически получаются из реальных позиций исходного и отдельно подтверждённого целевого layout, в точном формате `sectional-season-physical-executor-v2.js`. Перемещение не угадывается. Для каждого выбывшего корпуса обязательна явная фактическая метка склада, для каждого добавляемого — реальный статус склада.
4. Обязательные `itemMoves` **не выдумываются**. Ожидаемый набор вычисляется по физическим ссылкам на днища, крышки, подкрышники, кормушки, разделительные решётки, сетчатые диафрагмы, временные металлические и зимние пластиковые заглушки. Любой пропуск, чужой аксессуар или постороннее дополнительное перемещение — BLOCKED. Фактический склад/новая позиция указывается пользователем.
5. Нет автоматического `actualWorkConfirmed`, DONE, IndexedDB write, merge семей или удаления видео.
6. `ok:true` означает только **валидность исходно-связанного списка**, возвращает `stagedOnly:true`, `operationCompleted:false`, `physicalLayoutValidated:false`, `requiresFullPhysicalAndArchiveGates:true`. Полные физические валидаторы, `SECOND_DEVICE_VERIFIED`, atomic CAS и физическое подтверждение — отдельные обязательные ворота.
7. `index.html` + offline `sw.js` v333 содержат модуль; пользовательская форма **пока не допускает живое выполнение OP11–14**, а только имеющийся preflight. Никаких скрытых новых UI-кнопок записи.
