# Архитектура приложения «Пасека»

Версия: 1.0  
Основание: README.md, package.json, sw.js на main SHA 33c7a1f87d7cb2327a8d9dd39ffcdd614a707875.  
Статус: обзор текущей архитектуры верхнего уровня; не заменяет полный аудит исходного кода.

## 1. Текущая архитектура — подтверждённые сведения

### Клиент
- Основной интерфейс — PWA, размещённая через GitHub Pages.
- В репозитории основной UI находится в index.html; в нём присутствуют разметка, стили и значительная часть клиентского интерфейса.
- Отдельные клиентские модули находятся в папке js/ (README перечисляет домены голосового управления, оборудования, Varroa, инцидентов, сезонного планирования и анализа погибшей семьи).
- Service Worker sw.js кэширует оболочку и перечисленные статические ресурсы для offline-first поведения.
- manifest.webmanifest и иконки задают PWA-оболочку.

### Android
- Android-оболочка построена на Capacitor 6.2.1.
- package.json содержит сценарий android:sync через подготовку web-ресурсов и cap sync android.
- CI собирает Android Debug APK. Debug APK не является подписанным релизом Google Play и не доказывает проверку на физическом устройстве.

### Локальные данные
- README указывает на хранение данных пасеки в IndexedDB в браузере/приложении.
- Есть автоматические внутренние снимки, ручной JSON backup/restore, проверки целостности и защита от конфликтующих записей между вкладками.
- Облачная синхронизация данных пасеки между устройствами не реализована.
- Для проверки IndexedDB используется fake-indexeddb (package.json).

### Серверные возможности
- ИИ-советник использует Neon Auth и Cloudflare Workers AI через Cloudflare Worker.
- Worker развёртывается отдельно; коммит и публикация GitHub Pages не обновляют Worker автоматически.
- README указывает, что ИИ-оператор предлагает пакетные перемещения рамок и задачи; изменение требует локальной проверки, предварительного просмотра и отдельного подтверждения.
- Серверная модель не должна напрямую изменять локальную базу пасеки.

### Тестирование
- package.json задаёт npm test как node --test tests/*.test.mjs.
- Основные тесты — Node.js test runner; для тестов IndexedDB присутствует fake-indexeddb.
- Успешный тестовый результат действителен только для точного commit SHA.

## 2. Схема ответственности

Пользовательский интерфейс (index.html и экраны)
→ клиентские доменные модули (js/)
→ центральное состояние и механизмы сохранения приложения
→ IndexedDB и локальные резервные копии.

Отдельный сетевой контур:
UI ИИ-функций
→ Neon Auth / Cloudflare Worker
→ Cloudflare Workers AI.

Эта схема описывает границы ответственности на уровне README и файлов верхнего уровня. Точные имена функций, транзакционные границы и контракты хранилища должны быть подтверждены отдельным code review до изменений.

## 3. Предлагаемое место технологического модуля

PR #54–58 предлагают следующий путь интеграции, но он ещё не входит в main:
- доменная логика в js/sectional-multiqueen-techprocess.js;
- интеграция экрана в index.html;
- отдельный реестр состояния техпроцессов, связанный с существующим ульем;
- хранение в существующем состоянии приложения, без нового object store IndexedDB;
- миграция прикладной схемы и включение состояния в backup/restore;
- включение нового модуля в Service Worker cache.

Это предложение из незамерженной цепочки PR, а не утверждённая часть текущей main.

## 4. Архитектурные ограничения

- Все новые и существующие интеграции должны соответствовать политике бесплатности: платные тарифы, платные API и автоматические платные fallback запрещены.
- AI-функции могут зависеть от бесплатных лимитов; при исчерпании квоты они должны корректно сообщать о временной недоступности и не переключаться на платный режим.
- Не делать платный внешний сервис обязательным условием работы основных локальных функций приложения.


- Не создавать отдельную базу данных для технологического модуля без отдельного решения.
- Не вводить облачную синхронизацию в рамках работы над локальным технологическим журналом.
- Не допускать прямого изменения пользовательских данных ИИ-моделью.
- Не обходить штатную очередь сохранения, аудит, backup/restore и проверки целостности.
- Не менять IndexedDB schema/version без анализа всех путей чтения, записи, восстановления и старых архивов.
- Не добавлять клиентские ресурсы без обновления Service Worker cache и проверки offline режима.
- Не смешивать профили оборудования разных типов ульев.
- Не менять существующие модули вне согласованного scope.

## 5. Целевая архитектура технологического журнала

Целевые границы:
1. **UI:** отображает текущую фазу, операции, сроки, фактические наблюдения и предупреждения.
2. **Доменный модуль:** проверяет последовательность, варианты, предусловия и фактическую конфигурацию; не обращается напрямую к DOM или сети.
3. **Адаптер хранения:** сохраняет состояние через существующий механизм приложения после проверки его контракта.
4. **Аудит:** фиксирует кто/когда/что изменил, не подменяя фактическое выполнение операции.
5. **Backup/restore:** переносит техпроцесс вместе с остальным состоянием и проверяет целостность ссылок.
6. **Offline cache:** обеспечивает загрузку нужного модуля без сети.
7. **Тесты:** покрывают доменную логику отдельно от UI и затем интеграцию с сохранением.

Целевая схема не означает, что все эти уровни уже реализованы или полностью проверены.

## 6. Обязательные архитектурные контрольные точки

До слияния PR #54–58 проверить:
- нет ли дублирования или конфликтов с текущей моделью ульев/оборудования;
- безопасна ли миграция схемы и совместимость старых backup;
- атомарны ли сохранения и восстановление при отказе;
- корректно ли работает межвкладочная блокировка;
- не ломаются ли старые профили оборудования и UI;
- Service Worker cache содержит все необходимые ресурсы и корректно обновляется;
- полный npm test и Android Debug APK прошли на актуальном HEAD цепочки;
- фактическая конфигурация секций/маток/корпусов не выдумывается при создании карточки.

## 7. Не входит в текущую архитектурную задачу

Физическое управление ульями, датчики, автоматическая телеметрия, облачная синхронизация и автономное изменение базы ИИ-агентом не считаются реализованными и не должны добавляться без отдельного утверждённого проекта.


## Дополнение от 2026-11-16 — реестр физических принадлежностей

В Draft PR #89 начат отдельный модуль `js/equipment-items.js` с необязательным `equipmentInventory.items`. Он не заменяет `equipmentInventory.bodies` и не меняет IndexedDB schema/version. Предметы создаются только явной регистрацией пользователя; шаблонная комплектация и фиктивное создание запрещены. Запись содержит тип, состояние, текущее место, заметки и историю событий. Размещение сетчатых/пластиковых заглушек требует ID технического отверстия, постоянной технической решётки — ID соединения. Проверка структуры и ссылок уже подключена к `validateVirtualApiary` и `validateBackupState`; архивы без необязательных полей `items`/`itemEvents` остаются совместимыми. Полный backup/restore round-trip и пользовательский UI ещё не выполнены; связь с физической моделью секций остаётся неполной. До этого профиль секционного улья не активировать.
