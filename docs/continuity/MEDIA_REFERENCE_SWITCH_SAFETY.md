# Безопасное переключение фотографий на Blob-ссылки

Статус: проектирование, не разрешение на автоматическую миграцию.
Основано на PR #19–#23. Рабочие данные не меняются.

## 1. Текущее поведение, подтверждённое кодом

- Основное состояние хранится в IndexedDB object store `main`, ключ `state`.
- `save()` формирует `stateForSave = {...S, snapshots: nextSnapshots}`; массивы `records`, `plantObservations`, `pesticideIncidents`, `deadoutReviews` в основном состоянии остаются полными, включая `media`.
- Внутренние исторические снимки `S.snapshots` создаются из `lightRecords`, `lightPlantObservations`, `lightPesticideIncidents`, `lightDeadoutReviews`, где `media` исключено. Поэтому исторические снимки не являются источником восстановления фотографий.
- Полная автокопия и архив v1 должны сохранять старую структуру data URL в состоянии. Экспорт архива v1 сериализует состояние и отдельные видео; новый формат не должен менять смысл v1.
- В IndexedDB уже есть `media_blobs` и `media_migration_journal`. PR #21 копирует фото и пишет checkpoint одной транзакцией. PR #22/#23 проверяют соответствие источника и Blob без изменения данных.
- Миграционный engine пока не переключает ссылки в `main/state`; UI не использует Blob-ссылки.

## 2. Совместимая модель ссылки

Новая запись изображения в `media` должна сохранять все существующие метаданные и добавлять:
- `storage: "indexeddb-blob-v1"`;
- `blobId: string`;
- `mimeType`, `sizeBytes`, `sha256` (дублируются из Blob-записи для проверки).

Старое поле `data` нельзя удалять в первой фазе. После переключения оно может быть сохранено как legacy fallback до окончания периода наблюдения и подтверждения нового полного архива. Рендерер обязан понимать оба вида:
1. Если ссылка валидна и Blob успешно проверен — использовать Blob.
2. Если Blob отсутствует/повреждён, но `data` ещё есть — показать legacy-фото и диагностировать проблему, не перезаписывать Blob молча.
3. Если есть только ссылка, а Blob отсутствует — показать явную заглушку и ошибку восстановления; не подменять изображение пустым содержимым.

Не использовать постоянные object URL в состоянии или архиве. Object URL создаётся только на время отображения, освобождается при закрытии/замене представления. Запрещено мутировать исходное состояние во время рендеринга.

## 3. Протокол одного переключения

Переключение одной фотографии — отдельная операция с compare-and-swap по revision основного состояния.

Предварительные условия:
- dry-run содержит candidate и не имеет rejected-ошибок для этого фото;
- copy engine завершил копирование;
- verifier подтвердил checksum исходника, Blob и journal;
- исходный data URL в актуальном `main/state` совпадает с проверенным SHA-256;
- текущая revision равна revision, прочитанной до начала операции;
- доступно достаточно места для записи новой версии состояния и резервной копии.

Commit одной фотографии:
1. Прочитать актуальный `main/state` и revision.
2. Повторно проверить исходный data URL и Blob checksum до транзакции.
3. Подготовить новое состояние в памяти: только соответствующий media item получает storage/blobId/checksum; остальные поля и элементы остаются без изменений.
4. Открыть одну IndexedDB readwrite transaction по `main` и отдельному store журнала переключения (новый store; не переиспользовать copy journal).
5. Внутри транзакции повторно прочитать `main/state`, сравнить revision и точный исходный media locator/data fingerprint. При несовпадении abort.
6. Сохранить rollback record с предыдущим значением media item, его locator, прежней revision и migrationId.
7. Записать новое состояние с новой revision и записью аудита.
8. Записать checkpoint `committed` в том же transaction.
9. Только после события transaction complete сообщать об успехе.

Нельзя выполнять `await crypto.subtle.digest`, `Blob.arrayBuffer()`, сетевые операции или другие асинхронные вычисления между началом IndexedDB transaction и её завершением: транзакция может стать inactive. Все криптографические проверки выполняются заранее, внутри транзакции только синхронные проверки данных из запросов и записи.

## 4. Восстановление и rollback

- При прерывании до commit IndexedDB откатывает транзакцию целиком; исходное состояние остаётся прежним.
- При прерывании после commit, но до обновления интерфейса, приложение читает journal и проверяет фактическую revision/locator; повторный запуск должен быть идемпотентным.
- Rollback допускается только если текущий media item всё ещё соответствует committed blobId и revision не была изменена несовместимым действием. Иначе конфликт, без перезаписи новых данных.
- Rollback восстанавливает прежний media object целиком, не только поле data.
- Blob удаляется только после отдельной проверки отсутствия ссылок из всех коллекций, rollback journal, архивных staging-сессий и иных владельцев. В рамках миграции удаление запрещено.

## 5. Архивы и резервные копии

- Архив v1 остаётся неизменным и экспортируется в legacy-compatible виде: перед сериализацией разрешается ссылка в data URL либо собирается эквивалентный legacy media object. Нельзя записывать в v1 ссылку без включения соответствующего фото.
- Импорт v1 продолжает создавать прежние media objects с data URL; это валидный формат и после внедрения Blob-хранилища.
- Новый формат архива (если понадобится) должен иметь новую версию и отдельные manifest entries для фото с ID, MIME, размером и SHA-256. Нельзя менять формат v1 задним числом.
- Внутренние `snapshots` сейчас не содержат media. Нельзя заявлять, что они являются полным photo backup. Отдельно решить, включать ли туда ссылочные descriptors и как обеспечить их удержание.
- Полная автокопия должна оставаться восстанавливаемой. Перед переключением нельзя допускать ситуацию, когда текущая основная запись использует Blob-ссылки, а единственная пригодная автокопия содержит ссылки без Blob.
- В UI явно показывать разницу между локальным снимком состояния, полным фотоархивом и переносимым архивом.

## 6. Критерии допуска к массовому переключению

Все условия обязательны:
- тесты на crash/reload между каждой фазой;
- конфликт revision и параллельная вкладка;
- quota error на записи состояния и журнала;
- отсутствующий/повреждённый Blob;
- изменённый legacy data URL после копирования;
- повторный запуск после частичного batch;
- rollback после успешного commit и конфликт rollback;
- экспорт v1 до и после переключения, импорт в чистую базу и проверка визуальной доступности фото;
- проверка автокопии и восстановления;
- проверка нескольких фото в одной записи и одинаковых/дублированных файлов;
- Android WebView тест на реальном устройстве для чтения Blob и object URL.

Массовое переключение должно быть opt-in, ограничено небольшими пакетами и останавливаться при первой ошибке. Никакого автоматического удаления data URL до отдельного, проверенного этапа и явного решения владельца.

## 7. Границы текущего этапа

Этот документ не запускает миграцию, не меняет пользовательские записи, не переключает ссылки, не удаляет legacy data URL и не меняет архив v1. PR должен оставаться Draft до независимой проверки и CI.
