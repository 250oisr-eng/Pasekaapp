# План вынесения фото и вложений из основного состояния

Статус: проектное решение, реализация не включена.

## 1. Что подтверждено аудитом текущего кода

- Основное состояние хранится в IndexedDB store `main`, запись `state`.
- В `save()` формируется исторический снимок без `media` для записей журнала, наблюдений растений, инцидентов и разборов погибших семей.
- Само сохраняемое состояние формируется как `{ ...S, snapshots: nextSnapshots }`, поэтому текущие поля `media` остаются в основном состоянии. Это значит, что фотографии по-прежнему увеличивают размер `main/state`.
- Видео летка уже хранятся отдельно в store `entrance_media`; полный архив экспортирует их оригинальные Blob отдельно и проверяет контрольные суммы.
- Формат архива v1 допускает отдельные записи только для `state` и `entrance_video`. Фото из `media` сейчас сериализуются внутри `state.json`.
- PR #15–#17 защищают историю/автоснимки, но не устраняют размер основного состояния и не выносят фото из JSON.

## 2. Целевое хранилище

Добавить отдельный IndexedDB object store `media_blobs` с `keyPath: id`.

Запись медиа:
- `id`: случайный уникальный ID, не имя файла и не путь;
- `blob`: исходный Blob;
- `mimeType`, `sizeBytes`, `name`, `capturedAt`;
- `sha256`: контрольная сумма содержимого;
- `createdAt`, `schemaVersion`.

В бизнес-записях хранить только компактные ссылки:
`{ id, kind, name, mimeType, sizeBytes, capturedAt }`.
Ссылки не должны содержать base64/data URL.

Видео летка остаются в `entrance_media` до отдельного решения: у них есть очередь анализа, статусы, повторные попытки и собственная логика архивирования. Не объединять два хранилища автоматически.

## 3. Критические инварианты

1. Ни один переход не удаляет исходный base64 или Blob, пока новая копия не записана и не проверена.
2. Сначала записать Blob, затем обновить ссылку в основном состоянии. Оба шага должны иметь компенсирующий откат при ошибке.
3. Для операций, которые можно выполнить в одной IndexedDB-транзакции, запись Blob и обновление `main/state` должны быть атомарными.
4. Удаление медиа — только после проверки отсутствия ссылок из всех поддерживаемых сущностей, включая архивные записи.
5. Не считать медиа-ссылку действительной без существующей Blob-записи и совпадения размера/контрольной суммы.
6. Сохранение обычной записи журнала не должно переписывать Blob.
7. Не создавать Object URL до получения Blob; каждый созданный URL освобождать через `URL.revokeObjectURL` при закрытии/замене превью.
8. Отсутствие места, отказ IndexedDB, прерывание транзакции или повреждённая ссылка должны приводить к явной ошибке, а не к молчаливой потере фото.

## 4. Миграция существующих данных

Миграция должна быть возобновляемой и идемпотентной.

Этапы:
1. Добавить `media_blobs` в новую версию IndexedDB, не меняя старые поля.
2. Просканировать только известные поля: `records[].media`, `plantObservations[].media`, `pesticideIncidents[].media`, `deadoutReviews[].media`.
3. Для каждого data URL проверить допустимый MIME, формат, размер и декодирование. Не принимать произвольные URL и HTML.
4. Создать стабильный migration ID на основе сущности + индекса + содержимого (или сохранить его в migration journal), чтобы повторный запуск не создавал дубликаты.
5. Записать Blob, прочитать его обратно, проверить размер и SHA-256.
6. Только после проверки заменить data URL компактной ссылкой.
7. Обрабатывать ограниченное число файлов за проход, сохранять cursor/progress, давать продолжить после закрытия приложения.
8. После полного прохода выполнить проверку ссылок и отчёт: перенесено, пропущено, повреждено, осталось legacy.
9. Удалять legacy data URL только отдельным завершающим проходом после успешной проверки всех ссылок и наличия резервной копии.

Миграция не должна запускаться автоматически при открытии приложения без контроля прогресса и оценки свободного места. Сначала нужен dry-run с оценкой объёма.

## 5. Архив и восстановление

Формат архива v1 остаётся читаемым.

Для v2:
- добавить тип записи `image_media` (не переиспользовать `entrance_video`);
- сохранять оригинальные байты фото без повторного сжатия;
- в state хранить ссылки на ID медиа;
- проверять уникальность ID, MIME, размер, SHA-256 и отсутствие dangling references;
- импорт сначала помещать в staging, затем атомарно коммитить вместе с state;
- rollback должен сохранять прежние ссылки и прежние Blob;
- восстановление v1 должно продолжать работать: data URL остаются legacy-форматом, и могут быть конвертированы в новый store после импорта.

Не менять формат v1 на месте и не ослаблять его валидаторы.

## 6. Снимки и квоты

- Новые автоснимки должны содержать ссылки и метаданные, а не дублировать Blob.
- Старые снимки могут содержать legacy data URL; их нельзя массово переписывать без отдельной миграции и проверки.
- Лимиты PR #17 остаются независимыми: 8 MiB на снимок и 16 MiB суммарно для `auto_snapshots`.
- В интерфейсе показывать приблизительный объём медиа, число файлов и предупреждение при приближении к квоте.
- Не обещать фиксированную доступную квоту: браузер/Android управляет фактическим хранилищем. Использовать `navigator.storage.estimate()` только как оценку, а не гарантию.

## 7. Обязательные тесты до включения миграции

- Сохранение/чтение Blob для каждого типа сущности.
- Дублированный повторный запуск миграции.
- Прерывание после записи Blob, но до обновления state.
- Прерывание после обновления части ссылок.
- QuotaExceededError и abort транзакции.
- Повреждённый base64/data URL, неподдерживаемый MIME и превышение лимита.
- Ссылка на отсутствующий Blob.
- Одинаковые файлы в разных сущностях: политика dedup должна быть явной, безопаснее сначала не дедуплицировать.
- Удаление сущности при сохранении общего вложения, на которое есть другие ссылки.
- Архив v1 -> импорт -> экспорт v2 -> импорт v2 -> проверка байтов.
- Rollback после частичного импорта.
- Проверка старых резервных копий и снимков.
- Офлайн-сохранение и повторное открытие на Android.

## 8. Порядок реализации

1. Отдельный модуль репозитория Blob и unit tests без изменения текущего поведения.
2. Добавление хранилища и диагностического dry-run.
3. Миграция небольшими порциями с progress journal и resume.
4. Перевод записи/редактирования журнала на media IDs.
5. Перевод остальных типов вложений.
6. Архив v2 и совместимость v1.
7. Удаление legacy data URL только после доказанной успешности предыдущих этапов.

До завершения всех этапов исходные фото остаются в прежнем формате; функция не должна заявляться как реализованная.
