# B01 · Два ежедневных локальных ZIP-архива

Дата: 27.11.2026. Продуктовое уточнение владельца: одна кнопка «Восстановить», ежедневное автоматическое копирование, два поколения, обязательная проверка перед заменой. Потеря телефона, перенос, облако, USB и внешние носители не входят в этот пользовательский сценарий.

## F0–F2: LIMITED_SAFE_DRAFT
- База: main 50cfdfd66e2691e471b698fbc53af0d16d99aa98. Повторно используем js/disaster-archive.js: экспорт всех stores и Blob, SHA-256, структура, атомарное восстановление с защитой живых оригиналов. Не переносим каскад исторических archive-v2 и USB/SAF-диагностик.
- Отдельная локальная IndexedDB paseka-daily-archives-v1 хранит два ZIP Blob (имена файлов, дату, полный SHA-256), вне рабочей paseka-v1; архивы не включают сами себя. ZIP32 STORE с одним существующим JSON-архивом, CRC32 плюс SHA-256 файла и внутреннего payload. Без новых библиотек, сети, платных сервисов, изменения production-схемы. Не утверждаем, что это файлы в общей папке Android.
- Временный третий объект stage: запись, повторное чтение, полная проверка, затем атомарная ротация двух слотов в отдельной транзакции с проверкой поколения. При ошибке два предыдущих слота не меняются. Переживший прерывание stage не считается архивом и не используется как успешная копия.
- Первый запуск после корректного открытия базы, возвращение на экран и периодическая проверка в активном приложении. Пропущенный день — при следующем безопасном запуске. PWA/WebView не гарантирует фоновое выполнение при закрытом приложении; нативный scheduler не считается реализованным.
- Интерфейс: два статуса и одна кнопка, выбор поколения и подтверждение. Существующая внутренняя автокопия состояния остаётся для аварийного запуска; прежние ручные диагностики скрыты в основном UI, не удаляют данные.
- Восстановление только после повторного чтения и SHA/CRC/структуры, подтверждения и existing atomicRestore. Защита живых Blob/File остаётся fail-closed: уже существующая строка с оригиналом сохраняется без clear/delete/put только после сравнения всех её полей и бинарных байтов под единым IDB write lock. Отсутствующие или изменённые оригиналы блокируют весь restore. Нет обхода #442, никаких изменений оригиналов и очистки пользовательской базы в этом цикле. Результат физического восстановления NOT_TESTED; не выпускать в production без приёмки.
- Прямые внешние/USB/SAF и переносные инструменты не являются обязательным пользовательским путём данного продукта; исторические PR не уничтожать, пока не доказано отсутствие уникальных изменений/зависимостей. Не менять B04/B05/B06/B10 и их отдельные требования безопасности.

## F3–F7: проверка
Обычный цикл: 3 дня → ровно 2 поколения, один день → без повторного создания, текущая база и архивы независимы. Негативные: повреждённый ZIP/SHA/CRC, сбой записи/чтения/ротации, параллельный цикл, повреждение последнего → предыдущий остаётся доступен, восстановление с изменившейся ревизией/живыми Blob → отказ без изменения данных. Проверить offline assets и legacy regression; Node/CI exact SHA и Android/WebView на отдельном QA. Запуск при закрытом приложении, power-loss, большие Blob, физический restore и production пока NOT_TESTED.

## Реализация на ветке
- `js/daily-archives.js`, `js/disaster-archive.js`, `index.html`, `sw.js` v324 и Node-регрессии. Встроенный ZIP STORE (без сжатия), предельный размер 256 MiB; при превышении старые копии не заменяются. При прерывании restore аварийный временный ZIP очищается только после полного совпадения исходного или подтверждённого целевого payload. Legacy экспорт/проверки остаются скрытыми и совместимыми; прежняя внутренняя автокопия остаётся защитой startup.

## Нативное расписание Android
- Android JobScheduler: один persisted job каждые 6 часов с окном 1 час, логическая дедупликация по локальной дате внутри rotate. Нет зависимости от интернета, нет exact-alarm permission, нет облака. Системное энергосбережение и force-stop могут задерживать запуск; catch-up при открытии остаётся.
- В отдельном WebView на неизменном https://localhost запускается сгенерированный из текущего приложения HTML с теми же валидаторами, но без startup, миграций, restore и UI. Проверяются прежний marker, уже существующая IndexedDB (abort on upgrade), ревизия, формат и целостность. Сетевые запросы, file/content access и навигация запрещены. Только архивное IDB хранилище записывается. Native bridge передаёт лишь OK/SKIP/RETRY, не содержимое базы.
- Подготовлен изолированный APK ru.paseka.journal.qa.daily, не обновляющий прежние QA/production. Chromium E2E проверяет worker HTML с имитацией native bridge и реальной IndexedDB; это не подтверждает физический Android JobScheduler или WebView.
- Большой архив всё ещё ограничен 256 MiB в целях безопасности. Снятие лимита требует потокового формата и отдельной проверки больших видео; не отключать предохранитель.
