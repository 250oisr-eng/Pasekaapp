# P1 — защита единой атомарной записи и полного повторного чтения

Дата: 23.11.2026. Ветка `feat/p1-op06-atomic-frame-exchange-2026-11-23`, stacked Draft #456, база Draft #455. **Не в main, production-данные не изменялись.** Цель — предотвратить незаметную порчу несвязанных данных при физической операции.

## F0 — исходное состояние и доказанная проблема

- `js/sectional-season-runtime-v2.js` уже блокировал критические операции без `SECOND_DEVICE_VERIFIED` и `externalCopyConfirmed`, контролировал CAS и холодное чтение физического stage.
- Однако `preparePersistentSnapshot` проверял только несколько полей по `JSON.stringify`. Изменение `records`, `auditLog`, `sectionalSeasonalEntranceObservations`, `extractions` и других данных могло остаться незамеченным.
- `JSON.stringify(new Blob(...))` возвращает `{}` — видео разных байтов при одинаковом типе/размере невозможно отличить. Чтение stage snapshot не доказывало целостность **остальных** данных после CAS.
- Внешний физический второй аппарат/архив/оригиналы PASEKA02 остаются недоступным доказательством; запреты не ослабляются.

## F1 — контракт минимального изменения

1. Подготовщик снимка получает **копию** staged-кандидата. Можно изменить только `meta.revisionId` и добавить новые `snapshots` без переписывания/удаления прежних.
2. Все прочие ключи документа и значения должны совпадать, включая журнал, медиа, семьи, корпуса, маток, исходные события, старые версии и неизвестные будущие поля.
3. Сравнение вложенных объектов — структурное; бинарные `Blob`, `File`, `ArrayBuffer`, типизированные массивы — **по байтам**, Blob порциями максимум 1 МБ на сторону, без двух целых видео в RAM.
4. До вызова persistence физический executor не имеет права изменять любые ключи за пределами **явного разрешённого набора для своей OP**. OP-09 изменяет лишь историю наблюдений летков, OP-06-RESCUE — инвентарь и audit; для OP-08 разрешён отдельный журнал откачек. Все остальные ключи проходят строгую проверку.
5. После CAS холодное чтение должно **полностью** совпасть с подготовленным состоянием по всем ключам и бинарному содержимому. Если данные не совпали — `*_commit_uncertain`, никогда не сообщать успешное завершение и не делать ложный rollback уже произведённой записи.
6. Независимая внешняя полная копия и восстановление оригинальных Blob `SECOND_DEVICE_VERIFIED` **по-прежнему обязательны** до реального изменения физического состояния в основной базе. Никаких фиктивных отметок проверки.
