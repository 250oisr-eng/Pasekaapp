## F0–F2

После переноса фильтрации до сортировки (#510) `renderJournalRecords` продолжал многократно вызывать `S.families.find(...)` в формировании списка семей и полнотекстовом поиске. Это требует прохода по массиву семей для каждой записи. Исторические имена из `familyNameAtTime`/`familySnapshotAtTime` обязаны продолжать работать, а неоднозначные реальные связи нельзя исправлять рендерером.

F2 LIMITED_SAFE_DRAFT: фиксированный локальный UI, без IndexedDB, новых API, Service Worker, техники OP и мутации истории. Не меняет состав или порядок результатов и не заявляет доказанного ускорения на устройстве.

## F3–F5

- В начале одного вызова `renderJournalRecords` строятся индексы `familyById` по `S.families` и `firstRecordByFamily` по доступным записям; затем поиск по ID выполняется без повторных линейных проходов. Для дублирующегося legacy ID сохраняется **первое** значение, как в исходном `Array.find`, без исправления истории. Действительные записи и идентификаторы остаются без изменений.
- Четыре регрессионных теста: запрет вызовов линейного `families.find` и полнотекстовый поиск имени; поиск исторического имени после удаления текущей семьи из каталога (только синтетическая фикстура), сохранение первого совпадения для дублирующегося legacy ID; отсутствие повторных `available.find` и сохранение самого раннего доступного исторического имени при нескольких событиях семьи.
- Существующие проверки фильтров, порядка, архива, медиа и 100-event audit preview должны пройти без изменений.
