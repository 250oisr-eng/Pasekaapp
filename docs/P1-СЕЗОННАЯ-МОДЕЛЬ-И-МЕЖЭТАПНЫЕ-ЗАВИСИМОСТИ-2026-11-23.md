3. `inspect()` для OP-07 требует равенства `layout.honeyStack.bodyIds` с первоначальными `op07.evidence.honeyBodyIds`, а также текущей структуры рамок с `frameComposition` на момент установки. Поэтому OP-08 (изъятие запечатанных рамок/корпусов), OP-10 (снятие медовых корпусов) и последующее добавление второй пары (2→4) будут отвергаться или делать старую историю ложной, если не отделить **исторический снимок** от **текущего физического состояния**.
4. `js/family-lineage.js` уже содержит `applySplit`, `applyMerge`, `configureAlternativeWintering`, `recordPlacementChanged`, `recordEarlyHoneyHarvest`; `js/sectional-physical-layout.js` поддерживает режимы `SIDE_BY_SIDE`, `ALTERNATIVE_WINTERING_COLUMN`, `SINGLE_FAMILY`. Эти проверенные примитивы **переиспользовать**, не создавать вторую систему родословной.
5. Пользователь явно подтвердил: две плодные матки учитываются, **никакого OP-06 DONE и снятия металлических сеток**, пока не подтверждена отдельная двухматочная процедура.
6. Источник (DOCX) описывает OP-08/10 в абзацах ~34–42 и ~46–61, OP-11/12/13 в ~55–76, OP-14 в ~77–87. Даты и продолжительность ориентировочные там, где так указано; выполнять операции может только человек.

## Необходимый переход к полному сезонному циклу

**G8 — двухслойная модель**:
- `sectionalLayouts` + инвентарь — только фактическая текущая раскладка и положение оборудования.
- `sectionalTechProcesses` — записи технологических **циклов**, их immutable evidence по этапам, исходные идентификаторы семьи/матки и сохранённая история, а не требование совпадения всех исторических этапов с сегодняшним layout.
- Каждый физический переход: явное подтверждение пользователя → локальный preflight → clone & stage → физический diff и перемещение предметов/рамок → lineage events → полный integrity check → CAS + IndexedDB durable save → холодный reopen / restore.
- Поддержать несколько последовательных циклов одного hiveId с сохранением архивного цикла и ровно одним активным. Создание нового OP-04 без valid previous terminal event запрещено. Нельзя переписывать OP07 evidence задним числом ради согласования.
- `MODEL_VERSION=1` остаётся читаемым без потерь. Ввести обоснованную v2 с явным миграционным тестом, но **не активировать в production** до P0 (Draft #452) и доказанной миграции/restore на старом архиве. Не очищать старые записи и события.

**G9 — UI OP04–07**: пользователь выбирает фактические семьи, корпуса, донья, технические отверстия, решётки, сетки и подтверждает их положение; существующий координатор проверяет каждую операцию; no auto-DONE и никаких выдуманных openingId. OP07 поддерживает сразу 2/4 либо дополнительную пару после двух; надо обеспечить историю и возврат на склад.

**G10 — OP08–10**: состояние запечатанности по конкретным рамкам; незапечатанные не откачивать; факт выемки/возврата; два/четыре медовых корпуса; после завершения взятка действительная инвентарная транзакция возврата решёток, корпусов, подкрышников/крышек. Не использовать legacy Farrar extraction handler для нового профиля.

**G11 — OP11/12/13**: взаимоисключающие зимние сборки. OP11 объединяет с неопределённой до наблюдения идентичностью оставшейся матки; OP12 сохраняет три семьи 2+1+1 и две диафрагмы. OP13 допускается **только** после OP12, с фактической проверкой развития и новыми доньями; не считать «около полутора месяцев» автоматическим датчиком.

**G12 — OP14**: отдельные ветви: ранний взяток с двумя медовыми корпусами преимущественно с сушью → медоотбор → сокращение до 3, при необходимости 4 корпусов → объединение → отдельное подтверждение через ориентировочно 3–5 дней → повторное разделение; либо перед объединением две реальные отдельные семьи-отводка с их матками/рамками. Новая lineage/operation cycle не должна уничтожать прошлый сезон.

**G13 — доказательная эксплуатация**: сценарии (включая ошибки/отмены) всех OP01–14, полный инвентарь/рамки/матки/летки, ретроспективная совместимость Farrar, миграция v1→v2, сохранение/отказ/рестарт, полный архив на другом устройстве, Android OnePlus на isolated package. Только после успешных ворот профиль можно предложить к отдельному согласованному включению.
