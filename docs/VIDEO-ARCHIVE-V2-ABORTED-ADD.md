# PASEKA02 — отменяемая репетиция записи проверенных видеобайтов

Дата: 2026-11-20. Статус: **изолированная проверка, ни одна запись не коммитится**.

## Цель

Подтвердить, что неизменяемые SHA-256 проверенные Blob-срезы исходного PASEKA02 могут быть переданы непосредственно в реальные запросы IndexedDB `entrance_media.add()` внутри **той же финальной `readwrite`-транзакции**, в которой повторно проверяются текущий ledger, состояние, staging, историю и ID видео.

Это не восстановление архива, не разрешение на удаление и не staging migration. Этот этап не изменяет пользовательскую базу.

## Изолированный контракт

`js/video-archive-v2-pinned-source.js` дополнен `rehearsePinnedEntranceAddsAbort(db, file, options, deps)`:

1. Проверить реальный архив и все исходные/сохранённые staging Blob штатным SHA-аудитом. Создать и независимо хэшировать **новые неизменяемые Blob-объекты непосредственно из верифицированных архивных срезов**. Не использовать staged Blob как источник `add()`.
2. Открыть общую `readwrite`-транзакцию пяти protected stores, синхронно перечитать и сверить существующие state/ledger, хранилище летковых оригиналов, staging, archive_history и full_backup.
3. Допускать только source=`entrance_media`, только однозначные идентификаторы (без записи record_media в entrance store). Использовать строго `add()`, а не `put()`, чтобы невозможна была замена уже существующего видео по ключу.
4. Дождаться `onsuccess` всех `add()` **без выхода из текущей транзакции**, затем **обязательно `tx.abort()`**. Если хотя бы один запрос не удался, вся транзакция тоже отменяется. Не существует ветки кода, завершающей этот `readwrite` с commit.
5. Вернуть только диагностические числа: `abortedAddRequestCount`, `pinnedSourceBytes` и строго `archiveSafe=false`, `restoreAuthorized=false`, `cleanupAuthorized=false`, `stagedBytesLocked=false`. Blob-ссылки не выходят из вызова.

В результатах нет durable state/media writes. Доказывается лишь возможность в одном вызове направить **те же** проверенные байты в очередь атомарной транзакции. Настоящий commit/rollback с видео потребует защищённого snapshot, сохранения истории, согласования state и ledger, идемпотентного recovery и независимого согласования журналовых вложений.

## Регрессии

- Успешные `add()`-запросы под writer-lock, после mandatory abort ни одного нового видео в `entrance_media`.
- Подмена staged Blob другими байтами того же размера/MIME после SHA-аудита: в запрос `add` передаётся неизменяемый Blob из **архива**, а не новый staged Blob; транзакция отменяется и ничего не записывает.
- Журналовый источник `record_media` отклоняется до выполнения `add`.
- Конкурирующее появление уже занятого `videoId` выявляется под final writer-lock, оригинал остаётся неизменным.
- Ошибка `add()` вызывает abort всего набора; защищённые staging/history сохранены.

## Что остаётся небезопасным для live

Этот test-only путь не делает persisted staging неизменяемым. Более того, журнал распознавания и state ещё не восстанавливаются/объединяются, нет сохранённого rollback-снимка для будущего настоящего commit, отсутствуют обязательные проверки после рестарта и все операции удаления управляемых копий. Результат не разрешает ни production, ни merge, ни автоматическое удаление видео. Отдельно необходимы Android-тесты на физическом устройстве с камерой, Gallery, Downloads и офлайн-режимом.
