# Стабилизация перед новыми функциями — обязательный режим

**Решение пользователя: 22 ноября 2026.** До завершения всей выявленной оптимизации и исправлений **не начинать разработку новых функций**. Это правило выше ранее запланированных расширений: после отдельной законченной задачи не переходить к feature-backlog, пока не закрыт контрольный список стабилизации.

## Что разрешено

- Аудит и сверка фактического `main`, действующих веток, PR, базирования, CI на точных SHA.
- Исправления существующего функционала, целостности данных, безопасности, критических гонок, структуры и восстановимости архивов, IndexedDB, Service Worker и офлайн-режима.
- Рефакторинг **только при доказанном дефекте или необходимости для безопасной интеграции**. Оптимизация CI, устранение дублирующих workflows, регрессионные и миграционные тесты.
- Изменения документации, матрицы рисков и PR в отдельных ветках / Draft PR.
- Программные синтетические тесты вместо недоступной в ноябре полевой съёмки.

## Чего нельзя делать до снятия режима

- Разрабатывать новые пользовательские экраны и функции, новый профиль улья, новые технологические операции или новые возможности ИИ/видеодетектора.
- Принимать новые технические решения, требующие непроверенных технологических параметров, только ради количества функций.
- Считать все старые ветки равнозначными заданиями или автоматически переносить 401 ветку и 317 PR в `main`. Не объединять и не удалять PR/ветки ради уменьшения счётчика без анализа lineage.
- Выполнять реальные backup restore, cleanup, физическое удаление оригиналов, private media probing, производство/развёртывание, объединение PR без дополнительного конкретного разрешения.
- Считать `skipped`, `cancelled`, `pending` или CI другого SHA доказательством `PASS`.

## Контроль выхода из режима

Перед переходом к новой функциональности должны быть выполнены **все проверяемые сейчас условия**:

1. По каждой обнаруженной P0/P1 ошибке есть конкретное разрешение: исправлено с регрессионным тестом или документированная блокировка с обоснованной технической границей (нельзя выдавать BLOCKED за PASS).
2. Сверены `main`, активные и зависимые PR, текущие SHA, CI; составлен управляемый план их безопасной интеграции. Успех tests на Draft не означает, что исправление доступно пользователю в `main`.
3. Для code changes: полный regression suite + нужная Android сборка успешны на точном актуальном code SHA, ошибки и пропущенные workflow обозначены отдельно.
4. Перед любой будущей задачей с реальными медиа реализованы fail-closed проверки. Там, где невозможны сезонные/физические испытания, нельзя объявлять физическую готовность и тем более разблокировать удаление.
5. Заполнены `PROJECT_STATUS.md`, журнал изменений, технический долг, матрица PR; существенные изменения документированы.
6. После закрытия стабилизации **запросить у пользователя отдельное подтверждение**, можно ли возобновлять разработку новых функций. До ответа режим действует.

## Порядок больших циклов

Один большой цикл: инвентаризация актуальных SHA/PR → один критический класс дефектов и его зависимые модули → ограниченное исправление → позитивные и негативные регрессионные тесты → общий и Android CI на актуальном code SHA → документация, журнал и Draft PR. Не останавливаться на каждом микрошаге; не обещать завершение бесконечного списка «всех возможных багов» без ограниченного доказательного перечня.

**Актуальный начатый блок:** убрать ложные `skipped` из изолированного архивного workflow. Его уникальный APK нужен только при ручном запуске или push отдельной исторической ветки `test/full-archive-android-isolated-2026-11-18`, а не при каждом чужом PR. Основной PR regression/Android CI остаётся обязательным.
