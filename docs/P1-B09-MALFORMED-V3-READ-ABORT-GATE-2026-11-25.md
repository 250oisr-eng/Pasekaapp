# B09 — отрицательные проверки IndexedDB v3 и завершённости readonly-транзакций

**Дата:** 2026-11-25. **F0:** current `main=0e62ced6e34ea1fc92e7e090c2c514e8306c5f8d`; #473 и #476 MERGED, существующие B09 тесты проверяют legacy v1/v2→v3, Blob/ArrayBuffer, abort двух-store write, quota, newer-schema. Исходный `index.html` `openDB()` проверяет наличие `main`, `full_backup`, `entrance_media`, а `readMain/readAutoBackup` разрешают Promise **только на `tx.oncomplete`**. Наличие реализации — не доказательство отдельного негативного сценария.

## F1–F2: достижимый безопасный тест без ПК

Проверить **реальные production-функции**, не дублировать новую реализацию: (a) существующая повреждённая v3 с отсутствующим обязательным store должна блокироваться без удаления старой записи, истории и Blob; (b) `IDBRequest.onsuccess` с дальнейшим `tx.onabort` не должен возвращать считанные данные и не должен считать автокопию подтверждённой. Для этого достаточно `fake-indexeddb` и управляемых synthetic transaction event objects. **LIMITED_SAFE_DRAFT**: не зависит от телефона, сети или release, но не доказывает реальный crash/power loss.

## F3 — инварианты

- `openDB()` не создаёт потерянные stores в **уже существующей v3** посредством скрытого пересоздания/понижения версии, закрывает opened handle и отклоняет загрузку. Оригинальная запись остаётся байтово идентичной.
- Получение значения в `request.onsuccess` само по себе не подтверждает завершение транзакции. `tx.onabort` и `tx.onerror` отклоняют результат даже после успеха отдельного запроса. `autoBackupInfo` не обновляется до commit.
- Если `tx.oncomplete` действительно наступает, читаемая запись возвращается; негативный тест не должен ложно запрещать нормальный сценарий.
- IndexedDB схема, Worker, APK, профили ульев, реальные пользовательские файлы и архивы **не меняются**. Все данные теста искусственные.
