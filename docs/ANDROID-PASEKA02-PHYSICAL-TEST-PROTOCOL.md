## 2026-11-21 — фактический формат Android APK: PASEKA01, не PASEKA02 (обязательная поправка)

На физическом OnePlus NE2213, Android 16/API36 установлен isolated test APK с SHA исходного GitHub commit `3735bc056c259b2ca517bc3590d98ead968ea4d9`. Пользователь запустил read-only `-InspectHeaders` и получил **5 из 5 файлов** с заголовком `PASEKA01` (2026-11-18, 2026-11-19, 2081-09-01, 2087-03-08, 2094-07-13). Последняя строка `PASEKA02_HEADERS: 0 of 1` некорректно указала знаменатель вследствие использования PowerShell служебной переменной `$Matches`; фактический знаменатель **5**. Код изменён на независимый массив `$archiveFiles`.

Исходник `js/paseka-archive.js` в проверяемой ветке содержит `MAGIC_TEXT = 'PASEKA01'` и `VERSION = 1`, то есть текущий архив **намеренно** использует PASEKA01. Следовательно, ранее предложенные условия «именно PASEKA02» **НЕ выполняются установленной версией** и старый сценарий `tools/check_android_archive_after_stop.py` с принудительной остановкой для PASEKA02 применять **нельзя**. Заголовок PASEKA01 не доказывает целостность файлов и наличие двух видео.

Дальнейшая безопасная проверка для установленного APK: создать **новый и однозначно отмеченный синтетический** полный архив текущего формата PASEKA01 в изолированной базе; до любого force-stop установить его provenance и независимый SHA-256, затем проверять побайтовую неизменность и reopen IndexedDB. Не переименовывать PASEKA01 в PASEKA02 и не «исправлять» заголовок: потребуется отдельная совместимая версия формата и тесты миграции. Не модифицировать пять обнаруженных файлов, происхождение которых неизвестно.

**Приведённые ниже этапы A/B/C по PASEKA02 — исторический план для будущего формата, на этой сборке НЕ применимы и не являются инструкцией для исполнения.** Полный физический интеграционный тест видео ещё не выполнен. Автоудаление видео по-прежнему отключено.

## Однокомандная проверка заголовков обнаруженных архивов (read-only)

После успешного Windows preflight допускается запуск того же `tools/android_paseka02_preflight.ps1` с параметром `-InspectHeaders`. Скрипт выполняет повторный preflight и **только** для файлов с заранее разрешёнными именами читает первые 8 байт и длину файла. Сохраняет границу 20 файлов, запрещает неожиданные имена и не распаковывает архивы.

Печатаемые признаки `PASEKA02` / `PASEKA01` — только сигнатура, а **не** доказательство целостности, принадлежности тестовой базе, полноты двух видео или права удалять оригиналы. Не выбирать файл автоматически для остановки процесса, пока не подтверждены его синтетическое происхождение и исходный независимый SHA-256. На неизвестных файлах не выполнять восстановление.

Пример из **проверенного зафиксированного SHA** (не использовать ссылку на плавающую ветку):

```powershell
$p = Join-Path $env:TEMP 'paseka02-preflight.ps1'; Invoke-WebRequest -UseBasicParsing 'https://raw.githubusercontent.com/250oisr-eng/Pasekaapp/<VERIFIED_COMMIT_SHA>/tools/android_paseka02_preflight.ps1' -OutFile $p; powershell.exe -NoProfile -ExecutionPolicy Bypass -File $p -InspectHeaders
```

## Быстрый Windows preflight (одно действие вместо серии ADB-команд)

При уже установленной изолированной APK можно выполнить **один** скрипт `tools/android_paseka02_preflight.ps1`, закреплённый на конкретном commit SHA. Он проверяет число USB-устройств, Android API, точный package ID, состояние процесса и **только имена** потенциальных архивов. Скрипт не читает содержимое файлов, не вызывает force-stop, не устанавливает/удаляет приложения, не меняет IndexedDB и не делает выводов о PASEKA02 по одним лишь именам.

Для вызова на Windows ПК, где `adb` уже доступен, скопировать одной строкой, заменив `<COMMIT_SHA>` на SHA коммита с проверенным `tools/android_paseka02_preflight.ps1`:

```powershell
$p = Join-Path $env:TEMP 'paseka02-preflight.ps1'; try { Invoke-WebRequest -UseBasicParsing -ErrorAction Stop 'https://raw.githubusercontent.com/250oisr-eng/Pasekaapp/<COMMIT_SHA>/tools/android_paseka02_preflight.ps1' -OutFile $p; powershell.exe -NoProfile -ExecutionPolicy Bypass -File $p } catch { Write-Error $_ }
```

Перед запуском допускается отдельно просмотреть [исходник](https://github.com/250oisr-eng/Pasekaapp/blob/test/android-archive-external-stop/tools/android_paseka02_preflight.ps1). Запуск PowerShell с `ExecutionPolicy Bypass` относится **только к указанному дочернему процессу**, без изменения системной политики. Скрипт выполняет только read-only preflight, не физический тест A/B/C. Результат `PREFLIGHT_COMPLETE` нельзя записывать как проверку SHA архива или видеоданных. Если нет архива, это ожидаемый следующий шаг: сначала создать проверенные синтетические данные и отдельный эталон SHA, а не экспериментировать с пользовательскими файлами.

# Android: физическая проверка PASEKA02 после остановки процесса

Статус: **подготовлено, физический тест НЕ выполнен** (2026-11-21). Draft PR #324, продолжение #323; без merge, публикации или изменений production.

## Назначение и пределы

Проверяется **один** отдельный синтетический архив PASEKA02 во внешней папке `/sdcard/Download/Пасека/` после `am force-stop` строго тестового пакета `ru.paseka.journal.archive.test`. Скрипт `tools/check_android_archive_after_stop.py` только читает этот архив и проверяет SHA-256 до и после остановки; не удаляет, не восстанавливает, не переименовывает и не записывает файлов. **Это не тест IndexedDB**, не подтверждение того, что Android Camera/MediaStore не создал дополнительных копий, и не разрешение удалять видео.

Физический тест выполнить только после подтверждения отдельных предусловий. Нельзя использовать рабочую базу пасеки, пользовательские видео, реальные резервные архивы или production-пакет приложения. **Не выполнять `pm clear`, `adb uninstall`, `rm`, `wipe data`, factory reset и удаление исходных файлов**.

## Подготовительные условия (всё обязательно)

1. Один физический тестовый Android с включённой USB-отладкой и доступной локальной утилитой `adb` на компьютере. Проверить `adb devices -l`: ровно одно разрешённое USB-устройство; не подключать эмулятор вместо телефона.
2. Установлен **изолированный тестовый APK** с `applicationId=ru.paseka.journal.archive.test`. APK обычной сборки `ru.paseka.journal` не подменять им. Убедиться, что изолированный APK реально собран и проверен на **том же SHA**, что тестируемый код. В workflow #324 изолированный APK пока `skipped`: это блокер.
3. В тестовом приложении создана исключительно синтетическая демонстрационная база (искусственные ID, медиа без личных или рабочих данных). Исходный контейнер PASEKA02 с двумя синтетическими видео уже создан **отдельным проверенным способом**, его исходные байты и точный SHA-256 доступны до передачи на Android. Не принимать за исходный эталон SHA экспортированного файла с самого телефона.
4. Функция PASEKA02 действительно доступна в изолированном тестовом приложении; архив экспортирован с этого тестового телефона в `Download/Пасека` и имеет ожидаемое имя `paseka-full-backup-YYYY-MM-DD.paseka` или `paseka-full-backup-YYYY-MM-DD (N).paseka`. Если формат или файл недоступны, **остановить испытание**: текущий обычный экспорт PASEKA01 не эквивалентен PASEKA02.
5. Синтетические записи/видео до теста учтены отдельно: ID, ожидаемые хеши оригиналов и учётное состояние (без реальных данных). Не использовать незавершённые или зависшие операции как подтверждённые.
6. Проверить отсутствие в тестовом пакете доступа к рабочей IndexedDB и пользовательскому пространству данных; для физического тестирования использовать изолированный профиль или тестовый аппарат.

## Испытание A: внешний архив и force-stop (имеющийся автоматизированный сценарий)

Сначала открыть **изолированное** тестовое приложение, чтобы процесс работал. Затем на компьютере в корне проверенной рабочей копии репозитория выполнить:

```text
adb devices -l
adb -d shell pm path ru.paseka.journal.archive.test
adb -d shell pidof ru.paseka.journal.archive.test
python tools/check_android_archive_after_stop.py "paseka-full-backup-2026-11-21.paseka" <SOURCE_SHA256_FROM_BEFORE_EXPORT>
```

Заменить имя на фактическое; SHA брать **из исходного синтетического контейнера до экспорта**. Не запускать при несоответствии имени, пути, пакета, эталона или набора устройств.

Ожидаемый результат: код выхода 0, JSON `archiveFormat=PASEKA02`, SHA совпадает до и после `force-stop`, процесс отсутствует после остановки, `indexedDbRestoreTested=false`. При любом другом ответе — **FAIL/INCONCLUSIVE**, без утверждений о сохранности. Сохранить текстовую команду, дату, серийный номер (в приватном журнале, не публиковать), Android version, SHA текущего PR, тестового APK и исходного файла; не загружать личные файлы/логи.

## Испытание B: перезапуск и локальная IndexedDB (не автоматизировано)

1. После A вручную вновь запустить изолированное тестовое приложение. Не очищать кэш, хранилище и данные пакета.
2. Проверить, что в изолированной базе сохранились обе синтетические исходные видеозаписи с ожидаемыми идентификаторами/байтами/SHA, связанные записи учёта и durable ledger; статус завершённого распознавания и запрет очистки соответствуют подготовленному состоянию.
3. Если выполняется импорт тестового PASEKA02, использовать только изолированную тестовую БД и отдельно подтверждённый staging/commit workflow. Проверить отсутствие частичных записей при аварийном прекращении процесса на заранее выбранных точках; повторный запуск не должен создавать дубликаты. **Нельзя** переносить этот опыт на рабочие данные.
4. После перезапуска прочитать и повторно сверить внешний архив; убедиться, что ни само приложение, ни тест не изменили его. Не подменять проверку двух оригиналов одним агрегированным счётчиком.
5. Записать фактические результаты по каждому пункту; отсутствие средства безопасного просмотра или вычисления SHA Blob в тестовой базе означает `NOT TESTED`, а не `PASS`.

## Испытание C: границы внешних копий (ручной read-only аудит)

Открыть Camera/Gallery/Downloads/MediaStore и отметить, появились ли внешние оригиналы при: записи через камеру, выборе существующего файла и экспорте. Проверять **только тестовые медиа**. Ни одного файла не удалять. Нельзя заключать из отсутствия файла в одном приложении, что оригинал отсутствует во всех доступных Android-провайдерах/облачной синхронизации.

## Критерии остановки

Любая ошибка данных, несоответствие SHA, неизвестный путь, неподтверждённый test APK, более одного ADB-устройства, отсутствие первичного SHA или невозможность отличить синтетические данные от реальных → **остановка проверки, без исправления/удаления пользовательских записей**. Инцидент фиксировать отдельно с SHA и воспроизводимыми шагами. До успешных A/B/C, ревью прав внешних копий и отдельного согласования автоматическую очистку видео не активировать.
