## Обязательный формат диагностики и крупные автономные циклы (решение пользователя 2026-11-22)

1. **Все новые диагностические Android APK и аналогичные интерактивные проверки, когда технически возможно, должны иметь кнопки «Провести тест» и «Копировать результат».** Никакого ручного выделения JSON, консоли, многократного переписывания или меню «Поделиться» как основного способа. После запуска целиком сформировать один машиночитаемый отчёт и копировать его в буфер одним нажатием. Для тестов с перезапуском/остановкой процесса разрешён автоматический переход к следующей фазе после открытия приложения, но итоговый отчёт всё равно копируется одной кнопкой.
2. Копирование работает и для `PASS`, и для `BLOCKED`, только после завершения проверки, с видимым сообщением об успехе/ошибке. Не подменять успешным отчётом частичные или неисполненные проверки; явно отмечать `NOT_TESTED` и `NOT_ATTEMPTED`. Нельзя утверждать, что текст отправлен в чат, пока пользователь его действительно не отправил.
3. По умолчанию **не передавать диагностику в сеть**, не открывать доступ к медиа или реальным пользовательским данным ради удобства тестирования. Буфер обмена заполнять только по нажатию; отчёт проходит валидацию и не включает секреты/содержимое видео.
4. При диагностических APK учитывать подпись Android: разные debug-ключи GitHub Actions не дают безопасно обновить установленный пакет с тем же applicationId. Для новой несовместимой диагностической сборки использовать **новый изолированный идентификатор**, не заставлять пользователя удалять старое приложение/очищать данные. По возможности устанавливать и поддерживать устойчивую подпись в отдельном безопасном процессе, не раскрывая ключи.
5. Разрабатывать **крупными автономными логическими циклами**: документация → анализ → минимальное безопасное изменение → регрессионные тесты → CI на точном SHA → APK → фиксация документации и Draft PR. Не останавливать выполнение после отдельного коммита, мелкой правки или проверки; продолжать до готового этапа либо реального технического ограничения. Человека подключать только для неизбежного физического действия/решения. Не обходить ограничения безопасности ради уменьшения касаний.

## Обязательное правило: максимально автономные испытания на физическом телефоне и ПК (подтверждено пользователем 2026-11-21)

**Любые испытания, диагностика, проверки и воспроизведение ошибок на физическом Android, Windows-ПК и иных устройствах пользователя проводить с минимальным участием пользователя.** Это постоянное требование ко всем последующим разработкам и проверкам проекта.

1. **По умолчанию — один проверенный сценарий на весь безопасный этап**, а не серия ручных команд, кнопок и запросов «продолжай». Объединять взаимосвязанные предварительные проверки, выполнение и сбор диагностических результатов в воспроизводимый скрипт/тестовый интерфейс. Где возможно, запуск с компьютера по ADB автоматически выполняет разрешённые операции на подключённом тестовом телефоне.
2. **Максимум действий — на стороне разработчика/CI.** Самостоятельно готовить скрипты, синтетические фикстуры, точные команды установки/запуска, проверки версий, SHA, тестовый отчёт, регрессионные тесты и документацию. Не поручать пользователю поиск путей, ручное сопоставление файлов, многократные проверки или копирование результатов по одному, если это можно автоматизировать. Пользователь подключает/разблокирует устройство, даёт необходимые разрешения и запускает одну заранее подготовленную команду, когда удалённый доступ невозможен.
3. **Не жертвовать безопасностью ради удобства:** сценарий предварительно проверяет конкретное устройство и пакет, источник и версию APK/скрипта, ограничивает область доступа синтетическими данными, работает fail-closed, не стирает, не перезаписывает и не восстанавливает существующие данные по умолчанию. Не выполнять необратимые операции или автоматическую очистку видео. Для действий с риском пользователю показывается отдельная понятная точка подтверждения.
4. **Минимизировать сообщения и ввод:** один запуск → один итоговый отчёт со статусами `PASS/FAIL/BLOCKED/NOT TESTED`, версией сборки, контрольными суммами при наличии надёжного эталона и причиной остановки. Не требовать от пользователя исполнения каждой внутренней стадии; после получения отчёта самостоятельно диагностировать ошибку, исправлять код/CI и готовить следующий безопасный блок.
5. **Автоматизация не равна успешному испытанию:** результаты симуляции, CI, запуска приложения, чтения заголовка или успешного сохранения файла не выдавать за доказательство целостности IndexedDB, двух видеозаписей, полного восстановления и отсутствия внешних копий. Неизвестное помечать `NOT TESTED`. Не создавать/подменять исходный SHA после экспорта; проверять реальное происхождение синтетических данных.
6. Не использовать динамические непроверенные скрипты и сторонние ссылки. Фиксировать источник на конкретном commit SHA, проверять PowerShell/Python syntax и регрессию в CI, а на физическом устройстве — подтверждать фактический результат пользователя. Нельзя требовать от пользователя платных инструментов; действия через локальные бесплатные ADB/PowerShell предпочтительны.

Применять правило также к проверкам Android APK, Service Worker, офлайн-сохранения, видео, резервирования/восстановления и аппаратно-зависимым тестам. Если физический доступ отсутствует, делать всё доступное без него и запросить **одно минимальное необходимое действие**, а не последовательность отдельных ручных шагов.

# Правила разработки и контроля изменений

Версия: 1.0  
Дата: 2026-11-16

## 1. Источник истины

- Код и история изменений — GitHub.
- Утверждённые требования, решения, ограничения и передача работы — документы в папке docs.
- Рабочая переписка ChatGPT — временный интерфейс обсуждения, не хранилище требований.
- Загруженный исходный DOCX остаётся первичным источником технологии. Полный файл не копируется в публичный репозиторий без отдельного разрешения пользователя.

## 2. Обязательная бесплатность и внешняя AI-помощь

- Приложение должно быть бесплатным. Не использовать платные тарифы, API, модели, хостинги, расширения или платные опции.
- Допускаются бесплатные сервисы и ежедневные бесплатные лимиты AI-помощников. Пробные кредиты, платёжная привязка и автоматический платный fallback не считаются гарантией бесплатности.
- Перед внедрением сервиса проверять его тарифы, лимиты, требования к оплате и поведение после исчерпания квоты. При сомнениях остановиться и запросить решение пользователя.
- Для независимого анализа можно подготовить запросы в Qwen и DeepSeek. Пользователь вручную переносит запрос и возвращает ответ; внешнее мнение перепроверяется и не считается автоматическим разрешением на изменение.
- Не передавать внешним AI ключи, пароли, токены, персональные данные или закрытые данные пасеки.
- Подробные правила: docs/ПОЛИТИКА-БЕСПЛАТНЫХ-СРЕДСТВ.md.

## 3. Защита от потери и замещения функций

Запрещено:
- заменять существующую функцию новой только потому, что новая проще;
- удалять поля, записи, сценарии, UI или совместимость без отдельного решения;
- переписывать целый файл ради локальной функции, если возможно минимальное изменение;
- менять схему IndexedDB, формат backup, service worker cache или API без анализа обратной совместимости;
- объединять независимые задачи в один PR без необходимости;
- считать отсутствие упоминания функции в новом ТЗ разрешением её удалить.

Перед изменением составляется список:
1. Файлы и функции, которые изменяются.
2. Функции, которые не должны измениться.
3. Данные и форматы, которые затрагиваются.
4. Сценарии успешного выполнения и отказа.
5. План тестирования и отката.

## 4. Согласование

- Пользователь утверждает функциональные требования, спорные трактовки источника, архитектурные изменения, удаление/замену функций и решения, меняющие смысл приложения.
- В рамках утверждённого объёма агент самостоятельно выполняет технические изменения, создаёт/обновляет Draft PR и проводит проверки. Слияние PR, публикация приложения/PWA и production deployment требуют отдельного явного подтверждения пользователя.
- Если требование неясно или источник допускает несколько вариантов, создать запись «Открытый вопрос» и не кодировать предположение как обязательное правило.
- Пользователь разрешает самостоятельно изменять код, тесты и документацию, создавать рабочие ветки и Draft PR. Это разрешение не включает merge, публикацию приложения/PWA или production deployment: для каждого действия требуется отдельное явное подтверждение пользователя. Изменения production-данных/схемы также требуют отдельного подтверждения, проверенной резервной копии и плана восстановления; необратимое удаление пользовательских данных запрещено.

## 5. Ветвление и PR

- Работать в отдельной ветке на основе актуальной main или явно указанной базовой ветки.
- Один PR — одна логическая задача.
- PR должен содержать: назначение, scope, список изменений, совместимость, тесты, известные ограничения и точный commit SHA проверок.
- Не сливать цепочку stacked PR частями, если зависимый PR требует предыдущий; сначала проверить всю цепочку.
- Не закрывать, не переписывать и не удалять старые PR автоматически. Сначала составить карту зависимостей и согласовать решение.
- Документационные изменения могут идти отдельным PR и не требуют изменения приложения.

## 6. Обязательная проверка перед PR

Применимо к коду:
- npm test — полный регрессионный набор;
- проверка синтаксиса затронутых JS;
- тесты конкретной функции и негативные сценарии;
- проверка сохранения/восстановления, если затронуты данные;
- проверка offline cache/service worker, если добавлены ресурсы;
- Android Debug APK, если меняются приложение, Android-конфигурация или workflow, связанный со сборкой;
- проверка точного SHA, на котором прошли тесты и сборка.

Не заявлять физическое тестирование Android, если оно не проводилось. Не использовать фиктивные записи реальной пасеки.

## 7. Работа с неопределённостью технологии

- Сроки из источника, выраженные как «примерно», не превращать в жёсткие запреты без отдельного решения.
- Альтернативные последовательности сохранять как сценарии.
- Неизвестные размеры, диаметры, концентрации и количества не подставлять.
- Утверждения автора о гарантированной зимовке, отсутствии роения, продуктивности и проценте потерь хранить как заявления автора, а не как обещания приложения.
- Любое исправление ошибок распознавания речи документировать, если оно влияет на смысл.

## 8. Журнал изменений

Каждый PR обязан обновлять docs/ЖУРНАЛ-ИЗМЕНЕНИЙ.md и docs/СОСТОЯНИЕ-ПРОЕКТА.md:
- дата;
- PR/commit;
- причина;
- затронутые компоненты;
- что изменено;
- какие функции защищены от изменения;
- проверки и их результат;
- открытые вопросы;
- статус: предложено / проверено / одобрено / объединено / выпущено.

## 9. Правило остановки

Если для продолжения нужно:
- выбирать между разными трактовками исходника;
- вводить отсутствующий в источнике параметр;
- менять архитектуру или данные вне утверждённого scope;
- выполнять merge при конфликте, неполных проверках или неясной зависимости;
- запускать необратимую миграцию без проверенной резервной копии/отката или выполнять релиз при неполных проверках,

работу остановить на этом месте, записать вопрос и запросить решение пользователя.

## 10. Постоянное разрешение пользователя

Слияние PR, публикация приложения/PWA и production deployment не входят в постоянное разрешение на разработку и всегда требуют отдельного явного подтверждения пользователя. Успешные тесты и CI сами по себе такого разрешения не заменяют.


## 11. Единый порядок разработки и управление приоритетами

### 11.1. Один главный приоритет

- В каждый момент времени вести один главный технический приоритет. Новую крупную функцию не начинать, пока текущая логическая задача не интегрирована, проверена и отражена в документации.
- Сначала завершать блокирующие риски сохранности данных и архитектурного фундамента, затем доменную модель/валидацию, технологические сценарии, UI и улучшения. Точная очередь определяется свежим аудитом, а не фиксируется навсегда.
- Перед началом каждого этапа перепроверять актуальное состояние main, все открытые PR, ветки, зависимые цепочки, CI и незавершённые задачи. Не полагаться на устаревший снимок или прошлую переписку.

### 11.2. Модель до интерфейса

- Сначала согласовать сущности, связи, инварианты, жизненный цикл и формат хранения данных; затем реализовывать доменную логику и валидаторы; после этого — интерфейс.
- Для изменений данных заранее определить совместимость со старыми записями, IndexedDB, резервными копиями, восстановлением, offline cache и Android/PWA в зависимости от области влияния.
- Не создавать UI, который допускает состояния, не поддерживаемые согласованной моделью или локальными проверками.

### 11.3. Малые законченные блоки и PR

- Делить работу на небольшие самостоятельные блоки с проверяемыми критериями готовности.
- Один PR — одна логическая задача. В PR указывать цель, scope, затронутые и защищённые функции, влияние на данные, тесты, ограничения и точный SHA.
- Перед созданием PR искать существующие ветки и PR с той же целью. Не дублировать реализацию.
- Не вести параллельно конкурирующие изменения одного файла, API, схемы данных или доменной модели. Связанные изменения выстраивать в одну прозрачную цепочку зависимостей либо интегрировать последовательно.
- Не создавать альтернативные реализации без обоснованной причины. Если они уже существуют, сначала сравнить diff и зависимости; не объединять их механически.

### 11.4. Инвентаризация и очистка очереди PR

- При большом числе открытых PR провести полную инвентаризацию: назначение, автор/ветка, base/head SHA, draft/ready, изменения, зависимости, конфликты, актуальность тестов и CI.
- Сгруппировать PR по риску и области: сохранность данных/безопасность, архитектурный фундамент, доменная модель, технологические операции, интерфейс, документация, независимые исправления.
- Сформировать одну приоритетную очередь интеграции. Не сливать устаревшие, дублирующие или конфликтующие PR ради сокращения количества; не закрывать и не удалять их без анализа последствий.
- Проверять stacked PR как целую цепочку и интегрировать в корректном порядке. Не считать CI дочернего PR достаточным доказательством безопасности всей цепочки.

### 11.5. Критерии завершения блока

Блок считается завершённым только если проверены: ожидаемое поведение, негативные сценарии, регрессии связанных функций, совместимость данных и backup/restore (если затронуты), офлайн/PWA/Android (если затронуты), документация и CI на точном актуальном SHA.

Статусы различать: «не начато», «в разработке», «реализовано» (код существует, но интеграция/проверки не завершены), «проверено» (критерии завершения подтверждены). Успешный CI не является полной гарантией безопасности.

### 11.6. Автоматизация и общий аудит

- Повторяемые проверки постепенно автоматизировать доступными бесплатными средствами: тесты, синтаксис, сборка, Android workflow, проверка миграций и backup/restore.
- После нескольких связанных блоков проводить интеграционный аудит всех затронутых модулей и прежних сценариев; перед релизом проводить общий контроль критических путей.
- Приоритет сохранности данных и корректности технологии выше скорости, числа PR и количества функций.

### 11.7. Обязательное завершение рабочего сеанса

После каждого логического блока обновлять `docs/СОСТОЯНИЕ-ПРОЕКТА.md` и `docs/ЖУРНАЛ-ИЗМЕНЕНИЙ.md`; `docs/ПЛАН-РАЗРАБОТКИ.md` обновлять при изменении очереди, статуса или критериев. Указывать точные SHA, ссылки на PR/CI, что подтверждено, что не проверено, риски, открытые вопросы и один следующий шаг. Новый чат начинает работу с этих документов и свежей проверки GitHub.


## 12. Постоянный журнал состояния в корне репозитория

- Корневой файл `PROJECT_STATUS.md` обязателен и является главным оперативным журналом состояния и восстановления проекта после обрыва связи.
- В начале каждого рабочего сеанса сначала прочитать `PROJECT_STATUS.md`, затем проверить фактическое состояние GitHub (main SHA, PR, ветки, CI) и Lovable. Сам файл не заменяет проверку сервисов.
- Файл должен содержать: название и текущее состояние проекта; последний завершённый этап; выполненные изменения и список изменённых файлов; результаты функциональных/CI-проверок с точным SHA; подтверждённый статус сохранения/merge в GitHub; известные ошибки и нерешённые проблемы; текущую незавершённую задачу; следующий конкретный шаг.
- После каждого логически завершённого этапа обновлять `PROJECT_STATUS.md` в том же PR/изменении, что и соответствующий этап. Не откладывать фиксацию прогресса до отдельного будущего сеанса.
- Историю важных изменений не удалять: добавлять новые контрольные точки, сохраняя предыдущие записи. Не записывать предположения как факты и не отмечать проверку, merge, публикацию или сохранение без подтверждения соответствующего сервиса.
- При восстановлении после обрыва: прочитать `PROJECT_STATUS.md`; проверить актуальные GitHub main/PR/CI; проверить состояние проекта в Lovable; сопоставить реальные изменения с журналом; выявить незавершённые операции; продолжить с последнего подтверждённого этапа без повторения выполненной работы.
- При расхождении журнала с реальным GitHub/Lovable сначала установить фактическое состояние и затем обновить журнал отдельной записью. Реальный статус сервисов имеет приоритет над текстом журнала.
- GitHub и `PROJECT_STATUS.md` — основа непрерывности разработки. История переписки ChatGPT не является единственным местом хранения прогресса.
