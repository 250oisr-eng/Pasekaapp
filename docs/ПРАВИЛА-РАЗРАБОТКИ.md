# Правила разработки и контроля изменений

Версия: 1.1  
Актуализация: 2026-11-25

## 1. Источник истины

- Код и история изменений — GitHub.
- Утверждённые требования, решения, ограничения и передача работы — документы в папке docs.
- Рабочая переписка ChatGPT — временный интерфейс обсуждения, не хранилище требований.
- Загруженный исходный DOCX остаётся первичным источником технологии. Полный файл не копируется в публичный репозиторий без отдельного разрешения пользователя.

## 2. Обязательная бесплатность и внешняя AI-помощь

- Приложение должно быть бесплатным. Не использовать платные тарифы, API, модели, хостинги, расширения или платные опции.
- Допускаются бесплатные сервисы и ежедневные бесплатные лимиты AI-помощников. Пробные кредиты, платёжная привязка и автоматический платный fallback не считаются гарантией бесплатности.
- Перед внедрением сервиса проверять его тарифы, лимиты, требования к оплате и поведение после исчерпания квоты. При сомнениях остановиться и запросить решение пользователя.
- Внешние Qwen/DeepSeek — необязательное дополнительное ревью, не источник разрешения. Использовать безопасные доступные инструменты самостоятельно, не требовать от пользователя рутинно переносить запросы между сервисами; без автоматического доступа пропускать необязательное ревью, не блокируя работу.
- Не передавать внешним AI ключи, пароли, токены, персональные данные или закрытые данные пасеки.
- Подробные правила: docs/ПОЛИТИКА-БЕСПЛАТНЫХ-СРЕДСТВ.md.

## 3. Защита от потери и замещения функций

Запрещено:
- заменять существующую функцию новой только потому, что новая проще;
- удалять поля, записи, сценарии, UI или совместимость без отдельного решения;
- переписывать целый файл ради локальной функции, если возможно минимальное изменение;
- менять схему IndexedDB, формат backup, service worker cache или API без анализа обратной совместимости;
- объединять независимые задачи в один PR без необходимости;
- считать отсутствие упоминания функции в новом ТЗ разрешением её удалить.

Перед изменением составляется список:
1. Файлы и функции, которые изменяются.
2. Функции, которые не должны измениться.
3. Данные и форматы, которые затрагиваются.
4. Сценарии успешного выполнения и отказа.
5. План тестирования и отката.

## 4. Согласование

- Пользователь утверждает спорные трактовки исходной технологии, новые нормы, решения, меняющие смысл приложения, и удаление пользовательских функций/данных. Агент вправе самостоятельно выполнить **необходимые, обоснованные и обратимые** изменения архитектуры и локальной схемы в рабочей ветке с миграциями/тестами/восстановлением; это **не** разрешение менять production-схему, сливать PR или публиковать приложение.
- В рамках утверждённого объёма агент самостоятельно выполняет технические изменения, создаёт/обновляет Draft PR и проводит проверки. Слияние PR, публикация приложения/PWA и production deployment требуют отдельного явного подтверждения пользователя.
- Если требование неясно или источник допускает несколько вариантов, создать запись «Открытый вопрос» и не кодировать предположение как обязательное правило.
- Пользователь разрешает самостоятельно изменять код, тесты и документацию, создавать рабочие ветки и Draft PR. Это разрешение не включает merge, публикацию приложения/PWA или production deployment: для каждого действия требуется отдельное явное подтверждение пользователя. Изменения production-данных/схемы также требуют отдельного подтверждения, проверенной резервной копии и плана восстановления; необратимое удаление пользовательских данных запрещено.

## 5. Ветвление и PR

- Работать в отдельной ветке на основе актуальной main или явно указанной базовой ветки.
- Один PR — одна логическая задача.
- PR должен содержать: назначение, scope, список изменений, совместимость, тесты, известные ограничения и точный commit SHA проверок.
- Не сливать цепочку stacked PR частями, если зависимый PR требует предыдущий; сначала проверить всю цепочку.
- Не закрывать, не переписывать и не удалять старые PR автоматически. Сначала составить карту зависимостей и согласовать решение.
- Документационные изменения могут идти отдельным PR и не требуют изменения приложения.

## 6. Обязательная проверка перед PR

Применимо к коду:
- npm test — полный регрессионный набор;
- проверка синтаксиса затронутых JS;
- тесты конкретной функции и негативные сценарии;
- проверка сохранения/восстановления, если затронуты данные;
- проверка offline cache/service worker, если добавлены ресурсы;
- Android Debug APK, если меняются приложение, Android-конфигурация или workflow, связанный со сборкой;
- проверка точного SHA, на котором прошли тесты и сборка.

Не заявлять физическое тестирование Android, если оно не проводилось. Не использовать фиктивные записи реальной пасеки.

## 6.1. Постоянный контракт пользовательского тестирования

**Предыдущие тесты пользователь удаляет. Это исходное предположение каждого нового диагностического пакета**, а не исключение. Ранние ZIP, папки, .ps1, .cmd, TAR и JSON могут отсутствовать полностью; не строить новые тесты на их наличии, не требовать восстановления, перемещения или ручного поиска. История ошибок остаётся в Git/журнале, а **новый тест сам собирает только необходимые новые доказательства**.

- **Одна выдача — один полностью самостоятельный ZIP:** один очевидный `START.cmd`, вложенные зависимости/диагностические модули, понятный README и **один конечный обезличенный JSON**. Распаковка в любую новую локальную папку. Не публиковать «дополнение», «патч», набор отдельных скриптов или обязательную инструкцию по совмещению версий.
- В штатном режиме требовать от пользователя только запуск готового пакета и передачу **одного итогового JSON**. Не просить копировать исходники, выбирать файлы прежних тестов, запускать команды/консоль вручную, переподключать ПК/телефон без фактической необходимости, вводить многократные подтверждения. Автоматизировать обнаружение официального ADB/SDK и проверку preflight, если они нужны.
- **Новый тест должен работать после удаления всех прошлых тестов.** Он получает актуальное состояние заново в рамках допустимых read-only операций. Проверка старого тестового артефакта возможна только как отдельный *необязательный* режим при наличии независимой причины и явном выборе пользователя; отсутствие архива не блокирует самостоятельную диагностику, если доступен безопасный новый источник.
- Верифицировать на Windows PowerShell 5.1: запуск из новой чистой папки без старых тестов, ошибку отсутствующего ADB/USB, корректный public-only сценарий, невалидный TAR, fail-closed, нулевое приватное чтение, единственный результат. ZIP проверять на полноту, хеши, CRC и отсутствие пользовательских файлов; CI на точном SHA.
- **Границы неприкосновенны:** один клик не разрешает `run-as` чтение приватной базы, установки/удаления APK, `force-stop`, сброс приложения, восстановление, изменение production-данных, удаление видео или необратимые операции. Для них применяются отдельные ограничения/подтверждения. Публичный USB read-only тест не доказывает backup или independent restore.
- Не включать в чат/CI TAR, SQLite/IndexedDB, пользовательские пути, фото, видео, ключи, серийные номера, сырые логи. Финальный JSON указывает версию, этап, точный код отказа, что реально проверено и что остаётся `NOT_TESTED`.

## 6.2. Максимальная автономия работы и актуальность правил

- Выполнять все **разрешённые** взаимосвязанные шаги подряд до проверяемого результата: изучить контекст, определить минимальное безопасное изменение, исправить код, создать негативные/регрессионные тесты, запустить доступные проверки, разобрать и исправить ошибки, оформить самостоятельный пакет, журнал, краткий статус, метрики и Draft PR. **Не останавливаться после каждого шага и не просить «продолжай».**
- Участие пользователя сводить к объективно неизбежному: доступ к физическому устройству/внешнему аккаунту, недостающие факты о реальной пасеке, спорная технология, отдельно разрешаемые merge, production и необратимые операции. Вместо инструкций по ручной технической работе сначала проверить доступные безопасные инструменты и автоматизированные действия. Без доступа не выдавать фиктивный PASS.
- Если один путь блокирован, зафиксировать доказательство и переходить к следующей независимой задаче, не создавая бесполезной серии версий теста. Не возвращаться к прежним гипотезам без новой информации. Обновлять один итоговый статус, а не несколько противоречивых инструкций.
- В конце каждого содержательного цикла **ревизовать действующие правила**: удалить или заменить устаревшие *процедурные* требования, привязки к прежним версиям тестов, ненужные ручные действия, дубли и конфликтующие указания. Исторические решения/CI/SHA переносить в Git-историю/журнал, но не оставлять как действующие требования. **Не удалять** подтверждённую пользователем технологию, постоянные границы безопасности, запреты на потерю данных, права подтверждения и условия восстановления.
- Сохранять один нормативный цикл F0–F7 и иерархию документов из `AGENTS.md`/индекса; эти положения не добавляют другой конкурирующий порядок разработки.

## 7. Работа с неопределённостью технологии

- Сроки из источника, выраженные как «примерно», не превращать в жёсткие запреты без отдельного решения.
- Альтернативные последовательности сохранять как сценарии.
- Неизвестные размеры, диаметры, концентрации и количества не подставлять.
- Утверждения автора о гарантированной зимовке, отсутствии роения, продуктивности и проценте потерь хранить как заявления автора, а не как обещания приложения.
- Любое исправление ошибок распознавания речи документировать, если оно влияет на смысл.

## 8. Журнал изменений

Каждый завершённый **макроцикл** фиксируется в `PROJECT_STATUS.md` и `docs/ЖУРНАЛ-ИЗМЕНЕНИЙ.md`; подробное `docs/СОСТОЯНИЕ-ПРОЕКТА.md` — периодический обзор, а не обязательный дубликат каждой правки:
- дата;
- PR/commit;
- причина;
- затронутые компоненты;
- что изменено;
- какие функции защищены от изменения;
- проверки и их результат;
- открытые вопросы;
- статус: предложено / проверено / одобрено / объединено / выпущено.

## 9. Правило остановки

Если для продолжения нужно:
- выбирать между разными трактовками исходника;
- вводить отсутствующий в источнике параметр;
- менять архитектуру или данные вне утверждённого scope;
- выполнять merge при конфликте, неполных проверках или неясной зависимости;
- запускать необратимую миграцию без проверенной резервной копии/отката или выполнять релиз при неполных проверках,

работу остановить на этом месте, записать вопрос и запросить решение пользователя.

## 10. Постоянное разрешение пользователя

**Полномочия определены разделом 4 и [AGENTS.md](../AGENTS.md).** Независимое разрешение на каждый merge, release/production deploy и опасные действия с данными обязательно; никакие проверки не заменяют его.

## 11. Единый цикл и управление приоритетами

Единственный нормативный порядок разработки — **F0–F7, раздел 4** [стратегии](СТРАТЕГИЯ-РАЗРАБОТКИ-ПАСЕКА-2026-11-23.md). Для безопасности действуют ограничения из разделов 1–10 выше и [AGENTS.md](../AGENTS.md); повторный альтернативный жизненный цикл здесь не устанавливается. Один крупный автономный цикл объединяет несколько небольших доказуемых изменений одной логической задачи, затем CI на точном SHA, обновление Draft PR и состояния. Ожидание отдельного разрешения на merge не блокирует независимую разработку; зависимые изменения не активируются до интеграции.

## 12. Документы состояния и сохранение истории

- [PROJECT_STATUS.md](../PROJECT_STATUS.md) — **короткая текущая контрольная точка**: live main/PR/SHA, результаты тестов, зависимости, блокеры, следующий конкретный цикл. При начале нового контекста проверить его против реального GitHub и Lovable (если затронут).
- [PROJECT-CONTROL.md](PROJECT-CONTROL.md) — только индекс нормативных/справочных документов, без журнала датированных CI.
- [ЖУРНАЛ-ИЗМЕНЕНИЙ.md](ЖУРНАЛ-ИЗМЕНЕНИЙ.md) и Git-история — подробная хронология, старые SHA и решение о сохранении данных; [ПЕРЕДАЧА-МЕЖДУ-ЧАТАМИ.md](ПЕРЕДАЧА-МЕЖДУ-ЧАТАМИ.md) — краткий указатель, а не дублированный журнал.
- [ПЛАН-РАЗРАБОТКИ.md](ПЛАН-РАЗРАБОТКИ.md) обновлять только когда реально меняется очередь/критерии, [метрики циклов](WORK-CYCLE-METRICS.json) — один раз по завершении крупного цикла.
- Изменения фиксировать **в конце логического макроцикла**, не после каждого коммита. Не удалять историю пользовательских решений, обязательных технологических требований и подтверждённых доказательств; историю файлов можно читать по Git на точном SHA.
