## 1. Результат

Изоляция технологической записи и AI-контекста от профиля Farrar реализована в PR #80. Создание технологической карточки намеренно остаётся заблокированным, пока физическая модель оборудования не поддерживает отдельный профиль.

Простого добавления profileId недостаточно. В общей модели приложения остаются предположения о числовых позициях корпусов 1–6, зимнем наборе Farrar [1, 3, 4, 6], ровно трёх зимних корпусах и медовой паре H1/H2. Применять их к трёхсекционной технологии нельзя.

## 2. Подтверждённая конструкция и происхождение параметров

### Прямо из DOCX
- Комплект включает два корпуса по 10 рамок и шесть корпусов по 6 рамок.
- Используются три дна, три подкрышника, три крышки и потолочная кормушка.
- После разделения образуются три секции; в описанной рабочей конфигурации каждой секции дают второй 6-рамочный корпус.
- Для медосбора описаны два медовых корпуса; для продолжительного взятка допускается комплект из четырёх, добавляемый парами.
- Основная зимовка объединяет три секции в одно гнездо из трёх верхних корпусов.
- Альтернативная зимовка сохраняет три семьи: сильная семья на двух корпусах, две другие — по одному корпусу, с двумя сетчатыми диафрагмами.

### Отдельно подтверждено пользователем
- Высота рамки — 180 мм.
- Диаметр технических отверстий в боковых стенках корпусов — 50 мм.
- Сироп 2:1.
- Количество жидкой подкормки — порция 100–200 г по силе семьи; периодичность этой порции не приписывается DOCX.
- Медовые корпуса устанавливаются только парами; общее количество — 2 или 4.

### Не задано источником
- Высота гнездового и медового корпуса.
- Точное число и расположение технических отверстий на каждом типе корпуса.
- Универсальная нумерация физических корпусов и постоянные номера позиций новой системы.
- Размер буферного коридора между постоянными решётками.
- Любые дополнительные геометрические размеры, не перечисленные выше.

Не добавлять неизвестные значения в профиль, миграцию или интерфейс. Внутренние ID приложения допустимы только как программные идентификаторы, не как утверждение о физических номерах из источника.

## 3. Что обнаружено в коде на HEAD PR #80

Проверены index.html, js/equipment-inventory.js, js/equipment-bodies.js, js/equipment-reconciliation.js, js/equipment-labels.js и js/sectional-multiqueen-techprocess.js.

1. HIVE_PROFILE_CATALOG содержит готовый профиль farrar-6x6-v1 и шаблоны Dadant/Ruta/custom. Готового sectional-multiqueen-v1 в каталоге нет. getHiveProfile возвращает null для неизвестного profileId, если в записи улья нет отдельного объекта profile.
2. Форма создания нового улья по умолчанию записывает profileId=farrar-6x6-v1. Отдельного выбора нового профиля пока нет.
3. validateVirtualApiary помечает любой профиль с family !== 'farrar' как profile_operations_not_supported. Затем общая проверка всё ещё ожидает числовые позиции 1–6, ровно три зимних корпуса, разрешённые номера 1/3/4/6 и медовую пару из двух элементов.
4. layoutFor и часть вспомогательных функций уже читают boxKeys из профиля, но при отсутствии профиля используют значения по умолчанию Farrar: 1–6 и H1/H2. Одного профильного ID недостаточно.
5. saveBox оставляет редактирование профилей, отличных от Farrar, в режиме ограниченного/неполного сценария; это не готовый редактор физической конфигурации новой технологии.
6. buildAIContext передаёт шесть числовых гнездовых позиций и две медовые группы. Для новой технологии контекст должен строиться из реальной конфигурации секций и оборудования, а не из фиксированной Farrar-схемы.
7. Откачка и возврат медовых корпусов в index.html используют фиксированные H1/H2. Новая модель должна поддерживать утверждённое число корпусов 2 или 4, не меняя старое поведение Farrar.
8. js/equipment-inventory.js использует встроенный профиль Farrar по умолчанию и возвращает null для неизвестного profileId без объекта profile. Спецификация физического корпуса сейчас не описывает все особенности новой секционной конструкции.
9. js/equipment-bodies.js получает профиль только из hive.profile и при отсутствии профиля использует H1/H2. Единый резолвер профиля нужен для всех модулей, но его изменение должно сопровождаться регрессионными тестами Farrar.

## 5. Безопасный следующий этап

До добавления профиля в пользовательскую форму:

1. Зафиксировать отдельный контракт физической модели секционного улья: три секции, фактические корпуса и дна, связи секций, матки, технические соединения, летки и временные заглушки. Не вводить неизвестные размеры и количество отверстий.
2. Отделить профильный layout от Farrar-структуры. Не использовать числовые ключи 1–6 и зимние ограничения Farrar как универсальные правила.
3. Сделать профильным инвентарь корпусов, проверку совместимости, замену корпусов и историю перемещений.
4. Представить основную и альтернативную зимовку как отдельные ветви с проверками фактической конфигурации.
5. Поддержать медовые корпуса парами: 2 или 4 в общей конфигурации; сохранить прежний сценарий Farrar.
6. Обобщить AI-контекст, резервное копирование, восстановление и проверку целостности так, чтобы данные нового профиля не преобразовывались в Farrar-схему.
7. Добавить регрессионные тесты, доказывающие неизменность поведения Farrar, и тесты новой секционной конфигурации на изолированных фикстурах.
8. Только после этого открыть создание профиля и технологической карточки.

## 7. Дополнительные блокеры после проверки PR #82

Проверены также профильные точки в js/equipment-inventory.js, js/equipment-bodies.js, layoutFor, family transfer, validateRawBackupIntegrity, buildAIContext и сценариях медосбора.

1. **Четыре медовых корпуса не поддерживаются инвентарём.** В js/equipment-inventory.js функции linkHoneyPair, createStockHoneyPairUnsafe и installStockHoneyPairUnsafe требуют ровно две позиции. Профиль с четырьмя корпусами не может безопасно использовать текущую модель одной пары. Нужна модель двух пар/парных групп без изменения Farrar.
2. **UI медового комплекта жёстко фиксирует H1/H2.** Отображение, переключение установки/снятия, извлечение, возврат пустых корпусов и AI-контекст обращаются к двум ключам. Для новой технологии необходимо получать позиции из профиля и поддержать 2 или 4 корпуса.
3. **layout и резервная проверка не полностью профильные.** validateRawBackupIntegrity проверяет фиксированные позиции 1–6 и медовую пару длиной 2; migrateState создаёт corpusIds для 1–6 и H1/H2. Перед вводом нового профиля требуется совместимая аддитивная схема и проверка старых backup.
4. **Семья привязана к одному корпусу.** Существующая модель размещения семьи и family.box ориентирована на одну позицию, тогда как одна секция новой системы включает два гнездовых корпуса. Требуется явная связь sectionId → familyId/queenId → два bodyId; не дублировать одну семью в двух корпусах.
5. **Инвентарь учитывает только корпуса.** equipmentInventory хранит bodies/events, а типы — brood/honey. Отдельные дна, крышки, подкрышники, кормушка, разделительные решётки, сетчатые заглушки и диафрагмы не представлены как физические единицы. Не добавлять их количество по догадке; для известного комплекта из DOCX использовать подтверждённые количества, неизвестные позиции задавать фактической конфигурацией.
6. **PR #82 — только первый узкий шаг.** Он передаёт profileForHive в PasekaBodies.swapLocations и позволяет разрешать ключи через каталог; он не меняет inventory, layout, wintering, extraction, backup или выбор профиля. На HEAD 2ee4f401 полный Node.js regression suite прошёл 431/431, Android Debug APK — success; Workers Builds — failure.
