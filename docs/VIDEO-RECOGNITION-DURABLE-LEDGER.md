# Изолированный реестр подтверждённых результатов распознавания видео — 20.11.2026

Статус: зависимый Draft PR после #242; **test-only API**, не подключён к UI/сетевому распознавателю и не разрешает удаление.

## Реализация
- `js/video-recognition-ledger.js` перенесён из отдельной экспериментальной ветки `feat/video-source-sha256-evidence-2026-11-20` как ограниченный модуль, без merge её несовместимой цепочки и без изменения живой базы.
- `recordRecognitionResult(db, input)` допускает лишь `completed` и `recognitionSucceeded=true`, ожидаемые `source,videoId,resultId,stateRevisionId,processedSourceSha256,processedSourceBytes`, ограниченный JSON без бинарных оригиналов.
- Для `entrance_media` модуль читает исходный Blob и хэширует его вне IndexedDB транзакции; для `record_media` сверяет Data URL и его байты. Затем отдельная IndexedDB write-транзакция перепроверяет revision/метаданные и сохраняет ledger по ключу `video_recognition_ledger_v1` в `main`. Состояние `cleanupState='blocked_archive_safety'`.
- Повторный одинаковый результат идемпотентен, конфликт отвергается. Отказ, неполные метаданные, старый источник без SHA, изменившийся источник и сбой транзакции не должны приводить к записи результата.
- `tests/video-recognition-ledger.test.mjs` проверяет правильную запись, рестарт, отклонённые/неверные результаты, старые видео, конфликт, гонки метаданных и сохранность оригинала. Это изолированные fake-indexeddb тесты, не проверка Android.

## Непреодолённые границы этого блока
- Для входного Blob изменение байтов при сохранении прежних метаданных между асинхронным digest и write lock не доказано невозможным. Поэтому ledger не является свидетельством безопасности удаления.
- Модуль ещё не подключён к `index.html`, `sw.js` или самому распознавателю; пользовательский сценарий `capture → AI → save` **не работает** в результате этого PR.
- Защищённые архивы PASEKA01/02, rollback, запись в Галерею или Camera/MediaStore, внешний экспорт и tombstones не гарантируют отсутствие копий. `deleteEntranceVideoBlob` из #241 остаётся безусловно заблокированным.
- Нельзя считать `recognitionSucceeded` гарантом фактической корректности AI-интерпретации; требуется пользовательская верификация, если результат приводит к изменениям пасеки.
- `main`, production, живые оригиналы, Android app и IndexedDB schema не меняются. До merge и релиза необходима проверка точного HEAD и интеграционный аудит зависимых PR.

## Следующий приоритет
Проверить CI текущего HEAD. Затем отдельно спроектировать и интегрировать независимый источник подтверждённого распознавания с безопасным вызовом ledger и явной моделью ошибок. Никакого auto-delete на этом этапе.

## Дополнительный блок — защита входного сохранения

В ходе первого CI обнаружено, что `putEntranceVideo` должен отклонять дублирующий ID, а не менять оригинал. В `index.html` переведён конкретный entry point с `put` на `add`, обновлён regression тест с исполнением реальной async-функции. Это не разрешение на удаление и не защита от всех unsynchronized writers.

## Проверка уже сохранённых результатов (следующий зависимый Draft блок)

До отображения статуса `recognized` или использования результата теперь необходим `validateLedger`: строгое чтение всех записей, уникальность `source:videoId`, проверка SHA, размера, времени, JSON payload и `blocked_archive_safety`. Отсутствующая запись ledger — `ledger_missing`, не подтверждённое распознавание. Ветка не меняет пользовательское видео и не разблокирует очистку. При будущей реализации `deleted` потребуется отдельный tombstone-модуль и ревизия схемы; пока такое значение отвергается.
