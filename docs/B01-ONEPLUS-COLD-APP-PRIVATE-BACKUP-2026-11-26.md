## Исправление транспортного дефекта — 26.11.2026 (Draft #543)

**Корневая ошибка в инструментарии:** `adb exec-out` использует один поток для удалённых stdout/stderr и возвращает код локального adb, который может быть 0 при ошибке удалённой программы. Поэтому даже `printf` мог давать лишние байты, а TAR терял 512-байтовое выравнивание. Это подтверждается исходным ADB client commandline.cpp (ветка AOSP main); конкретное содержимое 270 байт не наблюдалось и не реконструируется.

**Одно исправление:** `adb shell -T run-as ru.paseka.journal sh -c '...'` — no PTY + Shell v2, разделённые потоки и настоящий remote exit; если Shell v2 недоступен, команда отказывается работать. Любой stderr в preflight или во время передачи TAR блокирует результат. Ни одна запись private stdout не публикуется. Сохранены строгая проверка Base64, TAR header/zero-end, disk SHA и отказ от перезаписи архива. **Убрана матрица пяти альтернативных команд**: только одна проверка публичной константы с тем же транспортом, что используется для копирования.

Старые `.partial` нельзя исправлять, переименовывать или восстанавливать. До exact-head Linux/Windows CI и физической проверки `DEVICE_VERIFIED` отсутствует; B01 остаётся BLOCKED. У пользователя не требуется новая серия экспериментов с shell; после доступности подтверждённого ZIP разрешена одна штатная попытка без force-stop, с существующим безопасным preflight и без загрузки конфиденциального архива в чат.

Выходное `APP_PRIVATE_COLD_TAR_ARCHIVED_RESTORE_NOT_TESTED` означает лишь созданный неперезаписанный файл из остановленного app-private sandbox с проверенной TAR-структурой и hash. **НЕ** доказательство согласованного LevelDB runtime restore, MediaStore/Gallery полноты, долгосрочной стабильности и независимого физического восстановления.

## Реальная проверка закодированного канала: BASE64_PREFLIGHT_MISMATCH до чтения пользовательских данных

В очередной физической попытке с **Force-stop NO** получен `BASE64_PREFLIGHT_MISMATCH`. Никакой TAR не создавался, поскольку проверка на публичной константе выполнилась **до** чтения данных пасеки. Вывод не доказывает отсутствия команды `base64`: доказано только несовпадение контрольной строки. Нельзя повторять полный экспорт до восстановления безопасной передачи команды оболочке Android.

**Выявленная причина в коде:** ADB формирует удалённую командную строку, объединяя аргументы; передача `sh -c` с непроцитированным текстом `set -o pipefail; ... | base64` потенциально выносит `;` и `|` во внешнюю оболочку Android, нарушая границы `run-as`. По документированным правилам ADB удалённая команда с пробелами и метасимволами требует дополнительного уровня кавычек. В `scripts/oneplus-encoded-shell.mjs` текст **фиксированной** удалённой команды теперь целиком заключён в одинарные кавычки на уровне удалённой оболочки: `run-as ru.paseka.journal sh -c 'set -o pipefail; test -d app_webview || exit 47; printf PASEKA_BASE64_PROBE_V1 | base64'`; такая же схема применяется к `tar -cf - . | base64`. Никаких пользовательских строк в эти команды не подставляется. Проверка `test -d app_webview` подтверждает каталог в контексте run-as до вывода пробной строки.

Новый Windows ZIP содержит **`PROBE-BASE64-READONLY.cmd`**. Он подключает единственный авторизованный OnePlus и запускает **только публичную константу**, не читает app-private файлы и не создаёт TAR, не запускает force-stop, не меняет Android или ПК-файлы. Результат ограничен `status: PASS|BLOCKED`, `reason`, `remoteExitCode`, `outputBytes` и `normalizedBytes`, без вывода самого ответа Android. При `BLOCKED` передать этот короткий JSON, **не** переходить к `RUN-ONEPLUS-BACKUP.cmd`. После физического `PASS` может быть отдельно проверен полный архив по прежним защитным воротам; его реальная успешность и независимое восстановление по-прежнему NOT_VERIFIED.

## Реальная первая попытка Base64-канала: нулевой decoded output, код ошибки маскировался

Пользователь запустил новый Windows-набор с **Force-stop NO**. Вывод: `Failure code: DEVICE_BACKUP_BLOCKED`, `Tar exit code: 0`, `Bytes received: 0`, `Tar stderr present: False`, `Tar stderr category: NONE`. Из этого можно установить только то, что TAR не получен; причиной может быть недопустимый Base64 или отсутствие входа при нормальном exit 0. Прежде экспортёр дополнительно **скрывал** вероятный `BASE64_TRANSPORT_INVALID`: выражение `/^[A-Z_]+$/` отбрасывало коды с цифрами (`64`), заменяя их общим `DEVICE_BACKUP_BLOCKED`. Содержимое Base64/архива, PID, пути, видео не передавать. Старые `.partial` сохранять. Ни один результат не подтверждает независимое восстановление Android/WebView/MediaStore.

## Третий read-only анализ: систематические сдвиги — отказ от сырого бинарного потока

Реальный файл 5 122 278 байт, `invalidHeaderOffset=10240`, `resyncCandidateShifts=[1]`; расширенный инспектор на ПК вернул `driftTrace.result=NO_UNIQUE_NEARBY_HEADER`, `headersAfterDefect=23`, `shiftEvents=17`, `netShift=24`. Восьми первых событий достаточно, чтобы увидеть повторяющееся изменение границ TAR в нескольких местах, но **не** доказать точную причину искажения или объяснить остаток 230 байт. Дальнейшая «починка» этого `.tar.partial` недопустима: целостность бинарных payload записей не доказана.

В Draft #543 заменён **только транспорт**, не разрешая восстановление: Android создаёт TAR в памяти/потоке и сразу передаёт его через `sh -c 'set -o pipefail; tar -cf - . | base64'`; ADB несёт ASCII Base64, а Windows Node **строго** декодирует с проверкой допустимых символов, padding и разрывов CR/LF. На телефон ничего не сохраняется и не удаляется. После получения TAR на локальный носитель, до объявления успеха, проверяются блоки 512, полная структура заголовков, две нулевые конечные секции, независимый `tar -tf`, SHA256 и повторное чтение с диска. Любое повреждение, отсутствие команды `base64` или неподдерживаемый `pipefail` — `BLOCKED`, файл остаётся непроверенным `.tar.partial`. Нет fallback на старый сырой канал. При результате `APP_PRIVATE_COLD_TAR_ARCHIVED_RESTORE_NOT_TESTED` **отдельное независимое восстановление Android и MediaStore всё ещё не выполнено**.

Старый повреждённый `.partial` сохраняется без правок. Следующий физический шаг — одна попытка с новым ZIP `RUN-ONEPLUS-BACKUP.cmd` и **Force-stop NO** (при остановленном приложении), предварительно завершив сохранение любых данных. Если отказ — передать только безопасный `Failure code` и `Tar exit code/Bytes received/Tar stderr category`; нельзя загружать TAR, переносить/публиковать данные пасеки или разрешать удаление видео.

## Второй офлайн-анализ исходного файла: ошибка на 10240, соседний заголовок +1

Из **реального** повторного запуска `INSPECT-EXISTING-PARTIAL.cmd`:
`reason=INVALID_HEADER_CHECKSUM_FIELD`, `bytes=5122278`, `remainder512=230`, `headersVerified=17`, `invalidHeaderOffset=10240`, `resyncCandidateShifts=[1]`, `endMarkerFound=false`. Итак, первые 17 заголовков TAR математически верны, на точной границе 10 KiB обнаружена позиционная ошибка, а **на один байт далее** виден заголовок, прошедший проверку checksum. Это усиливает гипотезу вставки одного байта в транспорт, но ни происхождение байта, ни сохранность полезного содержимого, ни остальные 230 байт этим не доказаны. Не называть файл «частично восстановленным», не дописывать/удалять байты и не переименовывать в `.tar`.

Тот же **локальный read-only** инспектор теперь рассчитывает `driftTrace`: после первой ошибки продолжает читать только математически корректные заголовки при **единственном** смещении в окне ±16 байт на следующей границе, ограничивает 1024 событий и 250000 записей, сообщает число повторных смещений, накопленную величину, первые 8 смещений и найденные сдвинутые конечные блоки. Наличие конечных блоков при сдвиге всё равно **НЕ** означает безопасный архив — checksum заголовка не защищает payload. Если кандидат неоднозначен, дальнейшая трассировка останавливается; `.partial` не меняется. Регрессия: два независимых +1 смещения в синтетическом TAR и сохранение исходника.

**Одна проверка на ПК**, не новая USB-передача: скачать только исправленный ZIP с успешным Linux/Windows CI и повторно выполнить `INSPECT-EXISTING-PARTIAL.cmd` на том же файле. Для дальнейшего решения нужен **только объект `driftTrace`** из JSON. Ни Android, ни ADB, ни сохранённые записи не меняются.

## Реальный аудит сохранённого файла: 17 заголовков, нарушение checksum, конец не найден

Получен аппаратно-независимый локальный отчёт инспектора по **тому же файлу на ПК**: `status=TAR_INCOMPLETE_OR_INVALID`, `reason=INVALID_HEADER_CHECKSUM_FIELD`, `bytes=5122278`, `remainder512=230`, `headersVerified=17`, `endMarkerFound=false`. Это подтверждает, что структура обрывается при проверке одного из следующих заголовков; не устанавливает, были ли байты вставлены, потеряны или в момент анализа использовано некорректное смещение из заголовка предыдущего файла. Независимое восстановление не проверено. **Нельзя извлекать/восстанавливать/обрезать/дополнять архив**, даже при exit=0 и отсутствии Android stderr.

Вместо нового ADB TAR добавлено ограниченное локальное криминалистическое уточнение в **том же** `INSPECT-EXISTING-PARTIAL.cmd`: `invalidHeaderOffset` и `resyncCandidateShifts` — поиск до ±511 байт около ожидаемого заголовка, при котором контрольная сумма TAR-заголовка математически верна. Ни один кандидат не означает автоматическое разрешение на исправление. Если кандидат содержит `230`, это поддержит гипотезу вставленных 230 байт, но не докажет сохранность всех файлов. При отсутствии кандидата — вероятнее повреждение содержимого/неверное поле размера или иная проблема потока. Никаких имён файлов/PID/содержимого в JSON не помещается. Требуется **одна** повторная локальная инспекция старого `.tar.partial`, без связи с OnePlus.

## Факт реальной передачи Android TAR: exit 0, 5 122 278 байт, остаток 230

Пользователь получил `ANDROID_TAR_ALIGNMENT_INVALID`, `Tar exit code: 0`, `Bytes received: 5122278`, `Tar stderr present: False`, `Tar stderr category: NONE`; разрешение force-stop = NO. Доступ `run-as` и контроль остановленного процесса уже пройдены. Из этих фактов нельзя заключать, что архив целый: размер по модулю 512 = **230**, несовместим с обычным завершённым TAR-потоком. Не надо без проверки дополнять/обрезать 230 байт или считать exit 0 доказательством годности.

**Ближайшее действие не требует нового обращения к OnePlus.** ZIP содержит `INSPECT-EXISTING-PARTIAL.cmd`, который предлагает выбрать уже сохранённый `PASEKA-ONEPLUS-SANDBOX-*.tar.partial` на ПК и в режиме **только чтение** анализирует стандартные TAR-заголовки, октальные/base-256 размеры, контрольные суммы заголовков, непрерывные границы записей и две нулевые конечные 512-байтовые записи. Он исследует не более 16 GiB/250000 заголовков, не распаковывает и не показывает имена файлов, не взаимодействует с Android и не меняет `.partial`. Если `END_MARKERS_MISSING` / `ENTRY_CONTENT_TRUNCATED`, файл не является доказанным архивом; нужна другая стратегия транспортного потока. Если конец найден, но после него есть лишние ненулевые байты, требуется отдельная проверяемая нормализация **новой копии**, без удаления оригинала и без автоматического восстановления. Даже `TAR_STRUCTURE_CHECKED_LOCAL_ONLY` не значит, что вся физическая база восстанавливается на Android. Не запускать повторный TAR/force-stop до анализа уже переданных 5,1 MB.

Нужно выполнить **одну** проверенную исправленную попытку с локальным согласием **No** на force-stop, не открывая «Пасеку». В случае ошибки прислать только `Failure code`, `Tar exit code`, `Bytes received`, `Tar stderr category`. `.tar.partial` остаётся непроверенным и **не должен** использоваться как архив, но программа ничего не удаляет. Физический B01 остаётся NOT_VERIFIED, пока нет настоящего архивного файла и отдельно проверенного восстановления.

## Реальный диагностический отчёт: оба источника UNKNOWN, доступ WebView подтверждён

Пользователь запустил read-only `DIAGNOSE-ONEPLUS-READONLY.cmd` на OnePlus и передал: `PROCESS_STATE_AMBIGUOUS`, в обеих пробах `pidof.state=UNKNOWN`, `ps.state=UNKNOWN`, при этом `runAsAvailable=true` и `appWebviewAccessible=true`. **Это НЕ доказательство работающего или автоматически запускающегося приложения**. В старом коде `pidof` признавал остановку только при exit 1 с пустым stdout, а `ps` только при успешном `ps -A -o NAME`, что недостаточно для разных Android/toybox.

В отдельном модуле `scripts/oneplus-process-probe.mjs` исправлены точные условия:
- exit 0 с пустым `pidof` = `EMPTY_SUCCESS`, **не самостоятельный PASS**;
- exit 1 + пустой `pidof` = `ABSENT`; числовые PID при exit 0 = `PRESENT`;
- при неподдерживаемом `ps -A -o NAME` выполнить `ps -A`, найти позицию столбца `NAME/CMD/COMMAND/CMDLINE/ARGS` и просмотреть все строки;
- только подтверждённый `ABSENT` от полного или краткого `ps` **и** корректно пустой `pidof` дают разрешение на холодное чтение; любое совпадение `ru.paseka.journal` или `ru.paseka.journal:...` блокирует копирование, а неразборчивые результаты остаются `UNKNOWN`;
- диагностический JSON показывает `pidof.reason`, `psFallback` и `state` без раскрытия процессов других приложений, конкретных PID или частных данных.

**Следующее действие:** запустить лишь проверенную обновлённую версию `RUN-ONEPLUS-BACKUP.cmd` с теми же мерами защиты; при следующем `BLOCKED` **не** запускать цикл force-stop: использовать `DIAGNOSE-ONEPLUS-READONLY.cmd` из того же ZIP и передать отчёт. Новый сценарий не считает неизвестность эквивалентом «запущено» и не меняет оригиналы.

## Фактический третий отказ — остановка ADB не сняла блокировку (26.11.2026)

В третьем реальном Windows-отчёте: `Force-stop permission: YES`, далее `Failure code: APP_MUST_BE_STOPPED_MANUALLY`. **Нет доказательства, на каком именно шаге активный процесс был обнаружен**: `pidof` или `ps`, сразу после `am force-stop`, через 1300 мс или после создания TAR. Нельзя утверждать, что приложение само перезапустилось, поскольку текущий общий код отказа скрывает место; нельзя ни повторять остановку без диагностики, ни снимать инвариант сохранности.

**Следующий единственный физический шаг — только диагностика, не резервирование.** В новом Windows ZIP нажать `DIAGNOSE-ONEPLUS-READONLY.cmd` (не `RUN-ONEPLUS-BACKUP.cmd`). Экспортёр при этом не запускается. Скрипт делает по два `adb shell pidof ru.paseka.journal` и `adb shell ps -A -o NAME`, проверяет `run-as ... pwd` и `app_webview`; возвращает обезличенный JSON с полями `first`, `second`, `runAsAvailable`, `appWebviewAccessible`, `forceStopAttempted:false`, `archiveAttempted:false`, `phoneDataModified:false`. Путь устройства, PID, имена пользовательских файлов, содержимое видео, журнал и другие пакеты **не выводятся**.

Чтение не удаляет и не меняет данные; **процесс останавливать не нужно**. JSON можно прислать целиком. Далее исправлять непосредственно установленную причину (несоответствие двух источников / отсутствие `run-as` / настоящий автозапуск) только на основании отчёта. В случае отсутствия результата — B01-PHYSICAL `NOT_VERIFIED`, ZIP предыдущей версии не повторять.

## Повторный аппаратный результат — процесс Paseka остаётся активным

Пользователь **два раза** выполнил запуск Windows-набора с одинаковым `Failure code: APP_MUST_BE_STOPPED_MANUALLY`, второй раз после рекомендации ручной остановки. Повторять тот же совет больше нецелесообразно. Это **не** доказательство, что процесс нельзя остановить через ADB, и не доказательство порчи базы.

Новое ограниченное действие доступно в Windows-наборе: **отдельное диалоговое согласие**, по умолчанию **No**, на однократное `adb -s <selected-device> shell am force-stop ru.paseka.journal`, **только** если `pidof`/список процессов обнаружили активное приложение. Перед согласованием все изменённые записи/видео необходимо сохранить; остановка процесса может прервать несохранённую работу. После согласия код повторно проверяет `pidof` и `ps -A -o NAME`, ждёт 1,3 секунды, проверяет снова, и ещё раз проверяет после завершения TAR. Если процесс перезапустился — `BLOCKED`, непроверенный локальный файл остаётся `.partial`. При отсутствии процесса ADB `force-stop` **не вызывается**, даже когда разрешён опцией.

**Не вызываются** `pm clear`, `install`, `uninstall`, `rm`, изменение настроек/данных. В JSON `deviceForcedStopped` показывает фактический факт остановки, а не всегда `false`. Никакая операция не снимает блокировку независимого восстановления Android, Gallery/MediaStore и запрет удаления видео. Прежний ZIP без окна согласия устарел. Перед запуском требуется ZIP с успешным exact-SHA CI. Это явное подтверждение пользователя **в локальном окне**, а не неявное полномочие чата остановить программу.

## Что инструмент специально НЕ делает

- Не запускает `pm clear`, `install`, `uninstall`, `rm`, `deleteDatabase` и другие команды изменения пользовательских файлов. **Только после явного локального согласия** возможно остановить процесс `ru.paseka.journal` через `adb shell am force-stop`; это не очистка сохранённой базы, но может прервать несохранённую работу.
- Не использует несуществующую кнопку «Полный архив» на установленном OnePlus.
- Не предполагает, что все оригиналы медиа находятся внутри `app_webview`: Gallery/DCIM/Download и app-specific внешние медиа **не входят** в TAR. Обособленный `ru.paseka.journal.disasterproof2` также **не входит** — это другой package.
- Не объявляет `B01-PHYSICAL=PASS`. Для снятия блокировки нужны независимое восстановление в *пустую* Android/WebView среду, контроль реальных восстановленных объектов/Blob, MediaStore/все источники, backup media-copy и контроль подписей.
- Если код возврата 1, никакой факт наличия резервной копии не подтверждён. Если 2 — существует **только ограниченный sandbox-снимок**. Нет кода выхода 0 для полного B01.

## Технический контракт F0–F3

| Зависимость | Проверка | STOP |
|---|---|---|
| Настоящее устройство | ADB один `device`, без `unauthorized/offline` | любая неоднозначность |
| Installed package | `run-as ru.paseka.journal pwd` и `ls -ld app_webview` | `run-as` недоступен |
| Согласованность snapshot | `pidof` и `ps -A -o NAME` до и после, APP должна быть остановлена вручную; `tar` exit 0 | живой процесс/ошибка/изменение во время TAR |
| Приватные данные | `adb exec-out run-as ru.paseka.journal tar -cf - .` только чтение | слишком большой, пустой, неполный TAR |
| Копия на ПК | `wx` (исключить overwrite), SHA-256 во время потока, fsync, `tar -tf` и независимый повторный SHA-256 с диска | нет места, выход ADB != 0, невалидный TAR |
| Rollback | файлы `.partial` сохраняются как непроверенный вывод; телефон не тронут | при ошибке не удалять оригиналы |
| Миграции | архив — исходные файлы APK v1.0, без преобразования схемы | **нельзя** распаковывать поверх действующей базы |

**F2 = LIMITED_SAFE_DRAFT:** Android 16/OnePlus NE2213 и `run-as` ранее сообщались, но реальный текущий ADB, установленный signer, аппаратный TAR, независимый restart/restore и доверенность USB-накопителя не проверены из облака. Требуется один физический запуск на уже подключённом ПК — без установки приложения на телефон. В случае `RUN_AS_UNAVAILABLE` не пытаться `adb root`/factory reset; сохранить отчёт блокировки и искать отдельно санкционированный экспорт из установленной версии.

**F4–F5:** отдельные тесты имитируют запуск ADB, TAR, SHA, run-as denial, несколько устройств и оба вида живых процессов. Не сравнивать результат synthetic тестов с реальным физическим доказательством. **F6–F7:** Draft PR, не merge и не deploy; изолированный физический план после архивирования.
