# PASEKA02 — проверка готовности к восстановлению и карта защищённых данных

Дата: 2026-11-20  
Статус: **изолированная тестовая цепочка, не допущена к работе с пользовательской базой**

## Дополнение 2026-11-20: строго ограниченный atomic metadata-only path

В зависимой Draft-ветке появился `js/video-archive-v2-metadata-atomic.js`, который на изолированной тестовой IndexedDB реально выполняет **атомарную** запись импорта и его откат, но **только если нет вообще никаких оригиналов видео и protected backups и recognition ledger остаётся полностью прежним**. Данные для rollback сохраняются в той же транзакции; Inspector после сбоя ничего автоматически не переписывает. Это не полноценный импорт PASEKA02 и не готовность к удалению видео. Контракт и тесты: `docs/VIDEO-ARCHIVE-V2-METADATA-ATOMIC.md`.

## 1. Что проверяет связка

1. `video-archive-v2-metadata-codec.js`: точно распознаёт `PASEKA02`, проверяет манифест и размеры; SHA-256 каждого JSON payload, отдельного Blob леткового и журналового видео; восстанавливает Data URL журнала только после проверки исходных байтов.
2. `video-archive-v2-restore-gate.js`: не принимает отсутствие/перезапись существующей истории распознавания, её tombstones, подмену оригинала другим `videoId`, не привязанные к журналу video entries и неподтверждённые метаданные источника.
3. `video-archive-v2-restore-db-preflight.js`: в одной readonly-транзакции получает актуальное состояние, ledger и количество защищённых записей.
4. `video-archive-v2-commit-lock-guard.js`: заново проверяет те же данные под единой readwrite-блокировкой, после чего **преднамеренно abort**. Даже успешный результат не становится разрешением на восстановление.
5. `video-archive-v2-restore-dry-run.js`: проверяет реальный файл, проводит обе проверки действующей базы и хэширует исходный файл **до последнего write-lock guard**. Возвращает только обезличенный отчёт, не Blob или ссылку на запись.

Вся цепочка не подключена к рабочему пользовательскому экспорту и импорту. В ней нет `put`, `delete`, `clear`, `commit` для пользовательского состояния.

## 2. Полный состав защищённых IndexedDB stores

| Хранилище | Опасность | Текущее решение |
|---|---|---|
| `main/state` | Замена данных пасеки, журналовых Data URL | Чтение внутри общей транзакции; отсутствие/несовместимая схема блокирует проверку |
| `main/video_recognition_ledger_v1` | Потеря распознанных результатов и tombstones | Сверка существующей истории с входящей; нельзя потерять/изменить запись |
| `entrance_media` | Возврат летковых Blob после распознавания | Ключи читаются под общей блокировкой; байты входящего файла сверяются SHA-256; нужен отдельный протокол live reconciliation |
| `archive_staging` | Старые staged, orphan и rollback-видеокопии | При **любой** записи блокируем v2 restore; не удаляем копии |
| `archive_history` | Неучтённый предыдущий импорт, идентификатор или rollback | При **любой** записи блокируем v2 restore, не перезаписываем историю |
| `full_backup` | Старое состояние и резервная копия оригинального видео вне staging | При **любой** записи блокируем v2 restore; магазин обязателен в read/write-lock preflight |

Последний пункт выявлен при повторном чтении живой реализации v1: `commitStagedArchive` обращается к `full_backup` в той же readwrite-транзакции. Игнорировать этот store в v2 означало бы пропустить старые защищённые данные. Проверки `#224` и `#225` в этой ветке расширены на `full_backup` с регрессионными тестами.

## 3. Почему проверка пока не разрешает восстановление

Проверенный архив и два согласованных чтения не гарантируют безопасность **последующей** записи. После окончания последней транзакции возможно новое распознавание или новая запись журнала. Любой настоящий commit должен заново выполнить все проверки под той же readwrite-транзакцией, в которой он сохраняет state, ledger, медиа и историю. Не допускается асинхронный SHA, FileReader, сетевой вызов или ожидание ответа пользователя внутри IndexedDB write-транзакции.

Необходимый безопасный порядок:

1. Отдельно согласовать изменения видеоцепочки Draft PR #205–#213 с архивной Draft-цепочкой #168/#210–#225; до этого реализации построены на разных базовых ветках.
2. Проверить архив v2 целиком, включая реальный SHA-256 каждого исходного видео и сохранившиеся результаты распознавания.
3. Подготовить stage, не создающий бесконтрольно сохраняемых видеокопий. Каждая промежуточная копия должна быть зарегистрирована и включена в будущий механизм удаления после подтверждённого распознавания.
4. Проверить разрешённую миграцию state и сохранить **все** текущие данные и запись для отката. Нельзя пересоздавать данные из частичной копии или автоматически удалять старые бэкапы.
5. Под общей readwrite-транзакцией сверить live revision, ledger, media, staging, history и full_backup. Если всё проверено, атомарно записать импорт, исходное состояние для отката, и history; при любом отказе отменить транзакцию.
6. Перед rollback повторно проверить **текущий** ledger и все актуальные оригиналы. Если после импорта распознано новое видео, старый snapshot не должен его воскресить. При неразрешимом конфликте откат блокируется, снимок сохраняется для анализа.
7. Реализовать восстановление после сбоя, идемпотентность, контроль хэшей резервных копий и учёт всех локальных копий оригинала до включения удаления.
8. Запустить регрессионную матрицу, отдельную Android test APK и физический тест на телефоне, в том числе Gallery/Downloads, offline/restart, interrupted write/rollback. Только потом обсуждать включение рабочего v2.

## 4. Критические проверки

- Не принимать `PASEKA01` под видом `PASEKA02`.
- Никакой непроверенный Blob или Data URL не может пройти под новым именем после распознавания.
- Существующие результаты/tombstones не теряются ни при импорте, ни при откате.
- Байт, размер, MIME и ID каждого journal и entrance video связываются с манифестом.
- Отказ на любое неожиданное поле, повреждённый ledger, отсутствующий protected store, прежнюю staged/history/full_backup копию.
- Конкурирующая запись после readonly-проверки улавливается повторной проверкой под write-lock.
- Финальное хэширование файла происходит **до** заключительной проверки ledger под write-lock.
- Проверка и отказ не меняют рабочую базу и не удаляют резервные копии.

## 5. Что не доказано

- Протокол атомарного restore/rollback **не реализован**.
- `archiveSafe=false` и `restoreAuthorized=false` при любом результате.
- Не доказано удаление внешних копий телефона в Camera/Gallery, Downloads и кешах Android.
- CI подтверждает только протестированный SHA; не заменяет физические испытания.
- Необходимо явное разрешение пользователя до merge, production deployment и необратимых изменений данных.

**Требование пользователя:** оригинал видео на телефоне только до долговечно подтверждённого распознавания, затем удаление всех управляемых копий. До завершения этих условий автоматическое удаление выключено.
