# B07 OP12 — инвариант нижней двухкорпусной семьи в истории

Источник: пользовательский `улей для каждого техпроцесс.docx`, абзацы **64–70**, особенно 66–69. После определения сильнейшей семьи пчеловодом эта семья остаётся **снизу** на двух корпусах, средняя и верхняя — по одному, две сетчатые диафрагмы сохраняют разделение семей. Индекс массива без позиции не означает фактическую силу семьи.

## F0–F2: дефект

В актуальном main на `dcf8a7c519a4ec64e1d2c86a0cfeb72ba3497417` `PasekaFamilyLineage.configureAlternativeWintering()` и `inspect()` сортируют `bodyCount`, допуская неверные 1/2/1 и 1/1/2. `validateOperationEvidence(...,'OP-12')` допускает эти же перестановки. Отдельный Draft #662 меняет `js/sectional-physical-layout.js`, **но не модуль lineage** — это независимый незащищённый маршрут.

## F3–F4: минимальная коррекция

Правило строго `lower:2, middle:1, upper:1` применено к трём путям: создание OP12-события, инспекция сохранённых событий, проверка доказательств операции OP12. Старый код ошибки `alternative_wintering_body_distribution_invalid` сохранён. Исторический недопустимый вариант не переписывается автоматически: возвращается ошибка, а не физическая перестройка улья. Семьи и матки не переименовываются, источник на других профилях не меняется. Регрессии обновлены для оп13/оп14, чтобы синтетические данные продолжали только корректный OP12-путь.

**Границы:** это локальная lineage-проверка. Она не устанавливает диафрагмы, не решает какая семья сильнее, не закрывает B07 activation, не пишет production/IndexedDB, не выполняет backup/restore. Draft #662 независим и должен быть безопасно интегрирован отдельно; оба уровня необходимы. Конкретный SHA и результаты Node/Android/Governance — в PR после исполнения CI. Слияние не разрешено.
