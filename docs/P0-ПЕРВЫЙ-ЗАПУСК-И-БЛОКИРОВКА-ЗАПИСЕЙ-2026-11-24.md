# P0 — безопасный первый запуск и блокировка записей при ошибке базы

Дата: 24.11.2026. Статус: **реализация в отдельной ветке / первый CI выполнен с ошибками тестовой обвязки, повторный прогон ожидается**. База изменений — реальный `main=ecea1c3c50801250d42f49366e00e1e9e96d556f` после разрешённого merge PR #468.

## F0 — аудит фактов

- Пользователь **не имеет реальных данных и видео**, готовая пользовательская версия приложения ещё не выпущена. Это не дефект и не стоп-условие для подготовки первого выпуска.
- `main/index.html` уже содержит IndexedDB v3, `paseka-v1`, основное состояние, автокопию, видео летков, startup CAS/модельные проверки, операции сохранения/импорта, пользовательские первые формы. Новый профиль улья не активируется.
- **Обнаруженный дефект:** если bootstrap/проверка данных выдаёт исключение, прежний `catch` только показывал `alert`, но оставлял активные формы/кнопки и память `S` с начальными значениями. Введённые после ошибки действия могли попытаться использовать неинициализированную БД. В случае другого открытого клиента `onversionchange` закрывал БД, но не отключал пользовательские действия.
- Существующие PR с видеопроверками (#417, #452) не устраняют конкретно этот runtime startup readiness barrier в `main`; не использовать повторные синтетические видео как замену.

## F1/F2 — контракт и минимальное изменение

Цель: нельзя сохранить или удалить данные, записать/удалить видео, запустить восстановление или выдать ложный JSON-архив, пока текущее состояние не открыто и не проверено. При ошибке — недвусмысленная блокирующая панель; в штатном новом профиле — обычная работа без миграции и без удалений.

| Файл | Изменение | Не менять |
|---|---|---|
| `index.html` | `startupWriteGate.ready=false` по умолчанию; разрешение записи только после `openDB`, `read`, валидации/миграции/проверки автокопии; блокировка на `catch` и `onversionchange`; защитные early return/reject для `save`, `write`, `putEntranceVideo`, `deleteEntranceVideoBlob`, `restoreBackup`, `restoreAutoBackup`, `downloadBackup`, `deleteAllData` | Формат базы, схема v3, технология улей/OP, валидаторы, восстановление и UI при успешном открытии |
| `tests/regression.test.mjs` | Существующие изолированные тесты обработчиков явно моделируют успешную загрузку (ready=true), чтобы новый runtime gate не давал ложных отказов | Базовые тесты CAS/migration/backup, model |
| `tests/first-launch-startup-gate.test.mjs` | Негативные проверки отсутствия действий до startup, нормальная запись после подтверждения, блокирующая панель, статический порядок ready только после проверок | Не создаёт настоящие данные или пользовательские файлы |

**Инварианты:** `startupWriteGate.ready=false` при загрузке, отказе и смене версии БД; `true` исключительно после полного успешного startup sequence. `writeMainIfUnchanged` (доверенный внутренний startup CAS) не блокируется внешним UI-gate, поскольку инициализация новой чистой БД/миграции требуют строго проверенных внутренних транзакций до открытия UI. Запись данных из пользовательских обработчиков до ready блокируется.

Не допускается аварийное `deleteDatabase`, `pm clear`, очистка хранилища, переписывание исходных видео или автозавершение физических OP. Если пользователь не видит рабочей формы из-за startup error, это сознательный fail-closed, а не повод сбрасывать хранилище.

## Степень доказательства / оставшееся

- Разработка в Draft, не в main, не опубликовано.
- Тестирование: Node regression + Android debug CI на точном SHA; отрицательные unit tests и подтверждение отсутствия изменений в production.
- Реальный PWA/WebView первый рабочий запуск с пустым новым origin, сохранение первой записи после перезапуска, offline airplane-mode, резервное копирование и независимое восстановление **ещё не подтверждены**.
- До релиза требуются независимое разрешение на merge данного PR и отдельное разрешение на production deploy. Никакие другие открытые PR не объединять. #442 video cleanup FROZEN.
