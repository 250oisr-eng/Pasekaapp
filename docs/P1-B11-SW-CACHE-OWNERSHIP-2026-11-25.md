# B11 — безопасная граница удаления версионных кешей Service Worker

**Дата:** 2026-11-25. **Scope:** только Service Worker, CacheStorage и регрессионные тесты. Веточная реализация в Draft [#478](https://github.com/250oisr-eng/Pasekaapp/pull/478); `main=0e62ced6e34ea1fc92e7e090c2c514e8306c5f8d`, опуб­ликованная/установленная версия не изменена.

## F0–F2 — фактический риск и решение

В `main` SW `paseka-shell-v317` при `activate` делает `keys.filter(key=>key.startsWith('paseka-shell-')&&key!==CACHE)`. Это удаляет не только собственные старые версионные кеши, но и **любые** записи CacheStorage с похожим префиксом, например `paseka-shell-user-content`, `paseka-shell-v317-user-backup` или даже более новую версию `paseka-shell-v319`. Фактического наличия подобных кешей у пользователя **не доказано**, но удаление без проверки собственности нарушает fail-closed правило. Существующий Draft #478 уже покрывает B11 VM lifecycle, потому исправление сделано в его же ветке без параллельного конкурирующего PR.

**F2: LIMITED_SAFE_DRAFT.** Изменение можно проверить на реальном JS-коде SW в изолированном Node VM и CI без телефона/ПК пользователя. Нельзя утверждать физическую миграцию/обновление SW на OnePlus.

## F3–F4 — инварианты и минимальное изменение

1. Удалять исключительно ключи формата `paseka-shell-vN` с положительным целым **без лидирующих нулей**, безопасно представимым в JS (`Number.isSafeInteger`), если `N < 318`.
2. Сохранить без изменения: текущий `paseka-shell-v318`, будущие версии `v319+`, чужие имена, кеши пользовательского содержимого, в том числе с похожим префиксом и `v317-user-backup`, нераспознанные/слишком большие суффиксы.
3. Поднять версию кеша с **v317 до v318**: новый worker не должен записывать свои ответы в CacheStorage одновременно со старым активным v317; при отклонённом install старый кеш не должен быть затронут новыми записями.
4. `install` продолжает запрещать `private`, `no-store`, `404`; `fetch` продолжает не перехватывать не-GET/сторонний origin/не-shell API. IndexedDB и пользовательские Blob не изменяются. Никаких shell-cache clear на телефоне, установки APK, удаления видео, import/restore.
5. Activation/skipWaiting остаются в штатных lifecycle promises; если `caches.delete` отклоняется, `clients.claim` не объявляет успешную активацию.

## F5–F7 — проверка и ограничения

- VM test `tests/service-worker-offline-lifecycle.test.mjs` запускает текущий `sw.js`; перед `install` и `activate` создает реальные для harness имена v315/v316/v317 и близкие пользовательские/future cache keys. Проверяет, что только устаревшие 3 версии удалены, остальные сохранены, нынешний v318 присутствует.
- `tests/regression.test.mjs`: две проверки текущей версии кеша обновлены с v317 на v318; `tests/service-worker-install-private.test.mjs` остаётся без смысловых изменений и по-прежнему тестирует запрещённый private/no-store/404.
- Автоматические проверки: Node/Android CI и Governance на **точном финальном SHA**; Green CI означает только синтетическое доказательство, не физический upgrade.
- **Откат:** не выпускать SW v318 до отдельного разрешения merge/release и доказанного полного внешнего архива/restore. Если регрессии FAIL — исправить в Draft; ни в коем случае не чистить CacheStorage рабочего телефона как обход. Если при будущей миграции потребуется rollback, сохранить независимо подтверждённые пользовательские файлы и отдельную работающую подписанную сборку.
- **Текущий статус:** IMPLEMENTED_DRAFT, физическая проверка v315→v318 **BLOCKED** (B01 backup/restore, B04 signer, B11 release). Main и production untouched.
