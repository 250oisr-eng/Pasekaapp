### Строгий контроль фонового выполнения G4 (без изменения состояния телефона)

**Дополнительная автоматическая проверка полного снимка:** `scripts/oneplus-g4-dumpsys.mjs` (чистый Node, без ADB-команд, без записи на телефон). Использовать только **полный** `G4-before-open.txt`, а не урезанный вывод `Select-String`:

```powershell
node scripts/oneplus-g4-dumpsys.mjs "C:\\PASEKA-QA\\G4-before-open.txt"
```

Скрипт находит изолированный блок `JOB #... ru.paseka.journal.qa.daily/.PasekaDailyArchiveJob`, его интервал/окно/ограничения и возвращает **`backgroundExecution: NOT_VERIFIED`** даже при упоминании `Last successful run`. Такое событие JobScheduler само по себе не доказывает, что ZIP записан, прочитан и проверен до открытия QA. Реальный G4 PASS потребует независимого свидетельства выполнения и нового verified ZIP с временем до первого открытия. Отрицательные тесты анализатора: `tests/oneplus-g4-dumpsys.test.mjs`.



Перед следующим **естественным** запуском приложения после наступления реального нового дня записать независимую дату устройства и полный снимок данных JobScheduler. Не полагаться на `Select-String` из полного дампа для attribution `Last successful run`: он часто захватывает соседние сервисы.

```powershell
adb shell date
adb shell dumpsys jobscheduler > "C:\PASEKA-QA\G4-before-open.txt"
adb shell dumpsys jobscheduler ru.paseka.journal.qa.daily > "C:\PASEKA-QA\G4-package-before-open.txt"
```

Команда с именем пакета зависит от версии Android, поэтому если её вывод пуст или указывает на ошибку — использовать полный `G4-before-open.txt`. Сверять именно события и время выполнения `PasekaDailyArchiveJob`, а не только `PERSISTED`/`RUNNABLE`/следующее окно. Без наблюдаемого события и архивного результата **не присваивать G4 BACKGROUND_PASS**. На 27.11.2026 уже существовал verified latest от будущей даты 28.11; `rotate` пропускает создание при `latest.day >= currentDay`, поэтому первый возможный натуральный новый архив — не ранее **29.11.2026**, если все поколения остаются проверенными. Не менять часы повторно, не сбрасывать архивы.

## 1. Что изменилось и что больше НЕ испытывать в B01

**Единственный пользовательский сценарий B01:** автоматические проверенные ежедневные ZIP **внутри телефона**, максимум два поколения («Последний» и «Предыдущий»), одна кнопка **«Восстановить»**, безопасная ротация и восстановление с подтверждением. Архивы хранятся в отдельной IndexedDB `paseka-daily-archives-v1` (Blob); не обязаны быть видимыми в «Загрузках». В фоне Android предусмотрен JobScheduler с периодом 6 часов и flex 1 час, но это **не гарантия** точного выполнения при закрытом приложении.

**Не включать в обязательную приёмку локального B01:** `paseka-full-idb-*.json` в Downloads, Android SAF-файловый диалог `ru.paseka.journal.qa.archive`, USB, внешние накопители, перенос на другое устройство, потеря телефона, копирование через облако. Ранее неуспешный цикл JSON/ZIP остаётся **историческим результатом старой функции**, не FAIL нового локального B01. SAF PR #619 и старые QA не подменяют испытание нового `ru.paseka.journal.qa.daily`. Существующие архивы/версии не удалять.

**Запреты:** не устанавливать/обновлять production `ru.paseka.journal`, не очищать хранилища и не переустанавливать установленные QA; не менять дату телефона ради ускорения; не повреждать реальные ZIP руками, не вводить в QA реальные ульи, персональные данные, видео/медиа и критические OP; не запускать восстановление production; не удалять оригиналы. Риск B02/B04/B05/B06/B10 не снят.

## 6. Автоматизированный read-only preflight на OnePlus (дополнение 27.11)

Проверенный сценарий B01 остаётся **только** на отдельном package `ru.paseka.journal.qa.daily`. Изолированный APK из [QA #45993522131](https://github.com/250oisr-eng/Pasekaapp/actions/runs/45993522131/artifacts/15193929646) имеет SHA-256 `b1a80a510a85197903d936076b93a3f133c9428e7f112082bf602e8528357bfa`, источник `70216c734e91831fe09cc7d98e777814d1a5116d`. Не использовать неизвестные сборки.

В репозитории: [`scripts/oneplus-daily-qa.mjs`](../scripts/oneplus-daily-qa.mjs), негативные тесты [`tests/oneplus-daily-qa.test.mjs`](../tests/oneplus-daily-qa.test.mjs). На ПК нужны Node 20+, один авторизованный OnePlus через ADB, Android SDK build-tools (aapt, apksigner), на Windows Java, если используется `apksigner.jar`. Настроить `ANDROID_HOME` / Android SDK; для ADB нужен `PATH` или `ADB_PATH`.

После скачивания QA APK и `QA-PROVENANCE.json` в отдельную папку, из корня репозитория:

```bash
node scripts/oneplus-daily-qa.mjs --apk /path/to/PASEKA-DAILY-ARCHIVE-QA-ONLY.apk --provenance /path/to/QA-PROVENANCE.json --report QA-G0.json
```

Первая команда **только читает** наличие package, SDK/API, SHA APK и signer; файл `QA-G0.json` создаётся с запретом перезаписи. При `apkVerified=true`, отдельном устройстве и `qaInstalledBefore=false` разрешён **только явный** свежий QA install, без -r/clear/uninstall/upgrade:

```bash
node scripts/oneplus-daily-qa.mjs --apk /path/to/PASEKA-DAILY-ARCHIVE-QA-ONLY.apk --provenance /path/to/QA-PROVENANCE.json --install-qa --report QA-INSTALL.json
```

Для следующих календарных дней **до открытия QA** можно выполнить:

```bash
node scripts/oneplus-daily-qa.mjs --report QA-DAY2-READONLY.json
```

**Ограничение:** `PACKAGE_PRESENT_NOT_EXECUTION_PROOF` показывает только присутствие пакета в диагностике JobScheduler. Не является доказательством реального запуска в фоне, записи ZIP, восстановления или доступа к содержимому IndexedDB. Для G2/G3/G5/G6 нужны осмотры приложения по таблице выше и свидетельства пользователя; G4 background остаётся `NOT_VERIFIED` без независимого события до открытия. Не вводить реальные данные. Не менять часы системы. Не применять сбои/повреждения на телефоне. Актуальность подписи и бинарника подтверждается независимо от CI кода тестов; проверка приложения на физическом устройстве пока **NOT_TESTED**.
