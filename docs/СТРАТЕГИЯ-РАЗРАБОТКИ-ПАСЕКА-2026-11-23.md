## 3. Границы ответственности и источники истины

1. **Технология улья**: «улей для каждого техпроцесс.docx», отдельно документированные решения пользователя; не переносить Farrar/Dadant/Ruta, не считать внутренние номера OP цитатой из видео. Факты, рекомендации, необязательные действия, неизвестное — разные типы требований. OP-07 0 или 12–15 календарных дней подтверждены пользователем отдельно.
2. **Физическая реальность**: пользователь подтверждает, что операция сделана; ИИ/план/таймер не меняют состояние улья. Нет дат/масс/геометрии без источника. OP-02: сироп 2:1, 100–200 г на семью В СУТКИ, поле gramsPerColonyPerDay; курс примерно 12–15 дней, белковая подкормка ежедневно, остальные нормы неизвестны.
3. **Локальная база**: реальный IndexedDB, история и устройства пользователя важнее скорости. Нет удаления/перезаписи ради миграции. Любые критические переходы валидируются локально и проходят атомарно с rollback.
4. **Исходники кода**: только проверенный текущий main и явно названные Draft PR. Не объединять по названию или зелёному CI. Документы дополняют код, а не подменяют проверку.
5. **Область автономности**: агент может исследовать/кодировать/тестировать/обновлять docs/создавать Draft. Пользователь необходим только для реального технологического выбора, разрешения merge/release, доступа к оборудованию и необратимых операций. При невозможности — блокер с вариантами, без бесконечных повторов.

## 4. Непрерывный конвейер принятия каждой новой функции (F0–F7)

**F0 — Инвентаризация.** Установить актуальный main SHA, проверить все связанные open/merged PR, наличие функции в runtime, существующие тесты, схему IndexedDB и совместимость профиля. Один ответ: «новое», «частично», «в main», «Draft», «дубликат», «неизвестно».

**F1 — Карточка контракта.** Заполнить docs/ШАБЛОН-КАРТОЧКИ-ФУНКЦИИ.md: пользовательский сценарий, роль, источник требования, обязательные и optional шаги, данные до/после, входы/выходы, опасные действия, неизвестные значения, ограничения устройств/платформ и список связанных модулей. Не приступать к большой реализации, если входной ресурс отсутствует.

**F2 — Feasibility Gate (до реализации).** Самым дешёвым способом проверить трудные внешние зависимости: установленное окружение, API Android, доступ к реальному устройству, формат исходных файлов, права/лицензию конкретной модели или датасета, наличие free-tier без счёта, стабильный офлайн-путь. Записать доказательства и критерии STOP. **Нет доказанного жизнеспособного пути — BLOCKED; нельзя подменить его сотнями синтетических тестов.**

**F3 — Данные и инварианты.** До интерфейса описать сущности/ID/события, историческую совместимость, миграции, backup/export/import, rollback, retention, конфликт одновременных изменений, права удаления, offline и отдельные профили ульев. Таблица инвариантов + отрицательные примеры обязательна для новых физических и данных операций.

**F4 — Минимальная реализация.** Один законченый вертикальный пользовательский сценарий в **небольшом main-based Draft** с тестами. Никаких массовых рефакторингов и скрытых активаций профилей, автоматических действий ИИ или «временных» permission обходов. Использовать существующие модули, не клонировать код из гигантской цепочки без сравнения.

**F5 — Уровни проверок.** (a) unit/domain + negative/fail-closed + legacy compatibility; (b) persistence/close/reopen/migration/backup/rollback для хранилища; (c) офлайн/Service Worker; (d) Android emulator; (e) **физический OnePlus** для аппаратной/UX/медиа операции; (f) реальная разрешённая выборка для распознавания. Проверять точный code SHA и финальный HEAD или доказуемый docs-only diff. Нельзя писать «прошло» о не запущенной категории.

**F6 — Интеграция.** Показать изменённые файлы, миграции, риски и cross-module regression; сравнить с main и соседними Draft; описать feature flag, recovery и план отката. Отдельное разрешение на merge. Пока #444 открыт, не merge.

**F7 — Выпуск.** Отдельное разрешение пользователя на публикацию/production. После предотвращения автоматического Pages deploy: отдельная release-source/release workflow с ручным запуском/защитой окружения. Контроль версии приложения/Service Worker, smoke на реальных сохранённых данных, откат без удаления оригиналов и observability; не считать зелёный CI фактом обновления устройства.

Статусы карточки: DISCOVERED → FEASIBILITY_PROVEN → CONTRACT_READY → IMPLEMENTED_DRAFT → CI_VERIFIED → DEVICE_VERIFIED/NOT_APPLICABLE → MERGE_APPROVED → IN_MAIN → RELEASE_APPROVED → RELEASED. BLOCKED и FROZEN — отдельные статусы. Для аппаратных функций DEVICE_VERIFIED не бывает NOT_APPLICABLE.

## 6. Специальный «анти-видео» Gate V0–V6 — закрыт до доказательств

**V0: право на данные и модель.** Точные лицензии датасета, модели и отдельно pretrained weights; источник, версия, контрольные SHA, возможность распространения/локального использования. Отсутствие веса или сомнительная лицензия ⇒ STOP.

**V1: доступный эталон.** Небольшой набор **оригинальных** видео/кадров пчёл с разрешением использования, реальные размеченные события и метрика с допустимыми ошибками, заранее установленная по задаче. Синтетический ADD-2 проверяет среду выполнения, не bee detector. Нет пригодных данных/критерия ⇒ STOP.

**V2: физическое раннее доказательство.** Одна вертикальная трасса «реальный разрешённый вход → лицензированная модель → результат → сохранённый журнал» на OnePlus 16/API36, сначала без удаления и без импорта рабочих пользовательских файлов. Замерить CPU/RAM/тепло/время/энергопотребление на реальном устройстве; не выдумывать бюджет и thresholds.

**V3: реестр местонахождения каждого исходника.** Для каждого видео: app-private/IndexedDB/MediaStore/галерея/загрузки/внешние копии, владелец, права, размер, MIME, SHA-256, идентичность, согласие. Проверить, что один и тот же файл не воспринимается как разные независимые объекты.

**V4: полный recovery.** Полный экспорт всех реально используемых storage stores, manifest, hash verification, версия формата, dry-run import, staging, атомарный commit, rollback после kill/restart/полной ошибки квоты. Не заменять реальное восстановление одиночным unit-тестом.

**V5: право удаления.** Только конкретный контролируемый временный файл приложения, после валидного фактического распознавания **и подтверждённой записи результата**, наличии разрешения, прохождения V3/V4 и отдельного пользовательского разрешения на включение. Никаких рекурсивных чисток, кэшей других приложений, Gallery/Downloads или удаления по одному истечению времени. При ошибке / нераспознанном / неполном backup → сохранить и показать статус. Настоящие оригиналы пока не удалять.

**V6: эксплуатация.** Офлайн/повторный запуск/прерывание записи/нехватка места/терминатор процесса/повтор обработки/отказ разрешения. Без доказанного конца сценария V0–V6 функция остаётся FROZEN. Пользовательское пожелание «удалять после распознавания» **не** даёт права удалить до безопасного завершения V0–V6.

Вся эта работа — отдельный будущий исследовательский трек. Она **не блокирует** независимые безопасные журнальные/технологические функции, но и не считается уже выполненной.

## 8. Технический набор заранее — не узнавать в конце проекта

- **Инструменты:** GitHub read/write PR, Fast Quality и Android Debug workflow; локальный Node test, regression fixtures; подключаемый OnePlus+Windows ADB (только по отдельному локальному запуску). Нет удалённого USB-канала от этого чата.
- **Матрица тестов:** web offline/reload, Chrome/PWA, Android WebView/API36, IndexedDB migration, multi-store rollback, free space/QuotaExceededError, stale revision, Airplane Mode, Service Worker lifecycle, собственный корректный JSON-результат с SHA и источником. Кодировка Windows PowerShell 5.1 UTF-8 BOM, кириллические пути и Android WebView Accessibility — специальные регрессии для будущих adb-скриптов.
- **Тестовые данные:** вымышленные ульи и семьи, снимки старых схем только обезличенные и разрешённые; отдельное защищённое реальное контрольное восстановление только после согласия и полного rollback. Не прикладывать приватные фото/видео/резервные копии к публичным PR или CI.
- **Права и стоимость:** реестр third-party лицензий и exact weights; политика docs/ПОЛИТИКА-БЕСПЛАТНЫХ-СРЕДСТВ.md. Если API/модель требуют оплаты или сомнительные права — не внедрять, переходить к бесплатному сценарию.
- **Доказательства:** timestamp, device/model/API, точный Git SHA, commit parent, checksums, steps, собственный JSON сценария, отдельная категория NOT_TESTED, без автоматического повышения до PASS по скриншоту запуска.
- **Риски:** шифрование/приватность и секреты (только локально/в защищённых настройках, не в Git), storage growth/backup bytes, частичный power-loss, stale SW/частичная загрузка, смена лицензии, Android SDK/Capacitor compatibility, устаревшие PR, неопубликованный code.
- **Режим дефицита ресурса:** отсутствие пользователя около ПК, нет оборудования, GitHub connector без admin, free-quota исчерпан или нет dataset/weights ⇒ зафиксировать конкретную недоступную зависимость, выполнить независимую задачу без подмены результата.

## 9. Политика PR/документации/релиза

1. Изменение с реальными функциями = один main-based Draft, краткий diff, тесты, откат, feature card. Не наращивать 700-коммитную цепочку на старый base. По возможности не больше одного активного функционального Draft.
2. Прежде чем заводить PR, GitHub search по совпадающим именам, merged_at и действующим веткам; если аналог уже в main, писать regression/integration fix, а не clone feature.
3. Законченный этап всегда обновляет PROJECT_STATUS.md, docs/ПЛАН-РАЗРАБОТКИ.md и журнал изменений. Одна верхняя **проверенная** контрольная точка; нижние старые блоки подписаны как исторические. Длинные старые карты PR — снимки, не live-state.
4. CI оценивается строго по exact SHA; отсутствие отдельного workflow для docs-only HEAD не считается FAIL или PASS кода. Сравнение с code SHA доказывает отсутствие изменения программы; Android compile не доказывает физическую функцию.
5. Merge и release — разные решения. **Пока #444 не решён, ни один новый PR не сливать.** После восстановления управляемого выпуска запрашивать отдельное разрешение на конкретное PR и затем на конкретный release. Admin settings GitHub Pages нельзя имитировать в коде.
6. Запрет удаления production БД, реальных медиа, backup, исторических записей и принудительных массовых cleanup. Любое разрушительное действие — отдельное утверждение и восстановленная тестовая копия.
7. В каждом отчёте: **в main**, **в Draft**, **на устройстве доказано**, **не проверено**, **заблокировано**, **релиз состоялся** — отдельные поля, не общий «готово».

## 10. Определение готовности и механизм остановки

Каждая feature card имеет: preflight assets, известные факты, unknowns, dependency owners, safe fallback, точные acceptance checks и выпускной барьер. Функция готова к включению только когда соответствующие факты подтверждены. Если стоп-критерий выполнен — записать код причины, последствия, обходной ручной процесс, не маскировать дефект. Не запрашивать одно и то же у пользователя после фиксации решения. Статусы BLOCKED/FROZEN не являются неудачей и не запрещают независимую разработку.

**Ближайшая реально полезная работа после этой стратегии:** выполнить по фактическому main сверку G0; отдельно спроектировать устранение #444; продолжить проверку Draft #445 и затем направлять усилия на конкретные незавершённые пользовательские сценарии, а не ещё одну видеодиагностику.
