# Mendeley v6 — реальные размеры пчёл и геометрия выбора входного разрешения

Дата: 2026-11-20. Статус: **реальные 113 bounding boxes измерены по оригинальным YOLO labels**, не модель и не проверка качества детекции.

## Прямой источник и контроль

Исходные данные — **Tomyslav Sledevic**, *Labeled dataset for bee detection and direction estimation on beehive landing boards*, версия **6**, DOI [10.17632/8gb9r2yhfc.6](https://doi.org/10.17632/8gb9r2yhfc.6), [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/). Отбор — `tests/fixtures/mendeley-v6-user-16-pairs-pinned.csv`, 16 JPG+YOLO pairs из восьми оригинальных коллекций. Полные JPEG и SHA JPG/TXT были доказаны в родительском PR #287 на exact SHA `b0d39ec04f8410f597d341c8461cdeec835fb0f6`, [Android #44770020236](https://github.com/250oisr-eng/Pasekaapp/actions/runs/44770020236) completed/success, [real 16/8 #44770020180](https://github.com/250oisr-eng/Pasekaapp/actions/runs/44770020180) completed/success.

Новый `tools/audit_mendeley_v6_real_box_scale.py` **не скачивает JPG повторно**, а по 16 pinned прямым ссылкам читает **только исходные TXT**, строго сверяет 16 label SHA-256 и YOLO `class=0`, вычисляет min(width,height) bbox в исходных пикселях и геометрию стандартного пропорционального letterbox resize в квадрат 640/960/1280. Тот же класс `bee` для всех рамок, `sourceVideoSessionIndependenceVerified=false`, `trainingAuthorized=false`, `detectorQualityMeasured=false`, `recognitionSucceeded=false`, `cleanupAuthorized=false`. Кадры пользователя, галерея Android, Service Worker и IndexedDB не затронуты. Не создаётся ни train/val/test split, ни набор pretrained weights.

Реальная [workflow #44771000596](https://github.com/250oisr-eng/Pasekaapp/actions/runs/44771000596) на кодовом SHA `ca9c6de7bcbaaaff04acaab594f06b983be6b2a9` выполнила **11 synthetic tests** и прочла все 16 pinned TXT, получив ровно 113 валидных bbox; статус проверить на exact final SHA после документационных изменений.

## Фактические геометрические измерения

Каждый bbox — **не тождественен отдельной пчеле и тем более входу/выходу** во временном трекинге. Метрики на одной небольшой выборке:
- исходный кадр **1920×1080**: минимальная меньшая сторона рамки **20.001 px**, p10 **33.000 px**, медиана **49.000 px**, p90 **66.600 px**, максимум **83.000 px**;
- при letterbox resize `scale = min(inputSide/1920, inputSide/1080)` коэффициенты **1/3**, **1/2**, **2/3** соответственно. Изображение перед padding занимает **640×360**, **960×540**, **1280×720**. Боксы масштабируются одинаково, без растяжения.

| Квадратный вход | Минимальная меньшая сторона bbox | p10 | Медиана | Боксы c min side менее 8 px | Боксы c min side менее 16 px |
|---|---:|---:|---:|---:|---:|
| **640×640** | 6.667 px | 11.000 px | 16.333 px | **3/113** | **53/113** |
| **960×960** | 10.000 px | 16.500 px | 24.500 px | **0/113** | **10/113** |
| **1280×1280** | 13.334 px | 22.000 px | 32.667 px | **0/113** | **3/113** |

В этой выборке ни один масштаб не даёт min side менее 4 px. Это **математическая проекция разметки**, а не количество нераспознанных объектов.

**Инженерное следствие:** автоматический выбор дешёвого `640` по умолчанию для первого реального детектора **не обоснован**. Стоит протестировать не меньше двух режимов, `640` и `960`, при наличии ресурса `1280`, с одинаковыми независимыми исходными кадрами и прямыми Android offline latency / RAM measurements. 960 сохраняет больше геометрических деталей; более высокое разрешение обычно дороже по вычислениям. **Ни точность, ни скорость, ни оптимальный размер пока не измерены**. Не повышать готовность модели и не менять runtime приложения по данным этой таблицы.

## Дополнительное подтверждение происхождения

В первичной научной статье о наборе указано, что изображения были извлечены из видео, снятых при **50 fps**: [Sledevič & Matuzevičius, Data in Brief, 2024](https://pmc.ncbi.nlm.nih.gov/articles/PMC10831503/), DOI 10.1016/j.dib.2024.110060. Исходная статья даёт сведения о процедуре сбора, **но не уникальные SHA видеосессий для каждой серии**. Близкие кадры внутри записи могут коррелировать; нельзя смешивать их между train и test случайным разбиением и объявлять unbiased качество.

## Дальше по главной задаче

1. Получить больше оригинальных публичных JPEG+YOLO пар/полный доступный detection dataset и приоритетно исходные source-video/session IDs и их SHA. Проверить полное покрытие, защиту от near-duplicate/temporal leakage, реальную лицензию model implementation/weights и независимый holdout.
2. Построить первую **реально обученную** compact detection model, экспорт ONNX, сравнить на независимых оригинальных группах 640/960/1280, измерить precision/recall и физические offline Android FPS/температуру/энергию.
3. Затем tracking bee IDs, калибровка пространственных зон у летка, отдельно ground truth incoming/outgoing crossings, корректная запись результата. Видео должно оставаться на телефоне до **доказанного успешного распознавания**, затем удаляться немедленно и из всех контролируемых копий; текущие `recognitionSucceeded`/`cleanupAuthorized` остаются false.

Все тесты исполняются на исследовательском GitHub Draft PR. Main, production база, приложение и пользовательские видеозаписи не изменены.
