# Изолированная проверка реальных SHA исходных видеозаписей

Дата: 2026-11-20. Статус: staging-only, без доступа к пользовательской медиатеке и без активации приложения.

## Задача

PR #279 проверяет только **заявленные** sourceRecordingSha256 в манифесте. Это защищает от очевидных конфликтов именования, но не обнаружит случай, когда в описании файла указан неверный хеш.

Новый `tools/verify-local-source-recordings.mjs` принимает **явно предоставленный каталог с локальными исходными файлами**, подготовленный вне приложения, манифест с sourceRecordingSha256 и список соответствий:

```js
const files = [
 { sha256: '...64 hex...', relativePath: 'recording-01.mp4', byteLength: 123456 }
];
const report = await verifyLocalSourceRecordings(manifest, '/trusted/staging-only', files);
```

Пути, размеры и хеши на примере условные. Инструмент не выполняет поиск по телефону, Gallery, IndexedDB, MediaStore, внешним папкам, не скачивает и не удаляет файлы.

## Фактические проверки

- Полное покрытие всех назначенных recording SHA списком файлов. `unassigned` не требует видеозаписи; назначенные записи без hash отклоняются.
- Каждому SHA соответствует ровно один локальный путь. Не разрешены повторные пути, абсолютные пути и traversal, symlink-файлы и symlink-папки. Корень каталога разрешается явно.
- Только обычные непустые файлы, не больше 2 GiB на файл и до 128 источников в одном вызове.
- Реальный потоковый SHA-256 байтов (64 KiB chunks), отдельная проверка файла до/после чтения; файл открывается только read-only. Отсутствующий файл, изменённый размер, несовпадение хеша — отказ.
- Результат `localBytesMatchDeclarations=true` означает **только совпадение хеша доступных байтов с переданным значением**. Он не проверяет, что изображение действительно извлечено из этой видеозаписи, что источник независим от других файлов, или что лицензия разрешает использование.
- Все поля `sourceIdentityVerified`, `independentHoldoutVerified`, `licenseVerified`, `trainingAuthorized`, `modelApproved`, `recognitionSucceeded`, `cleanupAuthorized` остаются false даже при положительном результате.

## Границы безопасности

- Не вызывается из пользовательского приложения, Service Worker, IndexedDB или Android.
- Не предназначен для пользовательских записей с камеры без отдельного разрешения на их чтение: тесты создают только синтетические файлы во временных каталогах.
- Параллельная замена файлов может привести к отказу; это не транзакционный snapshot файловой системы. Для provenance нужны также фактические метаданные связи frame→source video/session, лицензионные подтверждения и независимая оценка качества.
- Ограничения максимального размера и числа файлов — технические лимиты staging-инспектора, **не нормы хранения видео пользователем**.
- Никаких лицензий, pretrained weights, реального обучения или автоматического удаления не активировано.

## Проверки

`node --test tests/verify-local-source-recordings.test.mjs` — 14 сценариев (read-only success, actual mismatch, duplicate, missing, path traversal, symlink, zero size, flags). Общая сборка запускает `npm test` и Android debug build на точном SHA в PR.

## Укрепление защиты от ссылок и замены файла — 2026-11-20

В локальном staging-верификаторе выявлены дополнительные риски доступа к данным за пределами указанной папки. Добавлены проверки:

- отказ, если явно указанный корневой каталог — symlink;
- отказ от файлов с несколькими жёсткими ссылками (`nlink!==1`), так как обычный hardlink может указывать на внешнее содержимое, даже если локальный путь находится внутри staging;
- проверка нулевого символа в относительном пути **до** вызова файловых API;
- сравнение `dev` и `ino` файла до открытия и после открытия, а также после чтения; сравнение `mtimeMs`, `ctimeMs`, длины и link-count;
- повторная проверка конечного пути после чтения.

Ограничение: проверка inode/времени/пути не превращает обычную файловую систему в атомарный снимок. Враждебные конкурентные изменения остаются риском, поэтому использовать инспектор можно только на контролируемом неизменяемом staging-каталоге. Проверки не дают разрешения на обучение, распознавание или удаление записей.

Добавлено 4 синтетических регрессионных случая: symlink корня, внешний hardlink, NUL в пути и нормальный вложенный файл. Рабочие пользовательские видеозаписи не открываются.
