**Проверка кода:** 24 ноября 2026. Источники: `main=13c724a634f0987ff634a058a5fa37a1b8e20c92`, Draft #452 (полный архив v1), замороженный Draft #441 на `c0ef4afccc6060ad36898fce9d6eebde82e626cd` (PASEKA02). Это **инвентаризация контрактов по исходному коду**, не чтение рабочего телефона и не доказательство существования/сохранности конкретных пользовательских файлов.

## 2. Область уже готовых read-only функций (не переписывать заново)

- `PasekaVideoArchiveV2CopyInventory.auditManagedVideoCopies(db, guard)` использует одну readonly transaction для **пяти** stores и возвращает `copyCount`, `copies`, `issues`, `recognitionEntries`. Он сканирует текущие journal media, entrance originals, v2 pending, legacy staging, rollback_state/rollback_video, historical full_backup. Непрозрачные/неопознанные копии дают issues. Не возвращает Blob-байты и выставляет неизменно `auditComplete:false`, `byteIntegrityVerified:false`, `externalCopiesVerified:false`, `cleanupAuthorized:false`, `restoreAuthorized:false`.
- `PasekaVideoArchiveV2Snapshot.snapshotForV2` читает `main.state`, ledger и `entrance_media` из одной readonly transaction; требует идентификаторы и hash evidence. Не читает и не подтверждает внешние копии.
- `PasekaVideoArchiveV2RecordMedia.preparePendingRecordMedia` и `rehydratePendingRecordMedia` (изолированный модуль) требуют `videoId`, исходные SHA/размер и Data URL; есть лимит **16 MiB на один journal video**. Эти функции **не подключают live commit**.
- `PasekaVideoArchiveV2MetadataCodec` (`PASEKA02`) ограничен **250 MiB на entrance video**, **512 MiB на весь архив**, **128 pending videos**; превышение должно давать отказ, а не «частичный успешный архив». Это кодовые ограничения **изолированного v2**, не универсальные лимиты Android.
- `PasekaVideoArchiveV2RestoreDatabasePreflight` требует все пять stores и блокирует existing staging/history/backup records. `PasekaVideoArchiveV2EntranceAtomic` допускает только экспериментальный entrance-only сценарий, когда нет существующих entrance media; **не восстанавливает live journal record_media**, не удаляет оригиналы.
- Оставляем [issue #442](https://github.com/250oisr-eng/Pasekaapp/issues/442) **FROZEN**. Наличие функций в замороженном Draft #441 не означает доступность в рабочем `main` или наличие лицензированной модели распознавания.

## 3. Обнаруженное противоречие версий / границы архива

1. Draft #452 `PasekaDisasterArchive` находит **все stores переданной базы** и использует формат `paseka-idb-full-v1`; при отличии `db.version`, списка stores либо `keyPath` восстановление **отклоняет**. Это безопасно для отказа, но **не является миграцией**.
2. `main` создаёт три stores при DB version 3; замороженные функции #441 ориентированы на пять. Экспорт #452 из трёх-store main **не даёт доказательство** полноты данных пяти-store PASEKA02 и наоборот; каталог `main` не должен искусственно дополняться новыми stores ради прохождения теста.
3. V2 metadata codec + isolated staging не заменяют полный экспорт всех исторических/защищённых копий. `record_media` может быть в `main.state.records[].media`, в legacy backups и rollback; восстановление одной текущей записи без защищённой истории опасно.
4. `P0-OnePlus-Result.json` из ранее выполненного изолированного теста и `P1_ISOLATED_PREVIEW_SMOKE_PASS` подтверждают только соответствующие **синтетические тестовые APK**, не второй физический телефон, не полный оригинальный пользовательский архив.

## 4. Практический протокол независимого восстановления (пока НЕ выполнен)

| Gate | Минимально необходимое наблюдение / артефакт | Условие остановки |
|---|---|---|
| G0 — read-only инвентарь | Реальные DB name/version/store names, counts по каждому store, число journal Data URL/Blob, ledger, staging/rollback/backup copies; **без передачи личных видео** | Неизвестная БД/store, недоступный источник, расхождение схем или непрозрачная копия → BLOCKED |
| G1 — исходная внешняя копия | У пользователя есть **проверенный полный архив вне исходного телефона**, сохранён исходный SHA-256 и размер, файл можно открыть без исходного телефона | Неуспешное скачивание, нехватка места, разные хэши, нет второй копии → BLOCKED |
| G2 — изолированный приёмник | Другой физический Android или эквивалентное отдельно изолированное устройство; **другая package identity**, пустая выделенная test DB, нулевой доступ к рабочему `ru.paseka.journal` | Приёмник использует реальный package/DB пользователя или требует очистки текущей базы → STOP |
| G3 — перенос и preflight | Чтение **файла после переноса**, проверка SHA-256/size/manifest/store list/version/keyPath/recognition ledger/protected copies **до любой записи** | Несовместимая миграция или отсутствующий source → BLOCKED; никакой silent truncate |
| G4 — самостоятельный restore и restart | Подтверждённая запись на изолированном приёмнике, полный cold restart, неизменность всех записей, связей, ledger, Blob bytes/sha256, включая большие оригинальные MP4; повторный экспорт и независимое сравнение | Любое потерянное видео/связь, недостаточная квота, crash, timeout, несопоставимые хэши → FAIL |
| G5 — аварийный rollback | В отдельном изолированном приёмнике воспроизводимая ошибка commit/quota/interruption; проверка, что предыдущие записи/видео остались неизменны | Нет byte-for-byte rollback и полного журнала → BLOCKED |
| G6 — OS-копии | Ручная инвентаризация Camera/MediaStore/Gallery/Downloads, размеров и содержимого; копии вне области приложения остаются защищёнными | Нет доказательства покрытия ОС-источников → cleanup FROZEN |

**Артефакт приёмки** (без исходных файлов): `source_app_id`, `source_database_version`, `source_store_names`, `source_store_counts`, `backup_size_bytes`, `backup_sha256`, `receiver_package_id`, `receiver_device_model`, `restore_reopen_pass`, `original_video_count`, `verified_video_bytes`, `missing_original_count`, `unverified_external_copy_count`, `error_code`. Нельзя выводить PASS из пустых массивов или синтетического SHA.

## 5. Следующий исполнимый блок

Перед созданием ещё одного APK или изменением IndexedDB нужно подтвердить **G0** без записи/удаления на реальном устройстве и выяснить, где фактически хранится PASEKA02 оригинал. Для этого воспользоваться только read-only инвентаризацией (если установлен отдельный совместимый диагностический пакет); существующий `copy-inventory` из #441 **не включён в main**, и запускать его внутри боевого приложения сейчас нельзя. При отсутствии доступа к реальному источнику G0 остаётся `NOT_TESTED`, а не заменяется созданием фиктивных видео. Параллельный безопасный шаг — пересмотреть существующий #452 как возможную **основу v1-only** независимого восстановления, не активируя v2.

**Результат этого этапа:** `SOURCE_CODE_INVENTORY=COMPLETE_FOR_INSPECTED_REFS`; `ACTUAL_USER_MEDIA_INVENTORY=NOT_TESTED`; `INDEPENDENT_SECOND_DEVICE_RESTORE=NOT_VERIFIED`; `PASEKA02_CLEANUP=FROZEN`. Никаких работ с исходной базой пользователя не проводилось.
