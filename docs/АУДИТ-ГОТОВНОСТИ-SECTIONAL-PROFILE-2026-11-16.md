# Аудит готовности профиля sectional-multiqueen-v1

Дата: 2026-11-16  
Статус: аудит кода; профиль не активирован.

## Вывод

Технологический валидатор и физическая привязка двух больших решёток уже развиваются отдельными Draft PR #92–95. Но текущая модель приложения в целом ещё не поддерживает трёхсекционный многоматочный улей. Добавление записи в каталог профилей или включение `supportsSectionalMultiqueen` сейчас приведёт к противоречиям в сохранении, сборке, семьях, матках, инвентаре и AI-контексте.

**Решение:** не добавлять профиль в список рабочих ульев и не разрешать его эксплуатацию до устранения блокеров ниже.

## Подтверждённая геометрия и границы источника

- Пользователь подтвердил шесть 6-рамочных гнездовых корпусов, расположенных тремя парами.
- Пользователь подтвердил установку сверху двух либо четырёх 10-рамочных корпусов, полностью перекрывающих нижний блок.
- Пользователь подтвердил ровно две большие разделительные решётки, каждая размером с 10-рамочный корпус. Первая покрывает верхний корпус секции 1 полностью и верхний корпус секции 2 наполовину; вторая покрывает тот же корпус секции 2 наполовину и верхний корпус секции 3 полностью.
- Для двух решёток физический footprint уже описан в PR #92–95.
- DOCX в абзацах 22, 26 и 78–81 описывает два медовых корпуса. Позднее пользователь подтвердил допустимость двух или четырёх. Точное размещение четырёх медовых корпусов по уровням/парам в источнике и подтверждениях пока не определено. Не выводить его автоматически.
- DOCX — распознанная расшифровка видео; неоднозначные места не исправлять догадками.

## Подтверждённые блокеры в текущем коде

| Область | Наблюдение в коде | Риск |
|---|---|---|
| Каталог профилей | `HIVE_PROFILE_CATALOG` содержит рабочий профиль Farrar и шаблоны Dadant/Ruta/custom; `defaultHive()` всегда создаёт `farrar-6x6-v1`. Профиля sectional нет. | Техпроцесс нельзя корректно начать; подмена профилем Farrar недопустима. |
| Создание техпроцесса | `createSectionalTechProcess()` требует `profileId === sectional-multiqueen-v1` и `supportsSectionalMultiqueen === true`. | Добавление только ID без полноценного профиля не решает задачу. |
| Общая валидация пасеки | `validateVirtualApiary()` выдаёт `profile_operations_not_supported` для любого `profile.family !== 'farrar'`. Далее жёстко проверяет номера 1–6, ровно два honey-флага/группы рамок, вместимость 6/10 и зимние позиции `[1,3,4,6]`. | Новый профиль будет отклоняться общей проверкой даже при корректном технологическом состоянии. |
| Сборка и UI | `defaultHive()` создаёт только Farrar; обычная схема показывает фиксированные корпуса 1–6 и пару H1/H2. Ветка generic profile скрывает операции, пока профиль не ready, но не создаёт новую физическую модель. | Нет безопасного мастера конфигурации трёх секций. |
| Медовые корпуса | `js/equipment-inventory.js`: `linkHoneyPair`, `createStockHoneyPairUnsafe`, `installStockHoneyPairUnsafe` и `inspect` требуют ровно две honey-позиции/двухэлементную пару. | Четыре корпуса не поддерживаются. |
| Установка медовых корпусов | `layoutFor()` динамически создаёт honey-массивы, но для `installation:'paired'` при любом установленном элементе приводит все honey-флаги к одному значению; текущая валидация также требует всю пару. | Нельзя корректно описать выбор 2 или 4 корпусов в одном профиле. |
| Footprint медовых корпусов | `layouts.corpusIds` отображает один ID корпуса на одну позицию H1/H2; footprint на два верхних 6-рамочных корпуса не представлен. PR #95 добавляет footprint для решёток, но не для медовых корпусов. | Физическая схема над тремя секциями остаётся неполной. |
| Семьи | `layout.boxes[key].family` и `family.box` задают одну семью в одном корпусе; `validateVirtualApiary()` запрещает одну семью в нескольких корпусах. | Одна секция из двух гнездовых корпусов не может быть корректно представлена как семья; разделение одной семьи на три секции не моделируется. |
| Матки | `applyQueenChange()` хранит один `family.currentQueenId`; при замене предыдущая матка получает статус `replaced`. | Три одновременно действующие матки в трёх секциях одной исходной семьи не поддерживаются существующим UI/реестром. |
| Технологическая связь | `sectionalTechProcesses[].sections[].queenId` существует отдельно от `S.families` и `S.queens`; подтверждённой общей связи section↔family↔queen пока нет. | История семьи, история матки и технологическая карточка могут расходиться. |
| Основания/крышки и принадлежности | В физическом реестре есть типы предметов, но UI назначения предмета в секцию/позицию отсутствует. Для новой технологии требуется три отдельных донья и соответствующие крышки/принадлежности. | Нельзя доказать фактическую комплектацию трёх секций. |
| AI-контекст | `buildAIContext()` строит коробки жёстко для 1–6, honeyPair только при двух флагах, семью показывает с одним `physicalBox`. | ИИ получит неполную/искажённую картину нового профиля, даже если технологический модуль её знает. |
| Backup/restore | PR #95 передаёт полный state в R4-валидацию и сохраняет footprint в существующем JSON. Полный пользовательский backup/restore round-trip ещё не проверен. | Нельзя объявлять физическую модель завершённой. |

## Рекомендуемая последовательность работ

1. **Зафиксировать доменную модель секции и семьи.** До кода решить, является ли одна исходная семья одной колонией с тремя секциями и тремя матками либо каждая секция становится отдельной семьёй с общей историей происхождения. Модель должна связывать `sectionId`, `familyId`, `queenId`, два гнездовых корпуса, верхний корпус, отдельное дно и крышку. Не менять старые записи семей автоматически.
2. **Зафиксировать физическую модель медовых корпусов.** Поддержать два корпуса как подтверждённый исходный сценарий; для четырёх не кодировать расположение, пока пользователь не подтвердит, как они распределяются по двум footprint/уровням.
3. **Сделать profile-aware общую валидацию.** Убрать только подтверждённые жёсткие допущения Farrar и добавить отдельные валидаторы sectional. Не ослаблять проверки Farrar.
4. **Расширить inventory.** Поддержать honey-body footprint, пары/группы без смешения с решётками, три основания/крышки и установку по явным ID. Сохранять журнал перемещений.
5. **Связать семьи и маток.** Добавить section-aware связи без разрушения текущего one-family/one-box сценария старых профилей.
6. **Обновить UI.** Создание отдельного профиля, мастер трёх секций, явный выбор всех шести корпусов и `upperBodyId`, назначение маток, доньев, крышек, двух решёток и медовых корпусов. Не выводить верхний корпус из порядка массива.
7. **Обновить AI-контекст и команды.** Передавать реальные секции, семьи, маток, предметы и footprint. ИИ не должен менять физическое состояние без подтверждения.
8. **Проверить backup/restore, IndexedDB migration, offline cache и Service Worker.** Добавить round-trip и регрессионные тесты для старых Farrar-архивов.
9. **Только после полного аудита** разрешать статус `ready`, создавать ульи этого профиля и открывать OP-07.

## Незакрытые решения пользователя

- Связь одной исходной семьи с тремя секциями: одна семья/колония с тремя секционными матками или три самостоятельные семьи с общей историей происхождения.
- Физическое расположение четырёх медовых корпусов: исходный DOCX описывает два; пользователь подтвердил вариант 2 или 4, но точная схема четырёх пока не зафиксирована.

Эти решения не блокируют текущий кодовый аудит. Они понадобятся до изменения модели семей/маток и до поддержки четырёх медовых корпусов.
