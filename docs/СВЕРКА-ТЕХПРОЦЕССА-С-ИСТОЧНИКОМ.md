## Дополнение 2026-11-17 — блокеры перед реализацией OP-04/05/06

Сверка выполнена по исходному DOCX и текущим доменным модулям main/открытой ветки PR #142. Ниже перечислены расхождения, а не новые технологические правила.

1. **OP-04 и неизвестная исходная матка — исправлено в main.** DOCX прямо говорит, что при разделении пчеловод не ищет, в какой секции осталась старая матка. PR #142 объединён в main commit `02d91ef1cc57c61cbc7789b1b61eda03c8923122`: `PasekaFamilyLineage.applySplit()` допускает split без идентификации исходной матки, сохраняет `queenIdentityStatus='unresolved'` и не создаёт синтетическую матку. Это не подтверждает отсутствие матки; для него требуется отдельное явное событие `queen_absence_confirmed`.
2. **OP-06 и яйцекладка.** DOCX требует снимать сетчатые заглушки после облёта маток и начала яйцекладки, когда матки стали плодными. `getQueenPresenceStatus()` подтверждает только `confirmed_present`/`confirmed_absent`/`unresolved`; это не доказывает яйцекладку. Нужна отдельная append-only запись явного подтверждения пчеловодом наблюдаемых яиц для каждой из трёх семей. OP-06 не должен завершаться только по календарю или факту присутствия матки.
3. **OP-05 и покрытие проходов.** В описанной OP-04 конфигурации DOCX показывает четыре фактических технических отверстия и установку сетчатых заглушек с обеих сторон. Проверка OP-05 должна требовать одну заглушку на каждый фактический `openingId` текущей раскладки; helper `validateTemporaryQueenIsolationCoverage()` теперь проверяет полное покрытие, дубликаты и лишние ссылки без жёстко заданного числа.
4. **OP-04 и удаление пластиковых заглушек.** Источник перечисляет четыре пластиковые заглушки и требует убрать их перед сборкой трёх секций. `sectional-physical-layout` теперь запрещает непустой `closedOpenings` в `SIDE_BY_SIDE`.
5. **Комплектация.** DOCX перечисляет три подкрышника, одну потолочную кормушку, три крышки и три дна. Для каждого SIDE_BY_SIDE stack теперь обязательны ссылки на своё дно, крышку и подкрышник. Кормушка может быть привязана только к фактическому стеку; точное место не задаётся источником, поэтому допускается не более одной явно размещённой кормушки без предопределённой позиции.
6. **Число технических отверстий.** Для конкретной SIDE_BY_SIDE раскладки из DOCX описаны четыре отверстия: по одному на каждом крайнем корпусе и два в среднем корпусе; это также согласуется с четырьмя пластиковыми заглушками перед сборкой. Диаметр 50 мм — отдельное подтверждение пользователя. Не переносить эту конфигурацию на другие типы/варианты без источника или подтверждения.
7. **Сохранение lineage history.** `familyEvents` пока не включён в `save()` snapshot history, а `js/family-lineage.js` из PR #142 не подключён к runtime/save/backup/restore/Service Worker. До атомарного coordinator требуется определить безопасное расширение app schema, миграцию, проверку backup и включение append-only событий в snapshot history.

**Безопасный порядок:** сначала закрыть физические и lineage-контракты, затем реализовать coordinator с единым staged state и rollback. Для ветви с подтверждённым отсутствием одной матки OP-06 остаётся заблокированным: DOCX не описывает отдельную процедуру снятия заглушек в reduced two-queen scenario.

## Аудит прежней реализации OP-06 (кандидат PR #87) — 2026-11-17

Старая ветка `fix/sectional-op06-laying-observation-2026-11-16` не может быть перенесена в текущую архитектуру без переработки:

1. **Необязательность OP-05.** DOCX P18 разрешает не устанавливать временные сетчатые заглушки. В SPEC PR #87 операция OP-05 помечена `optional:false`, а OP-06 требует завершённый OP-05. Это прямое противоречие источнику. OP-06 должен допускать два фактических состояния: сетки были установлены и теперь снимаются; либо OP-05 пропущена и снимать нечего. Во втором случае требуется проверить отсутствие сеток в физическом реестре, а не создавать фиктивную операцию OP-05.

2. **Точка отсчёта срока.** DOCX P19 отсчитывает 20–21 день от первоначального разделения на три части. Для поэтапного OP-04 это `OP-04.startedAt`, а не `completedAt` второго ряда. Старый кандидат использует дату завершения OP-04 и потому может сдвинуть срок.

3. **Биологическое условие снятия.** P19 требует, чтобы все три матки вернулись с облёта и начали откладывать яйца. Одного статуса «плодная» недостаточно. Для каждой семьи/матки нужна отдельная датированная запись фактически наблюдаемой яйцекладки с явным подтверждением пчеловода.

4. **Append-only evidence.** PR #87 использует изменяемый boolean `queen.layingObserved`. Это не история наблюдения и не доказывает, когда и кем факт был подтверждён. В текущем `PasekaFamilyLineage` коллекция `queenEvents` пока содержит только `identity_confirmed`; события наблюдения яйцекладки и их runtime-валидации нет. Для OP-06 требуется отдельное append-only событие на каждую матку, связанное с семьёй, split event OP-04, techProcessId и временем наблюдения. Нельзя заменять его редактируемым флагом.

5. **Физическое снятие сеток.** `transitionOperation()` в PR #87 меняет технологический статус и версию правил, но не перемещает реальные `metalMeshPlug` через `PasekaEquipmentItems.place()`, не обновляет `temporaryQueenIsolation` и не фиксирует события перемещения оборудования. Такой переход не отражает физическое состояние пасеки и не может быть принят как coordinator OP-06.

6. **Абстрактное количество заглушек.** Старый SPEC использует `requiredMeshPlugCount` и абстрактный массив `meshPlugs`; новая физическая модель должна опираться на реальные `openingId` двухрядной раскладки (8 отверстий в описанной конфигурации) и реальные записи инвентаря.

7. **Reduced two-queen branch.** P28–P33 описывают продуктивный сценарий с двумя матками, если одна не вернулась, но точное правило снятия сеток в этой ветви не задано. Не разрешать OP-06 только по факту двух плодных маток; ветвь остаётся fail-closed до отдельного решения пользователя или однозначного источника.

8. **Необязательная вентиляционная корректировка.** P20 допускает дополнительное открытие вкладышей/летков. Это необязательное действие, его нельзя делать обязательным предусловием OP-06 или автоматически выполнять вместе со снятием сеток.

9. **Граница OP-06/OP-07.** Снятие сеток и подтверждение яйцекладки — отдельный этап. Последующие действия с подкрышниками/верхними корпусами и установкой больших разделительных решёток/медовых корпусов должны проверяться как следующий технологический переход, а не автоматически включаться в OP-06.

**Вывод:** PR #87 — источник полезного требования о наблюдаемой яйцекладке, но его SPEC и статусный transition противоречат DOCX P18 и не обеспечивают физическую атомарность. Не объединять и не переносить напрямую. Сначала реализовать append-only наблюдения для каждой матки и отдельный атомарный OP-06, допускающий отсутствие OP-05 только при подтверждённом отсутствии установленных сеток.
