# Модель семей и физической раскладки секционного улья

Статус: архитектурная спецификация для реализации. Новый профиль улья не активирован. Все правила ниже должны быть покрыты доменными валидаторами и регрессионными тестами до использования в рабочей пасеке.

## 1. Иерархия источников

1. Пользовательский файл «улей для каждого техпроцесс.docx» — основной источник последовательности технологии.
2. Явно подтверждённые пользователем параметры имеют приоритет при уточнении исходного текста.
3. Код PR #101/#104/#105/#106 — только кандидат на реализацию, не источник технологии.
4. Неизвестные размеры и параметры нельзя заполнять типовыми значениями других систем ульев.

## 2. Подтверждённые физические и технологические условия

- Конструкция: 6 шестирамачных гнездовых корпусов, 2 десятирамочных медовых корпуса, 3 донных узла, 3 подкрышника и 3 крышки.
- OP-02: сироп 2:1; 100–200 г жидкой подкормки на семью в сутки, курс ориентировочно 12–15 дней; белковая подкормка через потолочную кормушку ежедневно.
- OP-03: перестановка верхнего/нижнего гнездовых корпусов за 5–7 дней до OP-04 — рекомендация, не автоматическое подтверждение выполнения.
- OP-04: одна зимовавшая семья разделяется на три самостоятельные секции. Сначала допускается промежуточная конфигурация broodRows: 1 — по одному корпусу в каждой секции, затем второй ряд из трёх корпусов устанавливается сразу либо через несколько дней (DOCX P10–P11). Завершённая конфигурация broodRows: 2 содержит по два гнездовых корпуса на секцию. В двух безматочных секциях пчёлы выводят новых маток; одна матка остаётся исходной.
- OP-05: сетчатые заглушки на технические отверстия ориентировочно через 8–11 дней после OP-04.
- OP-06: заглушки снимаются ориентировочно на 20–21-й день после первоначального разделения (от `OP-04.startedAt`, не от позднего завершения второго ряда) и только после подтверждения облёта и фактической яйцекладки каждой из трёх маток. Для сценария с подтверждённым отсутствием одной матки правило снятия в DOCX не определено; событие queen_absence_confirmed не является разрешением на OP-06.
- OP-07/OP-14: два медовых корпуса и две большие ганемановские решётки; схема покрытия FULL/HALF: каждая решётка закрывает крайнюю секцию полностью и половину средней. Количество — две на весь улей, отдельно подтверждено пользователем 2026-11-17; DOCX подтверждает последовательную установку двух решёток, но не задаёт геометрию footprint.
- OP-08: основной медосбор; ориентир отбора — около 15 дней от начала взятка, при незапечатанном мёде дополнительная проверка примерно через 7 дней.
- OP-09: во второй половине августа сокращается летковая вентиляция по описанной в источнике схеме.
- OP-10: подготовка к зиме в середине/конце сентября.
- OP-11: стандартная зимовка — объединение в один улей на трёх гнездовых корпусах.
- OP-12: альтернативная зимовка — три семьи в одной вертикальной колонне, две сетчатые диафрагмы; распределение корпусов **перестановка [2,1,1]**. Двухкорпусная сильнейшая семья может оставаться на любом из трёх мест; нельзя фиксировать её только в нижней позиции.
- OP-13: после зимовки две однокорпусные семьи выводятся из колонны на отдельные донья; каждой добавляется ещё один пустой гнездовой корпус. Сильнейшая двухкорпусная семья остаётся на месте.
- OP-14: ранний медосбор; после отбора снимаются медовые корпуса и разделительные решётки, гнездо сокращается до трёх или четырёх корпусов, семьи объединяются; через 3–5 дней подтверждается фактическое объединение, затем выполняется повторное разделение.
- Диаметр технических отверстий 50 мм подтверждён пользователем. DOCX P10 описывает для первого ряда схему 1+2+1 (по одному отверстию в каждом крайнем корпусе и два в среднем); P11 повторяет эту схему для второго ряда. Для описанной двухрядной SIDE_BY_SIDE конфигурации это 4 отверстия в первом ряду и 8 всего, по одному на каждый крайний корпус и по два в каждом корпусе средней секции на каждом ряду. Для иных конструкций универсальное число не выводится.

## 3. Неизвестные параметры

- Высота рамки 180 мм подтверждена пользователем 2026-11-16 (отдельное уточнение, не из DOCX) и может использоваться именно как высота рамки. Высота корпуса и другие размеры этим подтверждением не определяются и остаются неизвестными. В PR #101 проверить, что 180 мм применяется только к рамке и не используется для вывода иных размеров.
- Не установлено универсальное количество отверстий для других типов и конструкций корпусов; для описанной схемы 1+2+1 на каждом из двух рядов количество выводится из P10–P11.
- Не следует подменять эти параметры размерами Farrar/Dadant или других систем.

## 4. Требования к модели данных

### Семья и линия происхождения

- Каждая самостоятельная семья имеет собственный `familyId`, состояние и историю.
- `colonyGroupId` связывает семьи, происходящие от одной технологической группы; нельзя выводить родство только из общего улья.
- История разделения/объединения — append-only события. Исторические семьи не удаляются.
- Объединение трёх семей не должно автоматически выбирать «выжившую» матку. Сохраняются все три кандидата до пользовательского подтверждения.
- После первоначального OP-04 исходная матка может быть подтверждена в одной из трёх семей. Две новые матки выводятся в безматочных секциях; их записи создаются/подтверждаются только после фактического подтверждения пользователем. ИИ не назначает маток автоматически.
- Подтверждение матки проверяет, что одна и та же матка не назначена одновременно двум активным семьям и что матка не имеет статуса погибшей/выбракованной.

### Физическая раскладка

- Физическая раскладка — отдельное актуальное состояние пасеки, не копия внутри записи технологического процесса.
- Для нового профиля предпочтительна отдельная коллекция `sectionalLayouts`, как в архитектурном варианте PR #105. Технологические записи ссылаются на состояние/версию раскладки и фиксируют выполненную операцию, но не становятся вторым источником физической истины.
- Раскладка должна описывать секции, корпуса, донья, технические соединения/отверстия, заглушки, диафрагмы, медовые корпуса и ганемановские решётки.
- Корпус и оборудование не могут одновременно числиться в двух физических местах.
- Семейная линия и физическое размещение связаны, но не взаимозаменяемы.

### Связь физического размещения корпусов с реестром оборудования

- Для секционного профиля ссылки `sectionalLayouts.sections[].broodBodyIds` и `sectionalLayouts.honeyStack.bodyIds` являются источником текущего физического местоположения корпуса. `equipmentInventory.bodies` хранит идентичность, состояние, спецификацию и историю корпуса; второе независимое поле местоположения не создаётся.
- `PasekaInventory.locateAll()` и `locateBody()` обязаны учитывать и legacy `layouts`, и `sectionalLayouts`. Если корпус найден более чем в одном физическом месте, состояние недопустимо. `PasekaInventory.inspect()` должен выполняться не только в диагностике/backup, но и в обязательном save gate.
- Корпус, установленный в `sectionalLayouts`, не может одновременно иметь складское местоположение. Текущий физический validator требует состояние `good`; `updateDetails` блокирует для установленного секционного корпуса `needs_repair`, «ремонт» и «списан», пока модель не будет отдельно расширена для безопасного обслуживания установленного корпуса.
- Миграция не выводит тип секционного корпуса только из ссылки в раскладке или маркировки: для секционного корпуса требуется явно зарегистрированная запись оборудования с профилем и вместимостью. Для гнездового корпуса проверяется вместимость 6 рамок, для медового — 10.
- Медовый стек из двух или четырёх корпусов должен состоять из полных пар: у каждой пары ровно два корпуса с одним `pairId`; половинная пара, пара между разными раскладками или корпус без пары блокируют целостность.
- Текущая секционная раскладка не хранит отдельный список рамок внутри каждого корпуса. Поэтому инвентарный интерфейс не должен показывать «0 рамок» как физический факт: для секционного корпуса количество рамок обозначается как пока не учитываемое.
- Это связующий слой физического учёта, а не активация профиля и не реализация OP-переходов. IndexedDB, `schemaVersion`, формат backup и старые записи без `sectionalLayouts` не меняются.

### Открытые физические контракты до OP-04/05/06

- DOCX на стр. 1 перечисляет три подкрышника, три крышки, три днища и одну потолочную кормушку. Пользователь отдельно подтвердил 2026-11-17, что первоначально три корпуса ставятся в один ряд на **трёх отдельных днищах**, а в каждом рабочем состоянии сохраняются ровно три подкрышника и три крыши. Для `SIDE_BY_SIDE` каждый из трёх стеков обязан ссылаться на собственные реальные `bottom`, `cover` и `topRiser`. Кормушка учитывается отдельной необязательной ссылкой на тот стек, где она фактически установлена; допускается не более одной установленной кормушки на этот улей. Источник не задаёт, в каком именно стеке она должна находиться, поэтому место не выводить автоматически.
- `temporaryQueenIsolation` хранит ссылку на сетчатую заглушку для фактического `openingId`. Добавлен отдельный `validateTemporaryQueenIsolationCoverage()` для проверки OP-05: он требует ровно одну заглушку на каждый opening из текущих технических соединений и не зашивает число проходов. Базовый layout validator не требует заглушек постоянно, поскольку они ставятся только на временном этапе.
- Источник требует удалить пластиковые заглушки при переходе к SIDE_BY_SIDE. Валидатор теперь отклоняет непустой `closedOpenings` в этом режиме.
- DOCX P10 описывает четыре технических отверстия в первом ряду (1+2+1); P11 описывает повторение той же схемы во втором ряду. Поэтому `broodRows:1` требует 4 opening references (по 2 на межсекционное соединение), а `broodRows:2` — 8 (по 4 на соединение, по одному отверстию каждого подключённого корпуса в каждом ряду). Валидатор проверяет покрытие каждого корпуса и запрещает незадействованные отверстия. Число не переносится на другие конструкции.
- Для OP-06 физическое снятие сетчатых заглушек должно зависеть не только от календаря и `confirmed_present`, но и от отдельного подтверждения наблюдаемой яйцекладки для каждой матки. Ветка с подтверждённым отсутствием одной матки остаётся fail-closed.

### Атомарные переходы

Разделение и объединение должны выполняться одной транзакцией clone-and-commit, которая согласованно обновляет:
- семьи и lineage events;
- маток и queen events;
- физическую раскладку секций;
- размещение корпусов и инвентарных предметов;
- аудит и технологическую запись.

Нельзя сначала изменить семьи, а затем отдельным несвязанным действием исправлять физическую раскладку.

## 10. Реестр оборудования и отдельная физическая раскладка — состояние на 2026-11-17

### 10.1. Реестр физических принадлежностей

- PR #134 добавил `js/equipment-items.js` и `tests/equipment-items.test.mjs` как доменный реестр.

- Каждый предмет регистрируется явно пользователем. Нельзя автоматически создавать донья, крышки, подкрышники, кормушки, решётки, заглушки или диафрагмы из шаблона.

- Для технической решётки и временной заглушки хранятся реальные `bodyId` + `openingId`. Диаметр технического отверстия — 50 мм (подтверждено пользователем). P10–P11 задают схему 1+2+1 на каждом ряду; в двухрядной конфигурации это 8 opening references. Для иных типов/вариантов корпусов шаблон опирается только на фактические `openingId`.
- DOCX, абзац 89: в каждом ряду межсекционное соединение связывает два технических отверстия, по одному на каждой из двух соседних секций; в каждом отверстии устанавливается техническая решётка, между ними предусмотрена буферная зона/коридор. Для двух рядов каждая из двух связей содержит четыре opening references (по два на ряд) и четыре реальные технические решётки. `bufferCorridorPresent` пока хранится на уровне всей связи; отдельное количество/геометрия коридоров для рядов источником не уточнены.
- Для `honeyQueenExcluder` хранится footprint двух разных верхних гнездовых корпусов: одна FULL и одна HALF. Две большие решётки покрывают левую секцию FULL + среднюю HALF и среднюю HALF + правую FULL. Их нельзя смешивать с техническими решётками Ø50.
- Для `meshDiaphragm` хранятся `stackId` и граница `lower-middle` / `middle-upper`. Для доньев, крышек, кормушек и подкрышников используется `stackId`.

### 10.2. Контракт отдельной коллекции `sectionalLayouts`

Физическое состояние — отдельная root-коллекция `sectionalLayouts`, не вложенная копия внутри techprocess record. Ветка PR #137 реализует чистый validator этого контракта; PR #105/#106 не используются напрямую.

Общие поля layout:
- `schemaVersion: 1`, `id`, `hiveId`, `profileId`, `mode`;
- `sections[]`, `stacks[]`;
- по необходимости: `technicalConnections[]`, `honeyStack`, `meshDiaphragms[]`, `temporaryQueenIsolation[]`, `closedOpenings[]`.

Секция:
- `id`, `position`, `familyId`, `broodBodyIds[]`, `upperBroodBodyId`, `openings[]`;
- `upperBroodBodyId` — явная ссылка на верхний корпус и обязательно входит в `broodBodyIds`. Нельзя определять верхний корпус по последнему элементу массива.
- Секция ссылается на `familyId`; queen ID не дублируется в физической раскладке. Источником текущей матки остаётся запись семьи и реестр маток.
- Каждое отверстие имеет `id`, `bodyId`, `diameterMm: 50`. Сохраняются только фактически существующие отверстия; их число не выводится автоматически.

Стек:
- `id`, `position`, `sectionIds[]`, `bottomItemId`, необязательный `coverItemId`, `boundaries[]`;
- в SIDE_BY_SIDE — три стека, по одному на секцию;
- в ALTERNATIVE_WINTERING_COLUMN — один стек с секциями lower/middle/upper и двумя границами lower-middle и middle-upper;
- в SINGLE_FAMILY — один объединённый стек.

Режимы:
- `SIDE_BY_SIDE`: три самостоятельные секции left/middle/right; broodRows: 1 — по одному гнездовому корпусу в каждой секции, broodRows: 2 — по два. В обоих состояниях сохраняются три отдельных стека, каждый со своим дном, подкрышником и крышей; два активных соединения left-middle и middle-right. Каждое соединение содержит по два фактических отверстия на каждый ряд: два в `broodRows:1` и четыре в `broodRows:2`; все opening references связаны с реальными корпусами и техническими решётками, а наличие буферного коридора подтверждается для связи.
- `ALTERNATIVE_WINTERING_COLUMN`: три семьи в одной колонне; распределение корпусов [2,1,1] допускает любую вертикальную позицию двухкорпусной семьи; обязательны две сетчатые диафрагмы на двух границах.
- `SINGLE_FAMILY`: одна семья на трёх или четырёх гнездовых корпусах. Для `purpose: primary_wintering` требуется явное пользовательское `closuresConfirmed: true` и отдельная установленная пластиковая заглушка в каждом объявленном техническом отверстии; подтверждение закрытия не выводится из пустой ссылки.

Медовый стек:
- `honeyStack.purpose`: early или main;
- два корпуса для раннего медосбора; два или четыре для основного медосбора;
- ровно две большие решётки `honeyQueenExcluder`, левая и правая, с footprint FULL/HALF на явно заданных `upperBroodBodyId`.
- Пары корпусов и точная схема размещения четырёх медовых корпусов не выдумываются, пока не описаны подтверждённой физической моделью.

### 10.3. Проверки и совместимость

- Валидатор сверяет семьи, `colonyGroupId`, статусы и текущую матку; не создаёт семьи/маток и не меняет физическое состояние.
- Текущий blocker до atomic OP integration: DOCX P29 допускает продуктивную двухматочную ветвь, если одна матка не вернулась с облёта. Нужен отдельный подтверждённый пользователем статус/event `queen_absence_confirmed`; null `currentQueenId` не является подтверждением отсутствия. До появления такого события layout validator принимает только `identified` и `unresolved` queen identity.
- Корпус или аксессуар не может одновременно числиться в двух физических местах; ссылки должны вести к существующим записям оборудования и реальным отверстиям/стекам.

- Старые данные без `sectionalLayouts` остаются совместимыми. IndexedDB version и `schemaVersion: 12` не меняются; миграции не нужны, пока поле остаётся необязательным.
- Service Worker кеширует `js/sectional-physical-layout.js`; версия кеша повышается при добавлении модуля.
- PR #137 не добавляет UI, CRUD физических операций, OP transitions или активацию профиля. Профиль остаётся неактивным до атомарной интеграции lineage + layout + inventory + audit + techprocess.
