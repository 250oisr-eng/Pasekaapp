## F0 — исходное состояние

Исходный `main=9b570ad1ff20c7e6cc440ecf8556b14e848667c9`. В `js/season-planning.js` функция `latestSavedInspection(records,hiveId,asOf)` фильтровала только по идентификатору физического улья. При перемещении семьи или замене семьи внутри одного и того же улья предыдущая запись другой семьи могла автоматически подставляться как «последний осмотр» текущей. История семьи в `index.html` уже различает записи по `record.family` и `familySnapshotAtTime.id`. Прямого изменения состояния нет, но неверная дата напоминания — практический риск. Аналогично `buildFeedingLedger` использовал только `record.family`, игнорируя `familySnapshotAtTime.id`, хотя историческая семья уже является допустимым источником идентичности в семейном журнале.

## F1/F2 — минимальный совместимый контракт

- Новый необязательный четвёртый параметр `familyId`. При указанном ID учитывать только записи осмотра **той же семьи** и не приписывать обезличенные старые записи. Противоречащий snapshot не подходит.
- Трёхаргументный вызов для старого интерфейса сохраняется в точности. Записи legacy не редактируются, не мигрируются и не стираются.
- В `buildFeedingLedger` когда `record.family` отсутствует, но `familySnapshotAtTime.id` существует, выдача относится к исторически подтверждённой семье. При расхождении двух ID запись показывается в отдельной группе «Семья не установлена», исключается из сумм и помечается как противоречивая; число выдач и исходные тексты сохраняются.
- При **ровно одной текущей семье** выбранного улья интерфейс применяет строгую проверку ID. При нескольких текущих семьях (в том числе незавершённый sectional профиль) автоматическая подстановка блокируется, пользователь может указать свою подтверждённую дату вручную. При отсутствии зарегистрированной текущей семьи старый hive-only режим сохранён с явной пометкой «связь с семьёй не установлена».
- Пропускаются архивные записи, некорректная и будущая дата, записи другого улья. Дата остаётся справочной; ни одна технологическая операция не завершается автоматически.
- Регистрация фактического ввода/замены матки (`applyQueenChange`) отклоняет дату позже текущего календарного дня на устройстве до любого изменения массива маток/событий. Пустая историческая дата (`null`) остаётся допустимой и не подменяется сегодняшним днём. Контракт не создаёт и не подтверждает физическую операцию автоматически.

Ресурсы: существующие `S.families`, `S.records`, `familySnapshotAtTime` и локальный модуль. Новые API, зависимости, платные средства, Android разрешения и миграции не нужны. Решение **LIMITED_SAFE_DRAFT**: узкая регрессия без записи данных. Физические действия не требуются до пользовательской приёмки.

## F0–F7 дополнение: реальная откачка и целостность архива (27.11.2026)

В исходном `saveExtraction()` было два дефекта: физическая медовая пара, статусы рамок, запись мёда и аудит менялись до подтверждения `save()`, а прямой `.map(frameLocationName)` передавал индекс массива вместо `hiveId`. `frameLocationName` затем мог создавать лишние раскладки `S.layouts['0']`/`S.layouts['1']`, из-за чего `validateRawBackupIntegrity` возвращал `orphan_hive_layout` и блокировал повторный запуск. Этот дефект впервые воспроизвёл расширенный Chromium E2E, не реальные данные пасеки.

Исправлено в `index.html`: дата фактической откачки только существующая и не позже сегодняшней; защита от двойной отправки; перед изменением данных создаётся клон; статусы рамок/снятие пары/журнал/аудит сохраняются вместе или откатываются без закрытия формы. `frameLocationName(key, hiveId)` и `frameArray(layout,key,hiveId)` теперь получают точный ID улья; отображение истории тоже передаёт настоящий ID, а не индекс. `confirmHoneyReturn` с уже существующим откатом сохранён.

Тесты `tests/regression.test.mjs`: false/throw/успешная запись откачки, рамки/аудит/журнал/пара, дата будущего, явный hive ID для рамок и названий. Реальный Chromium `tests/e2e/accounting-workflows.e2e.cjs` дополняет прежний маршрут: синтетическая запечатанная рамка → откачка → снятие пары → возврат → зимовка → `validateRawBackupIntegrity(S)` без ошибок → реальный reload IndexedDB; исходный складской корпус сохраняется, дополнительные ID являются только ожидаемой миграцией исторических раскладок.
