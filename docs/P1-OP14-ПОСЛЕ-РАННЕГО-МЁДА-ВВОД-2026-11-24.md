## Источник

Пользовательский DOCX «улей для каждого техпроцесс.docx», P78–P85. После отбора раннего мёда фактически снимают медовые корпуса и решётки, после чего три семьи объединяются на 3 или, при большом количестве пчелы/расплода, 4 гнездовых корпусах. Матка не разыскивается и программно не назначается. Ориентир 3–5 дней до следующего деления не является подтверждением выполнения.

## F0–F1: только source-bound решение

- Старт — ровно один секционный улей SIDE_BY_SIDE с подтверждённым `honeyStack.purpose=early`, 3×2 гнездовых корпуса, 2 реальных зарегистрированных медовых корпуса и 2 решётки с проверенной геометрией FULL/HALF.
- Только из реальной `sectionalLayouts` + `equipmentInventory` и однозначной ревизии. Новый familyId генерируется лишь для временного предпросмотра; новая семья остаётся с `currentQueenId=null`, `queenIdentityStatus=unresolved`.
- Пчеловод лично выбирает порядок исходных трёх верхних корпусов и опциональный четвёртый из прежних гнездовых нижних корпусов, с явно указанным местом вставки. Установленные медовые корпуса никогда не подменяются гнездовыми.
- Требуются реальное оставляемое дно, по выбору реальные крышка/подкрышник/кормушка, складские назначения каждого снятого корпуса/предмета, персональные подтверждения всех изменённых позиций и четырёх фактически выполненных действий (ранний медосбор, снятие диафрагм, семьи на отдельных днищах, объединение).
- Наличие двух событий `placement_changed` само по себе не достаточно; полная `PasekaFamilyLineage.inspect` проверяет корректность их истории, provenance тел и реальных предметов. Исходная физическая схема также проходит `PasekaSectionalPhysicalLayout.validate`.
- Никаких API записи, CAS, DONE, видеоудаления, автоматического выбора матки или тихой генерации склада. Исполнитель используется только в регрессионном синтетическом тесте.
