## 3. Несоответствия исходному DOCX

### OP-02 — количество жидкой подкормки

На странице 1 DOCX указано 100–200 г жидкой подкормки в зависимости от силы семьи и продолжительность подкормки 12–15 дней. DOCX не задаёт периодичность этой порции. Пользователь отдельно подтвердил, что 100–200 г — порция; сироп 2:1 также подтверждён отдельно и не приписывается DOCX.

Поле `gramsPerColonyPerDay` в PR #54/#58 приписывает неподтверждённую суточную периодичность. Для актуальной модели использовать `portionGrams`, не добавляя поле частоты. Этот вопрос для модели порции разрешён; дополнительное уточнение у пользователя не требуется. PR #80 на HEAD использует `portionGrams` и отдельно сохраняет обработку старого поля для specVersion 1.2.0. Ветка PR #79 всё ещё содержит суточное поле и помечена как не подлежащая отдельному слиянию.

### OP-14 — ранний медосбор

Страницы 8–9 DOCX описывают последовательность: ранний медосбор; снятие медовых корпусов и больших разделительных решёток; отбор мёда; сокращение гнезда до трёх корпусов, при избытке пчёл/расплода — до четырёх; объединение семей; через 3–5 дней повторное разделение для основного летнего взятка. Также описана альтернативная ветвь с отбором двух небольших отводков.

Текущая модель PR #54 задаёт `WINTER_ASSEMBLY_THEN_STANDARD_DIVISION`, то есть переносит повторное разделение на следующий сезон. Это не соответствует DOCX. OP-14 нужно моделировать как отдельный сценарий того же сезона, не сводя альтернативу с отводками к обязательной последовательности.

## 4. Смешение с профилем Farrar и AI-контекстом

В main присутствует профиль `farrar-6x6-v1`. Создание карточки нового техпроцесса в PR #56/#58 проверяет только `frame.heightMm === 180`. Поэтому существующий профиль Farrar проходит проверку, хотя одной высоты рамки недостаточно для доказательства совместимости всей конструкции с выбранной технологией.

В системной инструкции основного Cloudflare Worker также остаются подробные предположения о старой физической схеме Farrar, постоянных номерах корпусов и зимнем выборе корпусов. Если новый техпроцесс использует общий AI-контур без изоляции контекста, помощник может переносить старые правила в новую технологию.

Нельзя удалять или ломать существующий профиль и старый AI-сценарий. Требуется отдельный профиль/контракт оборудования для новой технологии и отдельное формирование AI-контекста, чтобы не смешивать правила.

## 5. Другие замечания

- Валидация импортированного реестра не проверяет все обязательные поля для статусов DONE, SCHEDULED, SKIPPED и FAILED так же строго, как интерфейсный переход.
- Проверка версии спецификации требует точного совпадения с текущей версией; при будущем обновлении нужен план совместимости старых записей.
- R6 — взаимоисключение OP-11/OP-12 и OP-13/OP-14 — частично реализовано, но требуется проверить на полном наборе переходов и импортированных данных.
- PR #55 описывает аддитивную миграцию схемы приложения 12→13 без повышения версии IndexedDB. Реальную миграцию пользовательской базы и восстановление backup на этом этапе не запускали.
- Полный npm test, Android build и проверка на физическом устройстве в рамках данного аудита не выполнялись. Результаты, заявленные в описаниях PR для других SHA, не считаются проверкой текущего HEAD #58.
