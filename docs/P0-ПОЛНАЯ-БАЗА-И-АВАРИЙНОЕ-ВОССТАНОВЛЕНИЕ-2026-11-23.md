# P0 — сохранность всей базы пасеки и аварийное восстановление

Дата: 2026-11-23. Статус: IMPLEMENTED_DRAFT; CI_PENDING; DEVICE_RESTORE NOT_TESTED. Новый механизм в Draft #452; в main отсутствует.

## Подтверждённый пользовательский приоритет
Сохранность всей базы пасеки и полноценное аварийное восстановление важнее дополнительных оптимизаций. Изолированные OnePlus P1-тесты доказывают только запуск процесса и сохранность внешнего контрольного файла, **не** сохранность IndexedDB.

## Исходные факты по main (13c724a634f0987ff634a058a5fa37a1b8e20c92)
- `index.html`: `downloadBackup()` сериализует только `{app:'Paseka',state:S}` в JSON, после `saveQueue`. Это не целостный экспорт всех object stores.
- `openDb()` использует основное хранилище, backup store и отдельный IndexedDB object store `entrance_media`; последняя не входит в JSON state.
- `restoreBackup()` валидирует JSON, выполняет `assertRawBackupIntegrity`, `migrateState`, `validateVirtualApiary` и атомарный `writeMainWithBackup` с ожиданием `saveQueue`. Нельзя объявлять полное восстановление только по наличию этих защит.
- `restoreAutoBackup()` работает с локальной автокопией; потеря телефона/очистка origin удаляет обе локальные копии.
- Пользовательские видеозаписи (включая PASEKA02) имеют отдельные provenance, quarantine и cleanup ограничения: #442 FROZEN. Резервная копия всех учётных записей и истории не даёт разрешения удалять оригиналы видео.
- Действующие Draft PR #73, #156, #203 и архивные ветки требуют сравнения с current main; не переносить старые ветки целиком, не дублировать уже объединённые исправления.

## Договор сохранности: что считать *полной* базой
Инвентаризация должна охватывать ВСЕ существующие данные, а не только три базовых массива: ульи, семьи, матки и линия происхождения; физические корпуса, рамки, уникальные ID и история перемещений; технологические операции OP; осмотры, журнал, события, измерения Varroa и фактические обработки; инвентарь; мёд/откачки; зимовка; подкормки; вложения и связи с ними; вспомогательные справочники и пользовательские настройки; версии схемы, revisions, audit/history; очереди неоконченной работы; отдельные IndexedDB stores; Service Worker/cache только если они содержат незаменимые пользовательские данные. Нельзя маркировать как INCLUDED без проверки конкретного ключа/store и двухстороннего round-trip.

Для сырого видео нужен отдельный согласованный контракт: временный оригинал до достоверного завершения распознавания; пока pipeline/restore не подтверждены, никакой auto-delete. Если архив не включает видео, пользователь должен видеть это ДО экспорта; база/журнал должны сохранять ссылки/метаданные непротиворечиво.

## Требуемая реализация по этапам
1. **F0 / Coverage matrix:** перечислить фактические IndexedDB базы/stores/ключи/связи, Blob, in-memory/pending, inline Data URL, schema 1–15+ и Android origin. Каждый пункт: INCLUDED / EXCLUDED_WITH_WARNING / UNKNOWN; UNKNOWN блокирует заявление FULL_BACKUP.
2. **F1 / Export:** согласованный versioned manifest (версия формата, schema, дата, размеры, перечень разделов, count, SHA-256 payload), snapshot на согласованной ревизии; ошибки/quota/cancel не дают архиву статуса «успешно». Проверяемое копирование ВНЕ телефона; без сетевых и платных зависимостей.
3. **F2 / Preflight:** автономная проверка checksum, manifest, schema compatibility, cross references и полных вложений без единого изменения рабочих данных; запрещён silent downgrade/частичный импорт.
4. **F3 / Staging + atomic commit:** восстановление только из проверенного staging; согласование межвкладочных записей, CAS revision; отказ, quota, crash, abort, duplicate events и отсутствие места должны оставлять старое состояние без потерь. Если нельзя сделать одну IndexedDB transaction для всех необходимых stores, явно спроектировать journal/rollback protocol, а не заявлять atomicity.
5. **F4 / Rehearsal:** изолированное устройство/профиль с тестовыми записями всех типов; export→wipe ONLY ISOLATED TEST DB→import→reopen→force-stop→reopen→offline→verify counts, IDs, links, media hashes, timelines, migration results. Тест на повреждённую копию, прошлую схему, отсутствие свободного места и interruption at each commit boundary.
6. **F5 / Real recovery:** лишь после F4 — недеструктивное ручное резервное копирование реальных данных с внешним подтверждением SHA/размеров и read-back. Удаление/очистка реальной базы не допускается без отдельного разрешения. Результат восстановления на чужом/чистом тестовом профиле проверять отдельно, без подмены результатами synthetic emulator.

## Запреты и критерии готовности
- Нет изменений production DB, schema, миграций, Service Worker и релиза в этом документальном этапе.
- Нельзя смешивать «восстановился процесс» с «восстановилась база».
- Нельзя считать локальную автокопию аварийным восстановлением при потере/поломке телефона.
- FULL_BACKUP/RECOVERY=PASS только после сохранения и чтения независимого файла, полного round-trip, crash/rollback проверок и физического доказательства на конкретной версии устройства; отсутствие проверок = NOT_TESTED.
- Следующее кодовое изменение — только после полного coverage и анализа конфликтующих Draft; отдельный Draft PR, регрессионные тесты, точные CI SHA, затем отдельное пользовательское решение об интеграции.

## Выполненный технический аудит и реализация Draft #452 (23.11.2026)

- Фактический IndexedDB: `paseka-v1`, version **3**, stores: `main` (key `state`), `full_backup` (key `previous` и возможные прочие записи), `entrance_media` (inline keyPath `id`, Blob-оригиналы). Отдельные записи всех stores учтены экспортом, не только текущие три известных ключа; обнаружение нового store выполняется динамически.
- В `main.state` сохраняются `meta.schemaVersion` (сейчас поддержка до 15), `meta.revisionId`, данные ульев/семей, журнал/аудит, рамки/инвентарь, OP/физическая модель и остальные поля state без выборочного обрезания. Сложные медиа внутри state также сериализуются; неизвестные классы/типы блокируют экспорт, а не тихо отбрасываются.
- Новый `js/disaster-archive.js`: один read-only snapshot всех object stores; envelope `paseka-idb-full-v1` с обязательными именами store, `keyPath`, `autoIncrement`, records и counts, SHA-256 от канонического JSON payload. Сериализация поддерживает JSON primitives, массивы/объекты, `Blob`, `ArrayBuffer`, `Date`; неподдержанные типы → FAIL CLOSED. Экспорт не меняет основную базу.
- Preflight целиком вне write transaction: SHA-256, store schema, число записей, формат значений и `validateBackupState` + `assertRawBackupIntegrity` для `main.state`. Неизвестный формат/версия, повреждённые Blob и неполный store → отказ.
- Restore: двойное ручное подтверждение проверенной ВНЕШНЕЙ копии прежнего состояния, CAS текущего `meta.revisionId` в **одной** IndexedDB readwrite transaction по всем stores; `clear/put` и rollback целиком при abort. При успешном commit запускается перезагрузка приложения. Это работает только для совместимой структуры существующей базы; автоматических миграций нового формата, опасного downgrade и silent partial restore нет.
- Прежние ручной JSON и локальная `full_backup.previous` оставлены без изменений; они **не** эквивалентны этому полному внешнему архиву. `sw.js` v315 включает новый JavaScript в offline shell. `scripts/prepare-web.mjs` уже копирует весь каталог `js` для Android.
- Автоудаление PASEKA02 **не активируется**; снятие #442 FROZEN невозможно из этого PR. Никакой production upload, restore, merge или release не совершены.

### Ограничения готовности

1. Экспорт формирует крупный JSON в оперативной памяти; при больших видео возможен дефицит памяти. Отказ должен быть показан как FAIL, а не как успешный архив. Внешнее сохранение и повторное чтение файла до утраты устройства должны быть проверены вручную.
2. SHA-256 — защита от случайных повреждений; без подписи/доверенного канала не защищает от злоумышленной подмены архива с пересчитанным SHA.
3. Тестировать в изолированной базе с несколькими Blob, старыми схемами, crash, quota, конкурентными вкладками, сменой Android origin. Только после этого возможно решение об integration; production не трогать.
4. Предварительная проверка не заменяет фактическую физическую проверку восстановления всей базы. `DEVICE_VERIFIED` и `RELEASED` — NOT_TESTED.
