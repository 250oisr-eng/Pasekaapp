# Автоматизированная проверка «Пасеки 2.0» без регулярного участия пользователя

Контрольная точка: 2026-11-23. Этот документ — рабочая стратегия испытаний, **не подтверждение, что нижеописанные будущие тесты уже реализованы**. Источники: `.github/workflows/quality.yml`, `.github/workflows/android-debug.yml`, `package.json`, фактический main, Draft #445; [полная стратегия](СТРАТЕГИЯ-РАЗРАБОТКИ-ПАСЕКА-2026-11-23.md).

## 1. Уже работающая автоматика

| Событие | Где исполняется | Фактический результат | Чего она НЕ доказывает |
|---|---|---|---|
| Push в рабочую ветку с `index.html`, `js/**`, `tests/**` или другими путями из `quality.yml` | Fast quality checks: `npm install`, `npm test` (node --test tests/*.test.mjs) | Зеленый или красный статус на конкретном SHA; все unit/regression тесты автоматически | Android WebView, фактические сохранения пользователя, публикацию |
| Push/PR с путями из `android-debug.yml` | Build Android APK, предварительные regression tests, сборка debug | Компиляция и артефакт debug APK без необходимости действий на телефоне | Установку/открытие конкретной версии на OnePlus, доступ к камере, устойчивость real media |
| Каждый рабочий сеанс агента/уже существующая ежедневная задача | Проверка GitHub main/Draft/CI на SHA и сверка PROJECT_STATUS | Сводка фактов и следующий независимый блок, когда задача исполнилась и имела GitHub доступ | Гарантию, что фоновая задача всегда может взаимодействовать с USB пользователя; новый release |
| Конкретное изменение модели данных | `tests/*.test.mjs`, существующие IndexedDB/rollback/legacy tests и новые regression tests рядом с изменением | Доказательства только покрытых входов и simulated faults | Реальный power-loss и восстановление production на телефоне |

**Пример реальной регрессии:** при разработке [Draft #445](https://github.com/250oisr-eng/Pasekaapp/pull/445) исходный обработчик закрывал диалог записи до успешной записи в IndexedDB. Новый путь: snapshot до изменения, confirm, один durable save, rollback при ошибке; защитить повторную отправку и не закрывать форму при отказе. Автоматизированный `tests/journal-persistence-rollback.test.mjs` проверяет именно этот JS-путь с имитацией save success/failure и двойного нажатия, **но не выдаёт mock save за настоящую IDB транзакцию**. Для реальных транзакций используются отдельные тесты IndexedDB.

## 2. Тесты, обязательные по типу изменений (без телефона)

1. **Обычная запись данных**: happy path; валидация отсутствующего/архивного объекта; инварианты; точные типы, единицы, дата; сохранённый исторический контекст; отказ write, конфликт revision; retry без дублей; откат уже изменённого memory state; доказательство, что UI не показывает «Сохранено» до успешного commit.
2. **Изменение физической модели**: уникальные ID и ownership; инвентарь и зеркальные ссылки; невозможные комбинации секций/корпусов/летков; матки, семьи, рамки; применимость только нужному профилю, неизменность Farrar; forbidden transition; подтверждение пользователя.
3. **Миграции и архивы**: fixture старой схемы, no-op при текущей схеме, восстановление после прерывания, invalid/corrupt payload fail-closed, old/new records, SHA, полный реестр stores, отсутствие удаления оригиналов; save queue и stale-revision race; fail on quota.
4. **Varroa/корм/мёд/зимовка**: фактические записи отделены от наблюдения/плана; источники норм; запрет автоматического заполнения неподтверждённых доз; единственно верные units; журнал после reload.
5. **Голос/ИИ**: offline commands формируют только черновик; недостоверные данные/невыбранный улей — запрет записи; физическая операция требует отдельного подтверждения; нет тайного платного/API вызова.
6. **Service Worker**: кеш только собственных известных assets; не перехватывает API/чужие origin/cache; offline-js не получает HTML; private/no-store не сохраняется; обновление версии не стирает пользовательские данные; негативные регрессии.

Каждый PR добавляет **минимально необходимый проверяемый сценарий**, не сотни имитаторов реальности.

## 3. Когда действительно нужен OnePlus и пользователь

| Событие | Требуется OnePlus? | Пользовательская работа |
|---|---|---|
| Изменение только документации, доменной формулы, валидации | Не требуется для базовой CI проверки | 0 действий |
| Новый экран/функция без новых Android permissions | Только выпускная UX-проверка после CI | Один тестовый сценарий, когда версия действительно готова |
| Новый видеокодек/камера/Android permission/офлайн-хранилище | Требуется до объявления DEVICE_VERIFIED | Одна объединенная безопасная диагностика на тестовых данных |
| Изменение destructive restore / delete | Требуется отдельное согласие и изолированная база, полная проверенная копия | Не запускать до явного решения и полной V0–V6 |
| Power-loss / реальные оригиналы / MediaStore | Требуется после юридического/технологического V0–V4 | Без разрешения не трогать реальные файлы |

**Правила одного диагностического пакета:** Windows PowerShell 5.1 UTF-8 BOM, запуск из кириллического пути, точный adb serial/package version, fail-closed, проверка реального WebView результата (не путать adb screenshot transfer stdout с сообщением об успехе), machine-readable JSON с категориями PASS/FAIL/NOT_TESTED и SHA сборки; отсутствие удалений, записи production и изменения сети без отдельного разрешения. Проверку повторять только после *содержательного* исправления, не ради получения зеленого статуса.

## 4. Новые автоматические сценарии — порядок реализации

| Приоритет | Дополнительный сценарий | Условие включения |
|---|---|---|
| QA-1 | Транзакционный журнал: submit/confirm/reject/double click/save failure/rollback/retry на production handler | В [Draft #445](https://github.com/250oisr-eng/Pasekaapp/pull/445), CI на exact code SHA |
| QA-2 | Связанный журнал через IndexedDB с fake-indexeddb и пересозданием соединения; недопустимый legacy rollback | После анализа существующих storage tests, без дублирования |
| QA-3 | Небольшой DOM/WebView интеграционный тест: «выбор улья → диалог → сохранение → reload → запись видна» на синтетической базе | Лёгкий бесплатный раннер, не заменять ручным apk-тестом |
| QA-4 | Совместимость PWA офлайн/cold start после реальной публикации + сегрегация cache/private API | Только после исправления #444, без тестового неразрешённого deploy |
| QA-5 | Видео от летков на реальном OnePlus с измеренными метриками и восстановлением | Только после V0–V6 и снятия FROZEN #442; синтетический ONNX smoke не подходит |

Новые сложные тестовые инфраструктуры запрещены, пока не доказана необходимость, бесплатность и отсутствие дублирования. Один красный CI — диагностировать конкретный лог/строку и исправить код или неверное ожидание теста, затем однократно перепроверить. **Не объявлять PASS при CANCELLED, PENDING, SKIPPED или отсутствующей проверке**.

## 5. Зависимости GitHub, точные SHA и безопасность выпуска

- Fast Quality по main HEAD #45126886680 и Android APK #45126886481 — PASS на f981e36d807d9cfb6c6077b7e3575f9abd42daf8. Это не доказательство нового Draft #445, который имеет собственные runs.
- При обновлении документационного HEAD без изменения runtime подтверждать сравнение diff с последним code/test SHA; точное имя SHA в отчёте обязательно.
- Тестовые ветки имеют собственный cache и не пишут в production. Обе системы запускаются автоматически по изменениям в исходниках/тестах; документационные изменения не должны заставлять бесконечно строить APK.
- Ветвь release полностью отделить от main до следующего merge: #444. Успешный обычный Android build не разрешает публиковать APK, GitHub Pages или Worker.
- Если фоновая автоматизация не смогла исполниться, текущие доказательства от неё не меняют статус; сохраняется исходный план и GitHub-контрольные точки.

**Приоритет пользователя:** минимальная помощь — автоматические CI, один конкретный ручной тест только когда аппаратный end-to-end необходим, ноль повторов уже пройденных синтетических проверок.
