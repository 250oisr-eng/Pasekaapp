## F1 — контракт и границы

Один скачиваемый ZIP-артефакт `PASEKA-UNIFIED-OFFLINE-CHECK-CENTER` из GitHub Windows CI; **одна кнопка** `ПРОВЕРИТЬ-ПАСЕКУ.cmd`. Команда должна:

1. Проверять SHA-256 заранее включённых файлов комплекта **до** выполнения скрипта, взаимодействующего с Android. Если файл изменён, отсутствует или manifest неверен — `PASEKA_CHECK_HUB_BLOCKED_PACKAGE_CHANGED`, **никаких ADB-операций**.
2. Запускать лишь существующий изолированный офлайн-центр: `adb devices/getprop/pm path`, штатные `run-as id` и чтение имён **трёх фиксированных** WebView-каталогов, плюс проверка полного локального экспортированного файла (если такой файл уже существует). Не пытаться выполнить новые команды `pull/install/pm clear/rm`.
3. Выдавать новый JSON S0–S7 со строго разграниченными `PASS/PARTIAL/BLOCKED/NOT_TESTED/FROZEN/NEEDS_INPUT`. **PASS S0 (USB) и S7 (локальный отчёт) не означает PASS B01, cold offline или video.**
4. Без интернета, пользовательских секретов и реальных данных в CI. На ПК запись разрешена только для нового локального JSON-отчёта; предыдущие отчёты не удалять и не перезаписывать.

Если авторизованного устройства/полного архива нет, система обязана безопасно завершиться с частичным результатом, а не требовать пользователя немедленно подключить телефон.

## F2 — feasibility

Наличие бесплатной Windows GitHub Actions среды, встроенного Node, существующего `fake-indexeddb`, ADB в штатных каталогах Android SDK и текущего Check Hub подтверждено предыдущим успешным Windows CI на #528. Архив, закрытый ключ обновления и полный MediaStore не доказаны, следовательно физическое восстановление/обновление **не запускать**. SHA256 manifest проверяет только целостность внутри скачанного ZIP и не является криптографической подписью издателя. Источник архива сверяется по точному SHA CI.

## F4–F5 — реализация и регрессии

Новый `physical-test-readiness.mjs` добавляет оценку без доступа к файловой системе или устройству. `verify-physical-kit.mjs` контролирует bounded manifest: точный GitHub SHA сборки, полный список файлов, размер, SHA-256, проверку путей и запрет symlink. Выполнение Check Hub невозможно до успешной проверки хешей. `tests/physical-test-readiness.test.mjs` и `tests/verify-physical-kit.test.mjs` проверяют отсутствие ложных PASS и отказ при модификации/подмене, без настоящих пользовательских архивов.

Windows workflow должен собрать **реально самостоятельный** ZIP, записать манифест по фактическим байтам, запустить чекер, затем дважды выполнить packaged Check Hub без телефона и проверить 2 неизменяемых JSON-отчёта. После этого намеренно изменить файл **только в временной тестовой копии** и проверить, что integrity preflight блокирует её. Прогон Node/Android/Governance на точном SHA обязателен. Отдельно проверить, что файл отчёта не содержит serial, ID семей, реальных архивов, видео и секретов.

## F6–F7 — как проводить физические испытания

**Сейчас 0 действий пользователя.** Если понадобится локальный тест и будет доступ к ПК, пользователь один раз скачивает ZIP из **успешного** Windows CI актуального SHA, распаковывает в отдельную папку, подключает ранее авторизованный OnePlus (если нужно новое доказательство) и запускает `ПРОВЕРИТЬ-ПАСЕКУ.cmd`. Затем передаёт только последний `PASEKA-CHECK-*.json`, **не исходный JSON, видео, ADB serial, ключи, APK и TAR**. Если подключение уже доказано и не изменилось, повторное USB-тестирование не требуется; достаточно локального export preflight.

После получения доказанной полной B01 копии и rollback потребуется **отдельное явное разрешение** на поздний Android UI/cold-offline тест — этот комплект сознательно не установит новую сборку сам. Без лицензированных весов и V0–V6 удаление оригиналов остаётся запрещённым.

**Итог готовности:** `KIT_READY_FOR_READ_ONLY_PREFLIGHT` только после PASS точного Windows CI; `DEVICE_FULLY_TESTED=false` до физических доказательств. Нельзя подменять одно другим.
