## Итог

Архивная цепочка содержит полезные независимые компоненты, но не является готовой к слиянию с текущим `main`.

Подтверждено в текущем `main`:

- Используются stores `main`, `full_backup`, `entrance_media`.
- Схема состояния приложения — 15.
- Ручной `downloadBackup()` формирует JSON только из `{app:'Paseka', state:S}`.
- `writeAutoBackup()` сохраняет состояние, но не оригиналы видео из `entrance_media`.
- Видео хранятся отдельными Blob-записями в `entrance_media`.

Это прямая несовместимость, которую нельзя устранять простым повышением номера версии: необходимо проверить структуру и валидатор состояния для схем 13–15 и правила миграции.

## Несовместимости и риски переноса

### 1. Версии

- Текущая IndexedDB: версия 3.
- Архивная ветка добавляет `archive_staging` и `archive_history`; в старой документации этот этап описан как IndexedDB v4, позднее ветка меняет схему дальше.
- Текущее состояние приложения: schemaVersion 15.
- Архивный codec v1 заявляет поддержку state schema 1–12.

Нужна новая проверка совместимости с schema 15 и явное решение о версии IndexedDB. Нельзя полагаться на номер версии из старой ветки без проверки полного кода upgrade path.

### 2. Модель медиа

Архивная цепочка включает миграцию фотографий в отдельный Blob store и переключение ссылок. Это отдельный проект изменения модели хранения медиа, не обязательный для первой безопасной версии полного backup видео летка. Не включать эту миграцию в минимальную интеграцию полного архива без доказанной необходимости.

### 3. Квоты и дублирование

Staging и rollback могут временно хранить несколько копий больших Blob. Ротационные snapshots также могут расходовать квоту. Перед интеграцией нужно определить верхние границы, проверить доступное место до старта, корректно обрабатывать QuotaExceededError и не удалять старые данные автоматически ради освобождения места.

### 4. Android

Документация старой ветки сама отмечает, что успешный CI/APK не доказывает фактическое сохранение и открытие архива через Android WebView/браузер. Нужен ручной тест на устройстве до объявления функции готовой.

### 5. Публикация

Любые изменения Service Worker могут обновить кеш при следующем открытии опубликованной PWA. Разработка должна оставаться в Draft PR; не объединять и не запускать публикацию без отдельного разрешения.

## Уточнение после построчной проверки runtime-кода

Проверены ключевые участки codec, restore manager, DB upgrade и snapshot module.

### Точная граница codec v1

В `js/paseka-archive.js` экспортный адаптер явно принимает только `state.meta.schemaVersion` от 1 до 12 включительно. Это не только формулировка документации: schema 13, 14 и 15 будут отвергнуты с `UNSUPPORTED_STATE_SCHEMA`. Поэтому v1 codec в текущем виде несовместим с `main`.

### Текущий автоматический backup

В `main` `writeAutoBackup(state, expectedRevision)` сохраняет объект `{at, state}` в `full_backup/previous`. Видео из `entrance_media` в эту запись не включаются. Это подтверждает, что текущий автоматический backup не является полной копией данных.

### Ротационные снимки из PR #15–#17

В отдельном модуле `js/paseka-auto-snapshots.js` заданы лимиты:
- максимум 3 снимка по умолчанию;
- 8 MiB на один снимок;
- 16 MiB суммарно.

Снимки сериализуют только состояние и проверяют revision/checksum. Они не включают Blob из `entrance_media`. Эти лимиты относятся к отдельному store `auto_snapshots`, а не к полному архиву и не устраняют дефект backup видео. Их можно оценивать независимо, не переносить как замену полного архива.

### Фактический upgrade path в PR #40

Ветка PR #40 открывает IndexedDB как версию 9 (текущий main — версия 3) и при upgrade условно добавляет:
- `archive_staging` с индексами `sessionId`, `kind`, уникальным `backupId`;
- `archive_history`;
- `auto_snapshots`;
- `media_blobs`;
- `media_migration_journal`;
- `media_reference_journal`.

Создание stores проверяет их отсутствие и не удаляет существующие stores, но это всё равно крупный скачок версии 3 → 9, объединяющий несколько независимых функций: архив, ротационные снимки и миграцию фотографий. Для минимальной поставки полного архива не следует автоматически переносить `media_blobs` и журналы миграции фото: это не требуется для упаковки уже отдельно хранимых видео летка.

При разработке собственной миграции нужно явно проверить upgrade из реальной базы версии 3, повторный запуск/открытие, заблокированную старую вкладку, ошибку создания индекса и поведение при нехватке места. Условное создание stores само по себе не доказывает безопасность всего upgrade path.

### Изменение плана

Минимальный безопасный scope первой реализации:
1. Не менять схему фотографий и не переносить `media` в `media_blobs`.
2. Сохранить текущий `main/state` и `entrance_media` без изменений формата их рабочих записей.
3. Создать отдельную additive IndexedDB migration только для staging/history полного архива, после аудита требуемых stores и индексов.
4. Реализовать новый формат архива, который явно поддерживает schema 15; старый v1 оставить только для чтения тех версий, которые он действительно валидирует.
5. Ротационные снимки состояния держать отдельной необязательной функцией; не обещать, что они защищают оригиналы видео.


## Решение пользователя: временное хранение оригиналов фото и видео

Уточнение пользователя от 2026-11-18 имеет приоритет над ранее предложенной концепцией «полного архива с оригиналами медиа». Фото и видео нужны как исходный материал для анализа. После успешного анализа сохраняются результаты, а оригиналы могут быть удалены. Постоянное включение оригиналов в резервные копии не требуется.

### Новый целевой жизненный цикл медиа

1. **Получение материала.** Фото/видео сохраняется локально до анализа. Это временное рабочее хранилище, а не архив.
2. **Офлайн-очередь.** Материал и метаданные очереди должны переживать закрытие приложения, перезапуск устройства и отсутствие сети. Подключение к ИИ может быть отложено до появления связи.
3. **Статусы обработки.** Как минимум различать «ожидает анализа», «анализируется», «ошибка/повтор» и «результат сохранён». Статус «результат сохранён» устанавливается только после надёжной записи результата в журнал/карточку соответствующей семьи.
4. **Ошибка или незавершённая обработка.** Исходный файл не удаляется; пользователь может повторить анализ.
5. **Успешная обработка.** После проверки сохранности результата оригинал разрешено удалить. Не удалять исходник до завершения транзакции сохранения результата.
6. **Ручное сохранение.** Если пользователь хочет оставить оригинал, приложение должно позволять не удалять его автоматически (детали UX согласовать при проектировании).

### Требования к резервным копиям

- Экспортируемый backup сохраняет состояние пасеки, журнал, подтверждённые факты и результаты анализа.
- Оригиналы фото/видео, уже обработанные и подлежащие очистке, в backup не включаются.
- Временные необработанные медиафайлы также не входят в переносимый backup по умолчанию. Они остаются только на устройстве до анализа.
- В интерфейсе backup нужно явно сообщать, что ожидающие анализа оригиналы не попадут в архив и при потере/очистке устройства до анализа не восстановятся.
- Не создавать ложное обещание «полного архива всех файлов». Называть backup копией данных пасеки и результатов анализа.
- Автоматические локальные snapshots не должны копировать временные медиафайлы.

### Архитектурные последствия

- Не разрабатывать упаковку Blob из `entrance_media` в переносимый архив ради постоянного хранения оригиналов.
- Не переносить фото в отдельный `media_blobs` store только ради архивирования.
- Сначала исследовать фактические схемы хранения фото и видео в текущем main, места создания/изменения/удаления записей и связи с семьями.
- Определить минимальный локальный media lifecycle: стабильный идентификатор задания, ссылка на семью/осмотр, время создания, статус, данные повтора и защита от удаления во время анализа.
- Очистка должна быть идемпотентной и безопасной при закрытии приложения/сбое между сохранением результата и удалением оригинала. После перезапуска приложение должно уметь завершить отложенную очистку только для заданий с подтверждённо сохранённым результатом.
- Нельзя считать ответ внешнего ИИ доказательством сохранения результата в приложении. Удаление разрешается только после локальной проверки записи результата.
- Не удалять медиа при ошибке, тайм-ауте, отмене, отсутствии сети или неподтверждённом результате.
- Не менять существующие пользовательские записи массово. Сначала покрыть lifecycle тестами.

### Изменение объёма прежнего аудита

Ранее описанные пункты о переносе «полного состояния + оригиналов `entrance_media`», проверке повреждённых staged-видео и rollback видео **не являются требованиями целевого backup** и считаются заменёнными этим решением. Из старой цепочки PR #9–#40 могут быть полезны общие идеи безопасного импорта, проверки целостности и транзакционного восстановления состояния, но медиаархивирование не переносить автоматически.

Новый порядок работ:
1. Проверить текущие механизмы хранения фото/видео и их привязки к семьям/осмотрам.
2. Спроектировать и реализовать локальную офлайн-очередь анализа с безопасным жизненным циклом оригиналов.
3. Определить формат backup состояния и результатов анализа без оригинальных медиа.
4. Сохранить совместимость со старыми JSON backup и текущей schema 15.
5. Добавить тесты: перезапуск в ожидании, offline/online переход, ошибка и повтор, отмена, сохранение результата, сбой до/после записи результата, отложенная очистка, ручное сохранение оригинала, отсутствие медиа в backup.
6. Только после этого решать, нужны ли staging/atomic restore-компоненты из старой цепочки; не переносить ненужную сложность.

Это пользовательское продуктовое решение. Оно отменяет прежнее предположение о необходимости постоянного резервирования оригиналов фото и видео.


## Фактическая инвентаризация текущего media lifecycle в main

Проверена текущая ветка `main` на SHA `8144ec8fe7e61c2f70f067c78f299bf0e7551dd7`, включая `index.html`, `js/entrance-analysis.js`, `sw.js` и regression tests.

### 1. Видео летка — отдельный локальный store и очередь-заготовка

- IndexedDB object-store version остаётся 3; store `entrance_media` создаётся отдельно с keyPath `id`.
- Видео летка сохраняется Blob в `entrance_media` вместе с hiveId, временем, метаданными, технической оценкой качества, статусом очереди и полями повтора.
- Статус при добавлении: `waiting_for_server`.
- UI прямо сообщает, что сервер анализа не подключён, передача и автоматическое удаление не выполняются.
- `js/entrance-analysis.js` содержит переходы статусов, предварительную проверку метаданных/качества кадров, вычисление метрик по уже предоставленным tracks и правила аномалий. В нём нет детектора объектов/пчёл и нет реализации отправки на AI-сервис.
- `canDeleteVideoOriginal(record)` возвращает true только если статус `completed`, `resultPersisted === true` и `serverDeleteConfirmed === true`. Однако фактическая автоматическая цепочка завершения анализа и удаления не подключена.
- В текущем UI пользовательская команда удаления вызывает прямое удаление Blob по ID после confirm; это ручное удаление, отдельное от автоматического lifecycle.

### 2. Фото и видео записей журнала

- Фото сжимаются до JPEG (максимальная сторона 1600 px, quality 0.82), затем кодируются Data URL.
- Видео осмотра до 50 MiB и до 40 секунд также кодируется в Data URL.
- Вложения сохраняются непосредственно в `S.records[].media[]`, а не в отдельном временном store и не в очереди анализа.
- Архивирование записи журнала не удаляет вложения: текст интерфейса прямо обещает сохранение истории и прикреплённых файлов.
- Ручной JSON backup сериализует весь `S`; следовательно, включает эти Data URL. Автоматическая копия также получает переданный state. Снимок исторического состояния при этом удаляет media из нескольких коллекций, но основная запись и полный текущий state сохраняют медиа.
- Автоматической обработки/очистки этих вложений в проверенном коде не найдено.

### 3. Фото других модулей

- `plantObservations[].media[]`, `pesticideIncidents[].media[]` и `deadoutReviews[].media[]` хранятся как часть state (вложенные объекты с Data URL в существующих сценариях).
- При построении некоторых исторических снимков `save()` исключает поле `media` из этих коллекций, но основной state остаётся с вложениями.
- Проверенный код показывает сохранение/отображение этих фотографий, но не подтверждает отдельный AI-analysis pipeline для них.
- Для этих медиа также не найден общий временный store/статус ожидания анализа.

### 4. Резервные копии и текущая фактическая граница

- `downloadBackup()` делает `JSON.stringify({app:'Paseka',state:S})`; фото/видео, встроенные в state, попадают в ручной backup.
- `writeAutoBackup(state,...)` сохраняет переданный state в `full_backup/previous`; оригиналы, встроенные в state, также могут попасть в автокопию.
- Видео летка из `entrance_media` не входят в эти state-копии, поскольку находятся в отдельном store.
- Поэтому предыдущая формулировка «backup только состояние и результаты, без оригиналов» пока не соответствует текущему коду: это целевое требование пользователя, но его ещё предстоит реализовать.
- Нельзя просто удалять `media` из `S` при экспорте без изменения модели хранения: это потеряет вложения, которые сейчас могут быть единственным доступным оригиналом, и нарушит обещанное сохранение вложений у архивных записей.

### 5. Вывод и безопасный порядок реализации

Существуют как минимум две несовместимые модели хранения: отдельный Blob store для видео летка и inline Data URL в state для фото/видео журнала и других модулей. Смешивать их одним общим delete routine нельзя.

До кода необходимо утвердить технический контракт:
1. Все новые исходные материалы, ожидающие анализа, хранятся отдельно от долговременного state в локальном временном media store; записи очереди содержат ссылку на улей/семью/осмотр/тип задачи и статусы, но не дублируют Blob в JSON state.
2. После перезапуска очередь восстанавливается из IndexedDB. Без сети элементы остаются локальными и ожидают подключения.
3. Результат анализа сначала проходит валидацию и сохраняется в долговременную запись приложения; только после подтверждения транзакции разрешается перевод задания в состояние, допускающее удаление оригинала.
4. Сбой между сохранением результата и удалением должен быть восстанавливаемым: отдельный статус очистки/идемпотентная уборка после перезапуска. Сбой до сохранения результата никогда не разрешает очистку.
5. Ошибки, отмена, недоступность модели, неподтверждённый ответ и низкое качество материала не разрешают автоматическое удаление.
6. Для старых inline вложений нужна миграция/совместимость с чтением старых backup. Не удалять существующие Data URL автоматически при первом запуске новой версии.
7. Экспорт backup должен включать подтверждённые результаты и исключать только те исходники, которые уже перенесены в новую временную очередь и ясно помечены как необработанные. До завершения миграции legacy media сохраняются, а UI должен предупреждать о legacy вложениях, которые ещё включаются в backup.
8. Нужен явный путь пользователя оставить оригинал; его предпочтение должно блокировать автоматическую очистку.
9. AI provider/transport не определён. Бесплатность обязательна; нельзя подключать платный API или делать вид, что техническая проверка качества кадра является распознаванием пчёл. Реальный provider adapter — отдельный этап после выбора/проверки бесплатного решения.
