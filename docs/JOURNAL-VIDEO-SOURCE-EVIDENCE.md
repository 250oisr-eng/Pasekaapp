# Стабильная идентичность и SHA-256 для новых видео журнала

Дата: 2026-11-20. Статус: изменение рабочего пути **только в Draft PR**, без deployment/merge.

## Подтверждённая проблема

В `index.html` обе формы добавления видео в журнал — `addCapturedVideo` и файлы `recordForm` — ранее сохраняли `{kind,name,type,data:DataURL}`. В этих записях не было гарантированных `videoId`, `sourceSha256`, `sourceBytes`. Новый архивный адаптер PASEKA02 не мог безопасно сопоставить такой оригинал с распознаванием. Старые пользовательские записи **не подлежат автоматической модификации**: отсутствие identity должно оставаться явным барьером, а не компенсироваться предположением по имени файла.

## Изменение

- Новый `js/journal-video-source.js`: `prepareVideo(file,deps)` до создания записи проверяет файл (непустой, не более действующего предела 50 MiB), видеотип, новый ID, SHA-256 оригинального Blob; затем читает Data URL, нормализует только его MIME заголовок и **повторно проверяет SHA-256 и размер уже декодированных байтов**. Ошибка любого этапа блокирует добавление.
- Новые видеовложения имеют `videoId`, `sourceSha256`, `sourceBytes`, `sourceEvidenceVersion:1` и прежний формат `data:video/...;base64,`. Фото и исторические media не изменяются.
- `index.html`: оба пути новой записи вызывают `prepareJournalVideoAttachment`; существующие вложения при редактировании копируются без преобразования. Ни удаление, ни распознавание, ни запись ledger автоматически не запускаются.
- `sw.js`: версия PWA shell повышена и модуль включён в precache, иначе офлайн-журнал мог бы не сохранить видео.
- `scripts/prepare-web.mjs` уже копирует целиком `js` в Android WWW, поэтому новых изменений сборки не требуется.

## Регрессионные проверки

`tests/journal-video-source.test.mjs`: реальный `PasekaSha256` и архивный `PasekaVideoArchiveV2RecordMedia`, byte-exact Data URL, ID, размер, SHA, обработка пустого MIME, mismatch при FileReader, ошибка crypto и неподдерживаемый формат; подтверждение, что старое видео без ID остаётся прежним и требует ручного разрешения при PASEKA02 import; оба UI пути и offline precache.

## Безопасность

Нет удаления старых записей, Data URL или оригиналов. Данный PR **не подключает** распознавание, не делает cleanup и не доказывает отсутствие внешних копий Android. Автоматическая очистка заблокирована. Для реального Android нужны испытания камеры, галереи, офлайн сохранения, обрыва связи и проверка старых записей. Переход в production и merge требуют отдельного разрешения.
