# P1 — сезонная модель v2: безопасный контракт, этап 1
Дата: 2026-11-23. Основа: Draft #453; новый этап — отдельная stacked ветка, НЕ в main.
## Область
`js/sectional-season-ledger-v2.js` — изолированный объект `PasekaSectionalSeasonLedgerV2`, пока без подключения к `index.html`, coordinator v1, offline cache или IndexedDB. Это НЕ включение профиля и НЕ миграция пользовательской базы.
- `inspect` отвергает некорректные записи, дубли ID, вторую активную запись, пропущенный номер цикла, непоследовательные события и завершённые циклы без последнего события `CYCLE_CLOSED` с причиной и подтверждением.
- `previewV1` создаёт только read-only копию исходного объекта `modelVersion=1` с полным original; ставит `REQUIRES_RECONCILIATION`. Ничего не переименовывает, не удаляет и не сохраняет.
- `planNewCycle` возвращает план в памяти лишь после терминального события предыдущего цикла. Никаких физически выполненных операций это не подтверждает.
## Не реализовано
Нельзя переносить эти функции в рабочую БД без проверки идентичности маток/семей, взаимосвязи физических компоновок, границ зимовки и повторного разделения; терминальный event не должен изготавливаться программно. Нужна отдельная логика OP08–14, проверка snapshot evidence и реальная миграция/rollback, включая полный восстановимый архив P0 #452.
Пока исходная v1 остаётся источником чтения. Тесты изолированного контракта не доказывают корректность OP08–14, Android или реального восстановления.

## Этап 2: v2 evidence, dual read, OP08–14 transition gate
- `js/sectional-season-evidence-v2.js`: снимки layout + корпусов/рамок + семей/маток до/после, связывание истории без изменения предыдущих событий. Требуются подтверждение пользователя, явные проверяющие функции прежнего/нового state и `validateTransition`. Результат — **только staged ledger**, не утверждение об успешной записи. Оба набора данных должны сохраняться одной CAS/IndexedDB-транзакцией.
- `js/sectional-season-operation-rules-v2.js`: правила переходов OP08–14. Факты о запечатанности рамок, хранении корпусов/решёток, сохранении трёх маток и зимней ветке не подставляются автоматически. OP11/OP14 допускают terminal stage только после подтверждённого перехода в `SINGLE_FAMILY`. OP12 остаётся отдельной зимовкой с 3 семьями; OP13 возвращает раздельную компоновку.
- `js/sectional-season-dual-read-v2.js`: чистый dual read старых `sectionalTechProcesses` и новых `sectionalSeasonCycles`, явное сравнение полного v1-original. Повреждение/несогласованное происхождение блокирует чтение, без попытки «починить» исходную историю.
- `planCloseCycle`: запрещает завершать цикл без последнего подтверждённого физического этапа OP11/OP14. Новый цикл не планируется при сомнительном терминальном событии.
- Тесты в `tests/sectional-season-{ledger,evidence,dual-read,operation-rules}-v2.test.mjs`: повторный цикл, миграция без мутаций, снимки и цепочка, заблокированные и разрешённые операции, неверные сезонные переходы. GitHub CI — отдельное доказательство только для точного HEAD.
### Что это НЕ завершает
Пока только чистые доменные проверки: **не существует** production-ready физического `completeOP08–14`, общего атомарного IndexedDB handler, полноценных форм для OP04–14, реального полного backup/restore с сезонным контейнером и физических тестов на OnePlus. Отсутствие этих пунктов делает P1 **незавершённым** и профиль недоступным для выпуска. Модули v2 намеренно не подключаются к runtime/SW до закрытия зависимостей. Нет подтверждённого безопасного OP06 для двух маток.
